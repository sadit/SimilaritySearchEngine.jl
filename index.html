SimilaritySearchEngine.jl

An embedded similarity search engine for Julia, and the service layer built on it

This site documents one repository that contains two packages. They are developed, tested and released together. The division between them is the following:

SimilaritySearchEngine SimilaritySearchServer
location the repository root server/
function an embedded, in-process library: storage, indexing and search a REST API, two command lines, and an asynchronous job queue
defined concepts RocksDB column families, inverted files, proximity graphs HTTP status codes, exit codes, job spools, access tokens
undefined concepts HTTP, processes, tokens index construction and storage

Storage, indexing and search are implemented in the engine. The server calls the engine’s public API and does not use its internal modules. The engine contains no reference to HTTP status codes or to process exit codes.

This separation determines how failures are reported. The engine raises a typed error, and the category of that error states the nature of the failure. Each interface then maps the category to its own vocabulary: HTTP status codes, command-line exit codes, or a branch in a Julia program.

Choosing a package

To search within a Julia process, use the engine. It requires a working directory, a project handle, and function calls. No server process, network port or serialization is involved. Access control is provided by the file permissions of the working directory.

: Begin with Getting started, then read Architecture.

To provide search to other processes, machines or programming languages, use the server. It holds one EmbeddedEngine per dataset, and translates each request into one engine call. An operation over an entire collection is executed in a separate Julia subprocess, so that a query is not delayed by a long operation such as allknn.

: Begin with the server tutorial, then read the server manual.

Both packages are documented in one generated reference: Engine API and Server API.

Installation

Neither package is registered in the Julia General registry, so both are installed from this repository. The dependencies of the engine are registered: SimilaritySearch.jl, TextSearch.jl, RocksDB.jl, and the RocksDB_jll binaries. No other repository has to be cloned, and the RocksDB binaries are not compiled here:

using Pkg
Pkg.add(url="https://github.com/sadit/SimilaritySearchEngine.jl")

The server is the server/ subdirectory of the same repository, and it resolves the engine by path:

git clone https://github.com/sadit/SimilaritySearchEngine.jl
cd SimilaritySearchEngine.jl
julia --project=server -e 'using Pkg; Pkg.develop(path="."); Pkg.instantiate()'
julia --project=server -t auto -m SimilaritySearchServer serve

Both packages require Julia 1.12 or later. No Manifest.toml is committed for the engine, so Pkg.instantiate() resolves the base libraries from the registry unless they are also developed by path.

Engine functionality

  • Project lifecycle: create_project, open_project and close_project! manage the on-disk RocksDB directory and the associated search engine.
  • Separation of engine and backend:
    • Payload engines: DenseEngine, SparseEngine and FullTextEngine determine the type of data stored.
    • Index backends: SearchGraph, ExhaustiveSearch, InvertedFile and BM25InvertedFile determine the indexing data structure.
    • payload_kind(engine) reports the data type, and the BACKENDS registry restricts which engine-backend pairs are valid.
  • Dense vector search: approximate nearest neighbor search with SearchGraph, which tunes its beam search parameters, or exact search with ExhaustiveSearch and ParallelExhaustiveSearch. For SearchGraph, insertion (append_items!) and graph construction (index!) are separate operations, so the caller determines when indexing latency is incurred.
  • Sparse vector search: inverted index search (InvertedFile) over sparse representations encoded by the caller, of fixed dimension. The available distance functions are cosine distance over the weights and set distances (Dist.Sets.*) over the support of the non-zero coordinates.
  • Full-text retrieval: lexical search with BM25InvertedFile or with TF-IDF weighting (TextInvertedFile). The first call to index! fits or initializes a TextProfile from the staged texts, which determines the vocabulary and the term weighting model.
  • Explicit text modeling: a text project requires an AbstractTextModelSpec:
    • DefaultProfile(:lang) resolves a pre-trained language profile and refits the vocabulary frequencies against the staged corpus.
    • BaseProfile(p) uses an existing TextProfile.
    • FitFromCorpus(cfg) fits a profile from the staged corpus, up to max_documents.
    • A query accepts a QueryPolicy, which determines orthographic correction and query expansion.
  • Typed interface: input is given in typed containers (DenseItem, SparseItem, TextItem), and queries return structured results (SearchResult, StoredItem, ExistsResult).
  • Logical deletion: delete_item! marks a document as deleted without modifying the index. Queries return such candidates with an explicit deleted field.
  • Recall calibration: calibrate! optimizes the beam search parameters for a set of target recall values, which minrecall then selects. SearchStats reports the number of distance computations a query performed.
  • Operations over an entire collection: in-process execution of all-pairs nearest neighbors (allknn), center selection (fft), closest pairs (closestpairs), and closest pairs between two collections (bichromatic_kclosestpairs).
  • Persistence: RocksDB column families for metadata and index structures, and memory-mapped files for dense vectors (dense_vectors.mmapdb).
  • Typed errors: a failure raised by the engine is an EngineError in one of four categories (InvalidRequest, NotFound, ConflictingState, StorageFailure), so that a caller can act on a failure without interpreting its message.

Server functionality

  • REST API: dataset lifecycle, insertion, dense, sparse and text search with metadata filters, logical deletion, recall calibration, and queries over more than one dataset (hybrid, ftsearch_group).
  • Asynchronous jobs: allknn, fft, neardup, hsp, searchbatch, closestpair, build, dump and load are enqueued and executed as separate Julia subprocesses. Each one opens its dataset in read-only mode, so the server continues to answer queries while they run.
  • Two command lines: similarity-search operates on a working directory, and similarity-search-ctl operates on a running server over HTTP. Both can be installed as applications with Pkg.Apps.
  • Operational interfaces: access tokens, an operation log per dataset (whose distance-computation counts are obtained from the engine’s SearchStats), cursors for paginated results, health and metrics endpoints, and unload and reload of a single dataset without restarting the server.
  • One error vocabulary: the engine’s four categories are mapped to HTTP status codes and to command-line exit codes by category, not by message text.
