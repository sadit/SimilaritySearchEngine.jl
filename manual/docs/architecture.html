Architecture

This document describes the architectural design and internal subsystems of SimilaritySearchEngine.jl. It covers the module organization, the engine type hierarchy, the decoupled staging-versus-indexing lifecycle, the multithreaded concurrency model, and the hybrid persistence layout combining RocksDB column families with memory-mapped array storage.

Subsystem Architecture and Module Map

The package is structured into four core submodules and an embedded orchestration layer:

  • Schema: Defines the metadata record contract (Schema.MetadataRecord) and serialization interfaces.
  • Project: Implements project metadata storage (ProjectManager), document ID indexing, and secondary key lookups.
  • IndexEngine: Implements the AbstractSearchEngine hierarchy, encapsulating indexing algorithms from SimilaritySearch.jl and TextSearch.jl.
  • Persistence: Provides storage adapters for RocksDB column families and memory-mapped files.
  • embedded.jl: Implements EmbeddedEngine and exports the high-level transactional API (create_project, append_items!, search, etc.).

Decoupling of Subsystems

IndexEngine and Persistence operate independently of Project and Schema: - IndexEngine is agnostic to RocksDB, interacting with persistence exclusively through structural callback hooks (index, sp, ep) -> nothing. - Persistence stores serialized Julia objects under key-value interfaces without semantic knowledge of index internals. - embedded.jl orchestrates these components into a unified transactional engine.

Uniform Metadata Contract

Projects use a standardized metadata record structure, Schema.MetadataRecord: - _id: Internal, sequential, zero-based or 1-based integer identifier aligned with vector storage indices. - doc_id: Caller-provided external string identifier. - keywords: Indexed string tags mapped via the secondary index idx_keywords. - refs: Indexed document reference links mapped via idx_refs. - meta: Arbitrary unstructured metadata stored as a serialized JSON object.

Engine Type Hierarchy

SimilaritySearchEngine.jl parameterizes search collections through two distinct abstractions: 1. Engine (AbstractSearchEngine): Defines the data domain of the stored payloads (DenseEngine, SparseEngine, FullTextEngine). 2. Backend (AbstractSearchIndex): Defines the underlying search data structure (SearchGraph, ExhaustiveSearch, ParallelExhaustiveSearch, InvertedFile, BM25InvertedFile).

create_project(w, ds)                                               # Dense vectors, SearchGraph (defaults)
create_project(w, ds; engine=DenseEngine, backend=ExhaustiveSearch) # Dense vectors, exact linear scan
create_project(w, ds; engine=SparseEngine, dimension=50_000)        # Sparse vectors, InvertedFile
create_project(w, ds; engine=FullTextEngine, backend=BM25InvertedFile,
                      textmodel=DefaultProfile(:es))                # Full text, BM25 scoring

Architectural Properties of the Hierarchy

  • First-Class Sparse Engine (SparseEngine): Provides direct inverted-index search over externally encoded sparse vectors. Callers supply pre-computed SparseVector objects without requiring linguistic tokenizers or text profiles.
  • Payload Domain Introspection (payload_kind): Returns :dense, :sparse, or :text, allowing client layers to inspect payload requirements.
  • Backend Compatibility Registry (BACKENDS): Enforces valid combinations of payload engines and search backends:
    • DenseEngine accepts SearchGraph, ExhaustiveSearch, and ParallelExhaustiveSearch.
    • SparseEngine accepts InvertedFile.
    • FullTextEngine accepts BM25InvertedFile and TextInvertedFile.
  • Domain Separation of BM25: BM25InvertedFile is restricted to FullTextEngine because BM25 scoring relies on corpus-level document frequencies and average document lengths rather than purely geometric vector properties.
  • Structural Dimension Constraints: SparseBackend requires an explicit dimension parameter at initialization because an InvertedFile allocates a fixed array of posting lists.
  • Encapsulated Linguistic Modeling: FullTextEngine encapsulates its entire linguistic configuration within a TextProfile (profile), including vocabulary frequencies, term weighting schemes, stopword lists, lemma clusters, and query-expansion graphs.

Decoupled Lifecycle: Staging vs. Indexing

SimilaritySearchEngine.jl decouples the ingestion of raw items from the computationally intensive construction of search index structures:

[ Ingestion ] ──────> append_items! ──────> [ Staged Backlog ] ──────> index! ──────> [ Searchable Index ]
                     (Durable in Store)                                              (Searchable in Engine)

Operational Dynamics

  1. SearchGraph (Dense Engine):
    • append_items! appends raw Vector{Float32} arrays directly to the memory-mapped vector file dense_vectors.mmapdb. This operation is durable and fast (\(O(1)\) per vector), but does not construct graph edges.
    • index! evaluates the backlog range length(index)+1:length(database(index)) and builds proximity graph connections via SimilaritySearch.index!.
  2. FullTextEngine (Text Engine):
    • append_items! appends raw text strings to StagedTextStore within RocksDB.
    • index! processes the staged text backlog:
      • On the first invocation of an uninitialized project, index! executes the linguistic model specification (fitspec) to build the initial TextProfile and instantiate the inverted index.
      • On subsequent invocations, index! encodes staged strings and inserts posting list entries.
  3. ExhaustiveSearch and InvertedFile (Sparse Engine):
    • Because exact linear scans evaluate directly over the database and sparse inverted files update posting lists upon insertion, append_items! makes items searchable immediately. index! operates as an idempotent no-op.

Concurrency Model

Index data structures in SimilaritySearch.jl and TextSearch.jl support concurrent read operations, but mutate unsafely if writes occur concurrently with reads or other writes.

SimilaritySearchEngine.jl coordinates multithreaded access via two synchronization mechanisms: ReadWriteLock and ContextPool.

Reader-Writer Synchronization: ReadWriteLock

Each engine maintains a ReadWriteLock to coordinate thread access: - Read Lock (Shared): Acquired by query operations (search, ftsearch, allknn, closestpairs). Allows multiple worker threads to execute searches in parallel. - Write Lock (Exclusive): Acquired by mutating operations (append_items!, index!, delete_item!, calibrate!). Blocks all active readers and concurrent writers.

Context Isolation: ContextPool

Search contexts (SearchGraphContext, GenericContext, InvertedFileContext) contain internal scratch buffers (beam priority queues, visited-vertex bitvectors, and accumulator caches). If concurrent search threads share a single context instance, memory corruption occurs.

ContextPool manages a dynamic pool of isolated context instances:

The pool expands dynamically to match the peak concurrent query volume and retains allocated buffers to eliminate runtime allocation overhead.

Cost Accounting Across the Pool Boundary

Pooling has a consequence for measurement. SimilaritySearch.jl accounts for the work an operation performs in the counters carried by the context itself (ctx.costdists), which accumulate and are never reset; the cost of a single operation is therefore a difference between two readings taken around it. That technique is sound for insertion, which runs on the engine’s own ctx under an exclusive write lock, and unsound for search: the context a query ran on was borrowed from the pool for the duration of the call and returned at the end, so a reading taken afterwards from outside describes whatever else has since been searching concurrently, not the query in question.

The count is consequently produced where it is unambiguous – inside IndexEngine.search_live, between checkout and checkin – and surfaced to the caller through a supplied SearchStats instance:

stats = SearchStats()
results = search(h, query, 10; stats)
stats.distance_evaluations

search, ftsearch and the filtered search path all accept it, the filtered path reporting the cost of the candidate search it actually ran rather than of the k results it returned. The field is overwritten by each call rather than accumulated. This is the mechanism behind the distance_evaluations field of the server’s op_log, which has no other way to attribute work to the request that caused it.

Persistence Architecture

SimilaritySearchEngine.jl employs a fine-grained, column-family-based storage architecture where mutations modify only the affected persistence segments.

The Persisted Text Index

A text project stores its index: posting lists in invfile_postings, per-document vectors in invfile_docvecs. This covers both text backends – their posting lists hold the same thing, document ids, and they differ only in what each document is stored as. Three shapes occur, and each stored value carries a one-byte tag saying which: integer term frequencies (BM25), Float32 model weights (the weighted backend), and bags of words (the weighted backend under a set distance, which reads membership rather than weights). A sparse project still stores the objects it indexed, in sparse_db, and reconstructs its index on every open; its items are vectors the caller encoded, so what it saves is already what it would have to write, and giving it the same treatment is a follow-up rather than a difference of principle.

The difference is not small at scale: over 265,000 Project Gutenberg paragraphs, reconstruction costs 20.4 s and assembly from storage 1.4 s on BM25 and 1.7 s on the weighted backend (measured 2026-09-11 and 2026-09-12). Indexing the same corpus costs 25.7 s and 26.4 s respectively, against 147.3 s before, because a block is now encoded by the library’s parallel batch path rather than one document at a time.

Writing is incremental and blockwise. Each index! call encodes its backlog as one block, splices the block’s document vectors and lengths into the live index, and hands its posting lists – ids shifted from block-local to global – to IndexEngine.persist_block!. The storage-backed implementation of that function performs a read-modify-write per token the block touched: appending is sound precisely because document ids grow monotonically, so a block’s ids are larger than every id already stored and the ascending order the query-time merge depends on is preserved. IndexEngine never names RocksDB; it dispatches on the kind of adjacency list its index was built with.

The unit of that write is the block, and its size has a cost: a token’s list is rewritten once per block that touches it, so the same 50,000 documents cost 5.8 s indexed in one block, 6.8 s in ten, and 10.1 s in fifty (measured 2026-09-12). Indexing in large blocks is therefore worth preferring, which is what append_items! followed by a single index! already does.

Posting lists are lazy; document vectors are not, and the asymmetry is measured rather than assumed. A query reads one posting list per query term, so serving them from storage costs 1.8% in latency (66.8 ms against 68.0 ms) while removing 55.8 MB of 237.5 MB from memory. Scoring, by contrast, reads a candidate’s term vector (bm25score(..., idx.db[docID])), and the merge makes every document containing any query token a candidate – so a query with a frequent term turns lazy document vectors into one point read per document in the collection: 1,771.9 ms against 66.8 ms for the same query. Document vectors are therefore read into memory at open (0.76 s for that corpus).

The lazy posting lists sit behind a least-frequently-used cache bounded by a maximum number of cached lists, trimmed back to a base size when it is exceeded. Eviction happens only after a query has fully resolved, never inside one: concurrent searches hold read locks, not exclusive ones, and a list dropped mid-query would be re-read by whichever of them was still walking it.

There is no migration path from the previous format, deliberately. A project written before the index was persisted opens with its profile and its staged text intact and no index at all; searching it says so, and one index! call rebuilds it from that staged text, which was always persisted independently of the index. Keeping the old format readable would mean keeping the whole rebuild-by-reinsertion path alive to serve projects that, with no released version, do not yet exist – so the procedure is explicit and costs a line:

h = open_project(workdir, dataset)
index!(h)

External Identifier Resolution

doc_id is the caller’s own identifier, and it is resolved through the idx_docid column family rather than by scanning records. Keys are composite (doc_id bytes followed by the four bytes of _id), which is what allows several items to share one doc_id: fetch_items returns every record carrying the requested identifier, in ascending _id order, and exists reports it as deleted only when all of them are. Measured on a 50,000-item project, resolving an external identifier costs 0.12 ms through this index against 59 ms for the full scan it replaces.

A project written before this index existed is migrated on its first writable open: Project.backfill_docid_index! performs a single pass over records and writes a marker key so no later open repeats it. A read-only handle opened against an unmigrated project falls back to the scan.

Compaction

Bulk writes leave a write-ahead log that the next open must replay, so compaction is an open-latency concern rather than a write-latency one. close_project! therefore compacts every column family of the project before closing, unless the handle is read-only, the session performed no writes, or the caller passes compact=false; compact_project! exposes the same operation mid-session. Measured on a 50,000-vector dense project, reopening costs 2.97 s without compaction and 0.28 s with it, for a compaction that itself takes 0.03 s.

Storage Subsystems

  1. EngineStore (Engine Field State):
    • Stores engine-level configuration as individual key-value entries (:minrecall, :opt_beamsearch, :deleted_ids, :profile).
    • Mutations (e.g., updating deleted IDs or storing calibration results) rewrite only their specific keys.
  2. Dense Vector Storage (dense_vectors.mmapdb):
    • Dense vectors are stored in a dedicated memory-mapped binary file managed by MMapMatrixDatabase.
    • Bypasses key-value serialization overhead, providing high-speed sequential appends and zero-copy random access.
  3. AdjacencyStore (Graph Topology):
    • Graph adjacencies are persisted incrementally through CallbackLog observer hooks during index!.
    • Stores only forward (direct) edges; reverse edges are reconstructed dynamically in memory during project reopening to ensure idempotency.
  4. StagedTextStore and InvertedFileObjectStore:
    • StagedTextStore holds un-encoded raw text lines.
    • InvertedFileObjectStore stores contiguous blocks of encoded posting-list objects.

Project Reopening Lifecycle

When a project is reopened, stored forward edges are reloaded and bidirectional reverse links are regenerated, restoring the search index to its exact state prior to closure.

Failure Reporting: Typed Errors and Their Boundaries

Every failure the engine raises deliberately is an EngineError, and the type is the contract. Four abstract categories sit beneath it, and a concrete type beneath each:

category meaning concrete types
InvalidRequest the call cannot be honoured as written; retrying it unchanged fails again PayloadMismatch, WrongDimension, UnknownBackend, InvalidOption, UnsupportedOperation
NotFound something the call named does not exist ProfileNotInstalled
ConflictingState the request is well formed but the project is not in a state that can serve it; the same call succeeds later PendingBacklog, NothingStaged, NoIndex, NotTrained, EmptyProject
StorageFailure what was read back cannot be interpreted CorruptedStorage

Concrete types carry structured detail where a caller can use it: PendingBacklog reports the staged and connected counts, WrongDimension the expected and received lengths, InvalidOption the keyword at fault.

Mapping lives at each boundary, never in the engine. The engine does not know what an HTTP status code or an exit code is. Its consumers translate:

try
    search(handle, query, 10)
catch e
    e isa ConflictingState && return retry_after_indexing()
    e isa NotFound && return not_found()
    rethrow()
end

SimilaritySearchServer maps categories to status codes (NotFound to 404, ConflictingState to 409, InvalidRequest to 400, anything else to 500) and its CLIs map the same categories to exit codes (4, 5, 2, 70), so a shell script can branch on the reason without reading output.

The alternative — bare error("...") — forces every consumer to classify by message text, which breaks silently the first time the wording improves. That had already happened here: this engine’s own concurrency test recognized a refused whole-dataset operation with occursin("requires no pending backlog", e.msg), and now matches PendingBacklog instead.

Dual Logging Architecture: Reporters vs. Observers

Contexts maintain two isolated logging channels: - Reporters (ctx.reporters): Receive progress messages via INFORM and output formatted status lines to stderr or custom IO streams. Throttled to prevent console flooding. - Observers (ctx.observers): Receive structural mutation events (:add!) via OBSERVE. Execute un-throttled callbacks that trigger persistence updates (CallbackLog).

Soft Deletions and Dataset Operations

  • Soft Deletions: The delete_item! function registers document identifiers in deleted_ids. The underlying index structure is preserved without requiring costly reorganization. Search queries evaluate candidates and attach an explicit deleted::Bool flag in SearchResult.
  • Whole-Dataset Metric Operations: Functions allknn, fft, closestpairs, and bichromatic_kclosestpairs execute directly on the in-memory graph index, utilizing multithreaded batch routines to perform comprehensive metric analyses across the entire collection.
