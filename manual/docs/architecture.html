Architecture

This document describes the internal design of SimilaritySearchEngine.jl: the organization of its modules, the engine type hierarchy, the separation between staging and indexing, the concurrency model, and the storage layout, which combines RocksDB column families with memory-mapped files.

Subsystem Architecture and Module Map

The package is structured into four core submodules and an embedded orchestration layer:

  • Schema: Defines the metadata record contract (Schema.MetadataRecord) and serialization interfaces.
  • Project: Implements project metadata storage (ProjectManager), document ID indexing, and secondary key lookups.
  • IndexEngine: Implements the AbstractSearchEngine hierarchy, encapsulating indexing algorithms from SimilaritySearch.jl and TextSearch.jl.
  • Persistence: Provides storage adapters for RocksDB column families and memory-mapped files.
  • embedded.jl: Implements EmbeddedEngine and exports the public API (create_project, append_items!, search, and others).

Decoupling of Subsystems

IndexEngine and Persistence operate independently of Project and Schema: - IndexEngine does not depend on RocksDB. It communicates with persistence only through callbacks of the form (index, sp, ep) -> nothing. - Persistence stores serialized Julia objects through key-value interfaces, and does not interpret the contents of an index. - embedded.jl combines these components into one engine.

Uniform Metadata Contract

Projects use a standardized metadata record structure, Schema.MetadataRecord: - _id: Internal, sequential, zero-based or 1-based integer identifier aligned with vector storage indices. - doc_id: Caller-provided external string identifier. - keywords: Indexed string tags mapped via the secondary index idx_keywords. - refs: Indexed document reference links mapped via idx_refs. - meta: Arbitrary unstructured metadata stored as a serialized JSON object.

Engine Type Hierarchy

SimilaritySearchEngine.jl parameterizes search collections through two distinct abstractions: 1. Engine (AbstractSearchEngine): Defines the data domain of the stored payloads (DenseEngine, SparseEngine, FullTextEngine). 2. Backend (AbstractSearchIndex): Defines the underlying search data structure (SearchGraph, ExhaustiveSearch, ParallelExhaustiveSearch, InvertedFile, BM25InvertedFile).

create_project(w, ds)                                               # Dense vectors, SearchGraph (defaults)
create_project(w, ds; engine=DenseEngine, backend=ExhaustiveSearch) # Dense vectors, exact linear scan
create_project(w, ds; engine=SparseEngine, dimension=50_000)        # Sparse vectors, InvertedFile
create_project(w, ds; engine=FullTextEngine, backend=BM25InvertedFile,
                      textmodel=DefaultProfile(:es))                # Full text, BM25 scoring

Properties of the Hierarchy

  • Sparse engine (SparseEngine): Performs inverted-index search over sparse vectors encoded outside the package. The caller supplies SparseVector objects, and no tokenizer or text profile is involved.
  • Introspection of the payload type (payload_kind): Returns :dense, :sparse or :text, so that a calling layer can determine what a project accepts.
  • Backend Compatibility Registry (BACKENDS): Enforces valid combinations of payload engines and search backends:
    • DenseEngine accepts SearchGraph, ExhaustiveSearch, and ParallelExhaustiveSearch.
    • SparseEngine accepts InvertedFile.
    • FullTextEngine accepts BM25InvertedFile and TextInvertedFile.
  • Domain Separation of BM25: BM25InvertedFile is restricted to FullTextEngine because BM25 scoring relies on corpus-level document frequencies and average document lengths rather than purely geometric vector properties.
  • Structural Dimension Constraints: SparseBackend requires an explicit dimension parameter at initialization because an InvertedFile allocates a fixed array of posting lists.
  • Text model: FullTextEngine keeps its linguistic configuration in a TextProfile (profile): vocabulary frequencies, term weighting, stopword lists, lemma clusters, and query-expansion graphs.

Decoupled Lifecycle: Staging vs. Indexing

The package separates the insertion of items from the construction of the index, which is the expensive operation:

[ Ingestion ] ──────> append_items! ──────> [ Staged Backlog ] ──────> index! ──────> [ Searchable Index ]
                     (Durable in Store)                                              (Searchable in Engine)

Behavior of Each Engine Type

  1. SearchGraph (Dense Engine):
    • append_items! writes the Vector{Float32} arrays to the memory-mapped file dense_vectors.mmapdb. The operation is durable and costs \(O(1)\) per vector. It does not construct graph edges.
    • index! evaluates the backlog range length(index)+1:length(database(index)) and builds proximity graph connections via SimilaritySearch.index!.
  2. FullTextEngine (Text Engine):
    • append_items! appends raw text strings to StagedTextStore within RocksDB.
    • index! processes the staged text backlog:
      • On the first invocation of an uninitialized project, index! executes the linguistic model specification (fitspec) to build the initial TextProfile and instantiate the inverted index.
      • On subsequent invocations, index! encodes staged strings and inserts posting list entries.
  3. ExhaustiveSearch and InvertedFile (Sparse Engine):
    • An exact linear scan evaluates the database directly, and a sparse inverted file updates its posting lists on insertion. append_items! therefore makes an item searchable immediately, and index! performs no work.

Concurrency Model

The index structures of SimilaritySearch.jl and TextSearch.jl support concurrent reads. A write that runs at the same time as a read, or as another write, corrupts them.

The package coordinates access from several threads with two mechanisms: ReadWriteLock and ContextPool.

Reader-Writer Synchronization: ReadWriteLock

Each engine maintains a ReadWriteLock to coordinate thread access: - Read Lock (Shared): Acquired by query operations (search, ftsearch, allknn, closestpairs). Allows multiple worker threads to execute searches in parallel. - Write Lock (Exclusive): Acquired by mutating operations (append_items!, index!, delete_item!, calibrate!). Blocks all active readers and concurrent writers.

Context Isolation: ContextPool

A search context (SearchGraphContext, GenericContext, InvertedFileContext) contains working buffers: beam priority queues, bit vectors of visited vertices, and accumulator caches. If two threads search with the same context, these buffers are corrupted.

ContextPool manages a dynamic pool of isolated context instances:

The pool grows to the number of queries that have run concurrently, and it keeps the allocated buffers, so that later queries do not allocate them again.

Measuring the Cost of a Query

The use of a pool has a consequence for measurement. SimilaritySearch.jl counts the work performed by an operation in the context itself (ctx.costdists). These counters accumulate and are never reset, so the cost of one operation is the difference between two readings taken before and after it.

This method is correct for insertion, which uses the engine’s own ctx under an exclusive write lock. It is not correct for search. A query uses a context taken from the pool for the duration of the call, and the context returns to the pool when the call ends. A reading taken afterwards includes the work of any other query that has used the same context since.

The count is therefore computed inside IndexEngine.search_live, between checkout and checkin, and is reported to the caller in a SearchStats instance that the caller provides:

stats = SearchStats()
results = search(h, query, 10; stats)
stats.distance_evaluations

search, ftsearch and the filtered form of search accept this argument. For a filtered search, the value is the cost of the candidate search that was executed, not of the k results that satisfied the predicate. Each call overwrites the field; values are not accumulated. The server obtains the distance_evaluations field of its op_log from this mechanism.

Persistence Architecture

A project is stored in RocksDB column families and in one memory-mapped file. A write modifies only the segments it affects.

The Persisted Text Index

A text project stores the index itself: posting lists in invfile_postings, and one vector per document in invfile_docvecs. Both text backends are stored this way. Their posting lists contain the same data, document identifiers, and they differ only in the representation of each document. Three representations are used, and each stored value begins with a one-byte tag that identifies its own: integer term frequencies (BM25), Float32 model weights (the weighted backend), and bags of words (the weighted backend under a set distance, which reads membership instead of weights). A sparse project stores the objects it indexed, in sparse_db, and reconstructs its index at every open. Its items are vectors encoded by the caller, so the stored objects are already the representation that would be written; applying the same treatment to a sparse project remains pending work.

The two procedures differ in cost. Over 265,000 Project Gutenberg paragraphs, reconstruction takes 20.4 s, and assembly from storage takes 1.4 s with BM25 and 1.7 s with the weighted backend (measured 2026-09-11 and 2026-09-12). Indexing the same corpus takes 25.7 s and 26.4 s respectively, compared with 147.3 s before, because a block is now encoded by the parallel batch procedure of the library instead of one document at a time.

Writing is incremental and proceeds by blocks. Each call to index! encodes its backlog as one block, inserts the document vectors and lengths of that block into the index in memory, and passes its posting lists to IndexEngine.persist_block!, with identifiers converted from block-local to global. The implementation of that function reads, modifies and writes one stored list per token that the block contains. Appending is correct because document identifiers increase monotonically: the identifiers of a block are larger than every identifier already stored, so the ascending order required by the merge at query time is preserved. IndexEngine contains no reference to RocksDB, and dispatches on the type of adjacency list of its index.

The unit of writing is the block, and the number of blocks has a cost. The list of a token is rewritten once per block that contains it, so the same 50,000 documents take 5.8 s in one block, 6.8 s in ten, and 10.1 s in fifty (measured 2026-09-12). Large blocks are therefore preferable, which is the result of calling append_items! and then a single index!.

Posting lists are read on demand; document vectors are not. The reason is measured. A query reads one posting list per query term, so reading them from storage increases latency by 1.8% (66.8 ms against 68.0 ms) and removes 55.8 MB of 237.5 MB from memory. Scoring reads the term vector of each candidate (bm25score(..., idx.db[docID])), and the merge makes every document that contains any query token a candidate. With a frequent term, reading document vectors on demand becomes one point read per document in the collection: 1,771.9 ms against 66.8 ms for the same query. Document vectors are therefore read into memory when the project is opened (0.76 s for that corpus).

Posting lists read on demand are kept in a least-frequently-used cache. The cache holds a maximum number of lists and is reduced to a base size when that maximum is exceeded. Lists are removed only after a query has finished, never during one: concurrent searches hold read locks rather than exclusive locks, and a list removed during a query would be read again by any search still using it.

There is no migration from the previous format. A project written before the index was persisted opens with its profile and its staged text, and with no index. A search against it reports this condition, and one call to index! builds the index from the staged text, which was always persisted independently of the index. Supporting the previous format would require keeping the reconstruction procedure for projects that do not yet exist, since no version has been released. The migration is therefore explicit:

h = open_project(workdir, dataset)
index!(h)

External Identifier Resolution

doc_id is the identifier supplied by the caller. It is resolved through the idx_docid column family, not by scanning records. Keys are composite: the bytes of doc_id followed by the four bytes of _id. This allows several items to share one doc_id. fetch_items returns every record that carries the requested identifier, in ascending _id order, and exists reports the identifier as deleted only when all of those records are deleted. On a project of 50,000 items, resolving an external identifier takes 0.12 ms through this index, compared with 59 ms for the scan it replaces.

A project written before this index existed is migrated the first time it is opened for writing. Project.backfill_docid_index! performs one pass over records and writes a marker key, so that later opens do not repeat the pass. A read-only handle opened on a project that has not been migrated uses the scan instead.

Compaction

Bulk writes leave a write-ahead log, and the next open must replay it. Compaction therefore affects the latency of opening a project, not the latency of writing to it. close_project! compacts every column family of the project before closing, unless the handle is read-only, the session performed no writes, or the caller passes compact=false. compact_project! performs the same operation while the project remains open. On a dense project of 50,000 vectors, reopening takes 2.97 s without compaction and 0.28 s with it, and the compaction itself takes 0.03 s.

Storage Subsystems

  1. EngineStore (Engine Field State):
    • Stores engine-level configuration as individual key-value entries (:minrecall, :opt_beamsearch, :deleted_ids, :profile).
    • Mutations (e.g., updating deleted IDs or storing calibration results) rewrite only their specific keys.
  2. Dense Vector Storage (dense_vectors.mmapdb):
    • Dense vectors are stored in a dedicated memory-mapped binary file managed by MMapMatrixDatabase.
    • Avoids key-value serialization. Appends are sequential, and random access reads the vector without copying it.
  3. AdjacencyStore (Graph Topology):
    • Graph adjacencies are persisted incrementally through CallbackLog observer hooks during index!.
    • Stores only forward (direct) edges; reverse edges are reconstructed dynamically in memory during project reopening to ensure idempotency.
  4. StagedTextStore and InvertedFileObjectStore:
    • StagedTextStore holds un-encoded raw text lines.
    • InvertedFileObjectStore stores contiguous blocks of encoded posting-list objects.

Project Reopening Lifecycle

When a project is reopened, the stored forward edges are read again and the reverse links are regenerated, which restores the index to the state it had before the project was closed.

Failure Reporting: Typed Errors and Their Boundaries

Every failure that the engine raises is an EngineError. The type of the error, not its message, is the interface. There are four abstract categories, and one or more concrete types under each of them:

category meaning concrete types
InvalidRequest the call cannot be honoured as written; retrying it unchanged fails again PayloadMismatch, WrongDimension, UnknownBackend, InvalidOption, UnsupportedOperation
NotFound something the call named does not exist ProfileNotInstalled
ConflictingState the request is well formed but the project is not in a state that can serve it; the same call succeeds later PendingBacklog, NothingStaged, NoIndex, NotTrained, EmptyProject
StorageFailure what was read back cannot be interpreted CorruptedStorage

The concrete types carry the values a caller can use. PendingBacklog reports the number of staged items and the number of indexed items, WrongDimension reports the expected and the received length, and InvalidOption reports the keyword that was rejected.

The mapping is defined at each interface, not in the engine. The engine contains no reference to HTTP status codes or to process exit codes. Each consumer performs the translation:

try
    search(handle, query, 10)
catch e
    e isa ConflictingState && return retry_after_indexing()
    e isa NotFound && return not_found()
    rethrow()
end

SimilaritySearchServer maps the categories to status codes: NotFound to 404, ConflictingState to 409, InvalidRequest to 400, and any other failure to 500. Its command lines map the same categories to exit codes 4, 5, 2 and 70, so that a shell script can select a branch without reading the output text. This mapping is the only coupling between the two packages of this repository, and the server manual states it in one table.

The alternative, error("...") with a message, requires every consumer to classify the failure by its text. Such a classification fails when the wording changes, and it fails without any error being reported. This had occurred in this repository: the concurrency test identified a rejected operation with occursin("requires no pending backlog", e.msg). It now matches the type PendingBacklog.

Logging Channels: Reporters and Observers

A context maintains two separate logging channels: - Reporters (ctx.reporters): Receive progress messages via INFORM and output formatted status lines to stderr or custom IO streams. Throttled to prevent console flooding. - Observers (ctx.observers): Receive structural mutation events (:add!) via OBSERVE. Execute un-throttled callbacks that trigger persistence updates (CallbackLog).

Soft Deletions and Dataset Operations

  • Soft deletions: delete_item! records document identifiers in deleted_ids. The index is not reorganized. A query evaluates such candidates and reports them with the field deleted::Bool of SearchResult.
  • Operations over an entire collection: allknn, fft, closestpairs and bichromatic_kclosestpairs operate on the index in memory, using multithreaded batch routines over the whole collection.
