Architecture

This document describes the internal design of SimilaritySearchEngine.jl: the organization of its modules, the engine type hierarchy, the separation between staging and indexing, the concurrency model, and the storage layout, which combines RocksDB column families with memory-mapped files.

Subsystem Architecture and Module Map

The package is structured into four core submodules and an embedded orchestration layer:

  • Schema: Defines the metadata record contract (Schema.MetadataRecord) and serialization interfaces.
  • Project: Implements project metadata storage (ProjectManager), document ID indexing, and secondary key lookups.
  • IndexEngine: Implements the AbstractSearchEngine hierarchy, encapsulating indexing algorithms from SimilaritySearch.jl and TextSearch.jl. It also defines the project specifications (specs.jl): DenseVectors, SparseVectors, TextDocuments and the types they are built from.
  • Persistence: Provides storage adapters for RocksDB column families and memory-mapped files.
  • embedded.jl: Implements EmbeddedEngine and exports the public API (create_project, append_items!, search, and others).

Decoupling of Subsystems

IndexEngine and Persistence operate independently of Project and Schema: - IndexEngine does not depend on RocksDB. It communicates with persistence only through callbacks of the form (index, sp, ep) -> nothing. - Persistence stores serialized Julia objects through key-value interfaces, and does not interpret the contents of an index. - embedded.jl combines these components into one engine.

Uniform Metadata Contract

Projects use a standardized metadata record structure, Schema.MetadataRecord: - _id: Internal, sequential, zero-based or 1-based integer identifier aligned with vector storage indices. - schema_version: Which declaration of meta was in force when the record was written (see below). - doc_id: Caller-provided external string identifier. - keywords: String tags. They are metadata of the item: the engine stores them, returns them, and passes them to filter functions. It does not index them. Until 2026-11-22 they were also written to the column family idx_keywords, which no function read (issue #5). - refs: Indexed document reference links mapped via idx_refs. - meta: Metadata stored as a serialized JSON object, in its own column family.

The record has the same shape in every project. What varies is meta, and a project may declare part of it.

The Declared Shape of meta

A project may declare which fields of meta it expects and what type each one holds. The declaration is a Schema.MetaSchema: a list of (name, type), with the type one of :string, :int64, :float64, :bool or :timestamp.

h = create_project(workdir, "papers"; meta_schema = ["year" => :int64, "published" => :timestamp])
meta_schema(h)                                    # what this project declares
declare_meta_schema!(h, ["year" => :int64])       # declare on a project that exists

append_items! checks each declared field and converts it when the conversion keeps the value: JSON has one number type, so 2024.0 is stored as the integer 2024, and a timestamp is stored as the string its instant prints as. A value of another type raises PayloadMismatch, which is an InvalidRequest.

Three properties define what declaring means here:

  • It is additive. A field nobody declared is stored as it arrives, and a record need not carry every declared field. Declaring says what a field must hold when it is present, not what an item may contain.
  • It does not reach backwards. Declaring on a project that already holds records reads none of them. The declaration governs what is written from then on; rebuild is what rewrites the rest. This is what makes declaring cheap on a project of any size.
  • It is not an index. The declared fields are stored in meta as before, and a filter over them is still evaluated per candidate. What the declaration changes is the comparison: a field declared :timestamp is compared as an instant rather than as the text that stores it, so two spellings of one instant match.

The declaration lives in the project, not in the record: giving MetadataRecord a typed column per declared field would make its Julia type vary from one project to the next, which propagates to every function that handles a record, to the Avro table dump writes, and to a process that holds several projects at once. schema_version on the record is what ties a record to the declaration it was written under.

Project Specifications

A project is described by one value, a ProjectSpec (issue #2). It says what the project holds, the index that holds it and, for dense vectors, how they are stored. Each type holds only its own options:

Level Types
What the project holds DenseVectors(distance; index, storage), SparseVectors(dimension, distance), TextDocuments(model; index)
Dense index Graph(; minrecall) (a SearchGraph), Exhaustive(; parallel) (ExhaustiveSearch or ParallelExhaustiveSearch)
Text index BM25() (BM25InvertedFile), VectorSpace(; distance) (TextInvertedFile)
Dense storage Float32Vectors(), Quantized(SQ(bits; range); rotation, keep_vectors), Sketched(hyperplanes; bits, rerank, keep_vectors, center, ...) 
create_project(w, ds)                                                    # DenseVectors(): SqL2, Graph(minrecall=0.9), Float32
create_project(w, ds, DenseVectors(Dist.NormCosine(); index=Exhaustive())) # exact linear scan
create_project(w, ds, SparseVectors(50_000))                             # sparse vectors, InvertedFile
create_project(w, ds, TextDocuments(DefaultProfile(:es)))                # full text, BM25 scoring
create_project(w, ds, DenseVectors(Dist.NormCosine();
                                   storage=Quantized(SQ(8); rotation=QRRotation())))

The options that apply to every kind of project are keywords of create_project: meta_schema, partitions=PartitionBy(field; graph_min) and runtime=Runtime(...). Runtime holds the options that are not saved with the project (maxbatches, the size of the cache of posting lists, edit_correction), and open_project takes it as well.

The engine dispatches on the type of the spec. IndexEngine.create_engine(spec; ...) has one method for each of DenseVectors, SparseVectors and TextDocuments, and open_project chooses how to restore the engine from the type of the saved spec.

Saved form. create_project saves the spec in the engine field :spec, as a dictionary with the structure of the JSON form of the HTTP API: {"dense": {"distance": ..., "index": {"graph": {"minrecall": 0.9}}, "storage": {"float32": {}}}}. A dictionary does not depend on the names of the Julia types of the spec. The distance is stored as the SimilaritySearch value. The text model of a DefaultProfile is stored with its options. A BaseProfile and a FitFromCorpus are stored by the engine in the fields :profile and :fitspec, and the dictionary only names which one it is. project_spec(h) returns the spec of an open project.

Projects saved before specs existed. They have no :spec. open_project builds the spec from the fields they saved (:kind, :backend, :distance, :minrecall, :dimension, or the exact index itself), and a writable open saves it in :spec. A quantized project saved before specs existed cannot be opened, and has to be created again.

Engine Type Hierarchy

Inside IndexEngine, a project is an engine (AbstractSearchEngine) with a backend. The engine type is the data domain of the stored payloads (DenseEngine, SparseEngine, FullTextEngine). The backend holds the search data structure of SimilaritySearch.jl or TextSearch.jl (SearchGraph, ExhaustiveSearch, ParallelExhaustiveSearch, InvertedFile, BM25InvertedFile, TextInvertedFile). These types are internal: a caller chooses them through the spec.

Properties of the Hierarchy

  • Sparse engine (SparseEngine): Performs inverted-index search over sparse vectors encoded outside the package. The caller supplies SparseVector objects, and no tokenizer or text profile is involved.
  • Introspection of the payload type (payload_kind): Returns :dense, :sparse or :text, so that a calling layer can determine what a project accepts.
  • Valid combinations of engine and backend: The spec types fix them. A DenseVectors spec takes a dense index (Graph or Exhaustive). A TextDocuments spec takes a text index (BM25 or VectorSpace). A SparseVectors spec has no index option, because InvertedFile is its only backend. A combination that is not valid cannot be written as a spec.
  • Domain Separation of BM25: BM25InvertedFile is restricted to FullTextEngine because BM25 scoring relies on corpus-level document frequencies and average document lengths rather than purely geometric vector properties.
  • Structural Dimension Constraints: SparseBackend requires an explicit dimension parameter at initialization because an InvertedFile allocates a fixed array of posting lists.
  • Text model: FullTextEngine keeps its linguistic configuration in a TextProfile (profile): vocabulary frequencies, term weighting, stopword lists, lemma clusters, and query-expansion graphs.

Decoupled Lifecycle: Staging vs. Indexing

The package separates the insertion of items from the construction of the index, which is the expensive operation:

[ Ingestion ] ──────> append_items! ──────> [ Staged Backlog ] ──────> index! ──────> [ Searchable Index ]
                     (Durable in Store)                                              (Searchable in Engine)

Behavior of Each Engine Type

  1. SearchGraph (Dense Engine):
    • append_items! writes the Vector{Float32} arrays to the memory-mapped file dense_vectors.mmapdb. The operation is durable and costs \(O(1)\) per vector. It does not construct graph edges.
    • index! evaluates the backlog range length(index)+1:length(database(index)) and builds proximity graph connections via SimilaritySearch.index!.
  2. FullTextEngine (Text Engine):
    • append_items! appends raw text strings to StagedTextStore within RocksDB.
    • index! processes the staged text backlog:
      • On the first invocation of an uninitialized project, index! executes the linguistic model specification (fitspec) to build the initial TextProfile and instantiate the inverted index.
      • On subsequent invocations, index! encodes staged strings and inserts posting list entries.
  3. ExhaustiveSearch and InvertedFile (Sparse Engine):
    • An exact linear scan evaluates the database directly, and a sparse inverted file updates its posting lists on insertion. append_items! therefore makes an item searchable immediately, and index! performs no work.
    • An exact project of Float32 vectors writes its vectors to dense_vectors.mmapdb, as on SearchGraph. open_project rebuilds the exact index from that file. Nothing else of the index is saved (issue #3).
    • Before 2026-11-22, an exact project saved its whole index in the engine field :index after each inserted item, so an append of \(n\) items wrote \(O(n^2)\) bytes. A writable open_project of such a project moves its vectors to dense_vectors.mmapdb and removes :index. A read-only open reads :index.
  4. Quantized and sketched dense projects, on every dense backend:
    • append_items! writes the Float32 vectors to dense_vectors.mmapdb, as on SearchGraph. An item is not searchable until index!, also on ExhaustiveSearch.
    • index! fits the encoder on its first call, encodes the staged vectors, and inserts the codes into the index. On SearchGraph it then builds the graph connections of the new codes. A sketched project fits its encoder at the first index! with more than 64 staged vectors. See Quantized Dense Indexes and Sketched Dense Indexes.

Concurrency Model

The index structures of SimilaritySearch.jl and TextSearch.jl support concurrent reads. A write that runs at the same time as a read, or as another write, corrupts them.

The package coordinates access from several threads with two mechanisms: ReadWriteLock and ContextPool.

Reader-Writer Synchronization: ReadWriteLock

Each engine maintains a ReadWriteLock to coordinate thread access: - Read Lock (Shared): Acquired by query operations (search, ftsearch, allknn, closestpairs). Allows multiple worker threads to execute searches in parallel. - Write Lock (Exclusive): Acquired by mutating operations (append_items!, index!, delete_item!, calibrate!). Blocks all active readers and concurrent writers.

Context Isolation: ContextPool

A search context (SearchGraphContext, GenericContext, InvertedFileContext) contains working buffers: beam priority queues, sets of visited vertices, and accumulator caches. If two threads search with the same context, these buffers are corrupted.

ContextPool manages a dynamic pool of isolated context instances:

The pool grows to the number of queries that have run concurrently, and it keeps the allocated buffers, so that later queries do not allocate them again.

A context is also what decides how far an operation spreads over threads: SimilaritySearch.getminbatch divides the work of a @BATCHES loop into 8 * Threads.nthreads() batches by default, capped by ctx.maxbatches, and a SearchGraphContext holds one set of visited vertices per batch slot. The two uses of a context therefore want opposite sizes. An operation over many elements – insertion, allknn, searchbatch – wants every slot; a single query is one element and uses one.

The contexts in the pool are built with one slot. Since version 1.6.5, SimilaritySearch allocates the set of visited vertices of a slot when a search first uses the slot: 128 KB for a graph of up to 2^20 vertices. Measured on 2026-10-13 with 64 threads, over a graph of 20,000 vertices, a context of the pool holds 0.13 MB after a search. A default context has 512 slots on 64 threads. It holds 0.3 MB after one search, and 62.7 MB after a searchbatch that used 500 of its slots. The two contexts returned the same identifiers for each of 1,000 queries. The context the batch operations run on, backend.ctx, keeps the full count, and create_project and open_project accept runtime=Runtime(maxbatches=n) to cap it: with fewer batches than threads, the threads that are left stay available for queries. That cap belongs to the process rather than to the project, so it is passed when the project is opened and not stored in it.

Measuring the Cost of a Query

The use of a pool has a consequence for measurement. SimilaritySearch.jl counts the work performed by an operation in the context itself (ctx.costdists). These counters accumulate and are never reset, so the cost of one operation is the difference between two readings taken before and after it.

This method is correct for insertion, which uses the engine’s own ctx under an exclusive write lock. It is not correct for search. A query uses a context taken from the pool for the duration of the call, and the context returns to the pool when the call ends. A reading taken afterwards includes the work of any other query that has used the same context since.

The count is therefore computed inside IndexEngine.search_live, between checkout and checkin, and is reported to the caller in a SearchStats instance that the caller provides:

stats = SearchStats()
results = search(h, query, 10; stats)
stats.distance_evaluations

search, ftsearch and the filtered form of search accept this argument. For a filtered search, the value is the cost of the candidate search that was executed, not of the k results that satisfied the predicate. Each call overwrites the field; values are not accumulated. The server obtains the distance_evaluations field of its op_log from this mechanism.

Persistence Architecture

A project is stored in RocksDB column families and in one memory-mapped file. A write modifies only the segments it affects.

The Persisted Text Index

A text project stores the index itself: posting lists in invfile_postings, and one vector per document in invfile_docvecs. Both text backends are stored this way. Their posting lists contain the same data, document identifiers, and they differ only in the representation of each document. Three representations are used, and each stored value begins with a one-byte tag that identifies its own: integer term frequencies (BM25), Float32 model weights (the weighted backend), and bags of words (the weighted backend under a set distance, which reads membership instead of weights). A sparse project stores the objects it indexed, in sparse_db, and reconstructs its index at every open. Its items are vectors encoded by the caller, so the stored objects are already the representation that would be written; applying the same treatment to a sparse project remains pending work.

The two procedures differ in cost. Over 265,000 Project Gutenberg paragraphs, reconstruction takes 20.4 s, and assembly from storage takes 1.4 s with BM25 and 1.7 s with the weighted backend (measured 2026-09-11 and 2026-09-12). Indexing the same corpus takes 25.7 s and 26.4 s respectively, compared with 147.3 s before, because a block is now encoded by the parallel batch procedure of the library instead of one document at a time.

Writing is incremental and proceeds by blocks. Each call to index! encodes its backlog as one block, inserts the document vectors and lengths of that block into the index in memory, and passes its posting lists to IndexEngine.persist_block!, with identifiers converted from block-local to global. The implementation of that function reads, modifies and writes one stored list per token that the block contains. Appending is correct because document identifiers increase monotonically: the identifiers of a block are larger than every identifier already stored, so the ascending order required by the merge at query time is preserved. IndexEngine contains no reference to RocksDB, and dispatches on the type of adjacency list of its index.

The unit of writing is the block, and the number of blocks has a cost. The list of a token is rewritten once per block that contains it, so the same 50,000 documents take 5.8 s in one block, 6.8 s in ten, and 10.1 s in fifty (measured 2026-09-12). Large blocks are therefore preferable, which is the result of calling append_items! and then a single index!.

Posting lists are read on demand; document vectors are not. The reason is measured. A query reads one posting list per query term, so reading them from storage increases latency by 1.8% (66.8 ms against 68.0 ms) and removes 55.8 MB of 237.5 MB from memory. Scoring reads the term vector of each candidate (bm25score(..., idx.db[docID])), and the merge makes every document that contains any query token a candidate. With a frequent term, reading document vectors on demand becomes one point read per document in the collection: 1,771.9 ms against 66.8 ms for the same query. Document vectors are therefore read into memory when the project is opened (0.76 s for that corpus).

Posting lists read on demand are kept in a least-frequently-used cache. The cache holds a maximum number of lists and is reduced to a base size when that maximum is exceeded. Lists are removed only after a query has finished, never during one: concurrent searches hold read locks rather than exclusive locks, and a list removed during a query would be read again by any search still using it.

There is no migration from the previous format. A project written before the index was persisted opens with its profile and its staged text, and with no index. A search against it reports this condition, and one call to index! builds the index from the staged text, which was always persisted independently of the index. Supporting the previous format would require keeping the reconstruction procedure for projects that do not yet exist, since no version has been released. The migration is therefore explicit:

h = open_project(workdir, dataset)
index!(h)

Partitioned Text Indexes

This section and the next describe the partitions inside a project. Since 2026-11-22 a partition follower holds the same structures in its own database (see Partition Followers), and migrate_partitions! moves the partitions of a project to one.

A text project can declare one meta field as its partition field (partitions=PartitionBy(field) in create_project, or declare_partition! later). Each value of the field is a partition. Three column families store the partitions:

  • partition_table maps each partition name to a number and to the number of items appended to it. Numbers start at 1, follow the order in which the names first appear, and are not reused. The table is read into memory when the project is opened.
  • partition_members maps the _id of an item to the numbers of its partitions. append_items! writes it before the staged text, so that an item never exists without its partitions.
  • partition_postings holds one posting list per partition and token, under the key [partition number][token id], both big-endian. The lists of one partition are therefore contiguous.

The global posting lists in invfile_postings do not change. A document identifier appears once in the global list of each of its tokens, and once more for each partition of its item.

Writing. persist_block! writes the global lists and the partition lists of a block in the same WriteBatch. It reads the partitions of the block’s documents from partition_members, splits each global list of the block by partition, and appends each part to the stored list of that partition and token. A failure during a block therefore leaves both kinds of list at the end of the previous block. declare_partition! builds the partition lists of a project that is already indexed by splitting each stored global list once. It reads no text.

Reading. A search in a partition runs on an index built for that query from the live one. It keeps the vocabulary, the scorer, the document vectors and the query pipeline, and replaces the posting lists with a PartitionPostings of that partition. Building it reads nothing from disk. The merge then considers only the documents of the partition. The score of a candidate is computed from the vocabulary statistics, the scoring parameters and the candidate’s document vector, which are the global ones. A document therefore gets the same score in the partition search and in the global search. Partition lists are read on demand and kept in one cache per project, with the eviction rule of the global lists.

Measurement. The values below were measured on 2026-11-10 with 64 threads, Julia 1.12.7, SimilaritySearch 1.6.11 and TextSearch 1.3.0. The project was a BM25InvertedFile project with 446,857 documents of the ReposMx corpus, in 91 partitions of 8 to 139,605 documents. The queries were the 114 distinct document queries of the ReposMx reference set, with k = 10.

  • declare_partition! took 12.0 s on the indexed project. index! had taken 207.9 s.
  • The partition lists hold 1,798,840 keys and 144.1 MiB of keys and values. The global lists hold 174,106 keys and 131.1 MiB.
  • A global search took 12.0 ms on average, with a median of 5.2 ms.
  • A search in a partition took 0.42 ms on average, over 10 partitions of different sizes. The median was 0.17 ms, and the maximum 26.4 ms. The mean was 0.11 ms for the partition of 8 documents and 2.21 ms for the partition of 139,605 documents.
  • A global search followed by a filter took 373 ms on average for the same 10 partitions. It asked for 40 results, and for 4 times as many each time the filter kept fewer than 10.
  • In the 1,140 pairs, the partition search and the filtered global search returned the same identifiers, in the same order, with equal scores.

Projects written before partitions existed. A writable open creates the three column families. A read-only open cannot create them, so it opens only the column families that exist on disk.

Partitioned Dense Indexes

A dense project declares its partition field in the same way as a text project, and uses the same partition_table and partition_members. A partition is a SubDatabase of the vectors of the project: a view whose map is the ascending list of the _ids of its members. No vector is copied. The distance from a member to a query is the same in the partition and in the global index.

  • A partition with fewer than graph_min members (an option of PartitionBy) is searched with an exact scan of its members. The default is DEFAULT_PARTITION_GRAPH_MIN, 4,096.
  • A partition with at least graph_min members, on a SearchGraph project, has its own SearchGraph over its view. The ids of that graph are positions in the view, and a search maps them back to _ids.
  • On an exact project, every partition is scanned.

Writing. On a SearchGraph project, a partition holds only indexed items. After the global graph indexes its backlog, index! reads the partitions of the new items from partition_members and appends them to their partitions. Then each partition graph indexes its new members, and each partition that reached the threshold gets a graph built from all its members. Both steps run under one write lock. A partition graph is saved as the global one is: the direct neighbors of each range go to the partition_graph column family, under the key [partition number][local id], and the number of members it holds goes to the engine field partition_graph_len. An item is inserted once in the global graph and once more in each of its partitions that has a graph. On an exact project, the members of a partition are added when the items are appended.

Reading. A scan returns the exact answer. A partition graph searches with its own BeamSearch and hints, tuned while it was built. calibrate!(h; partition) calibrates one partition graph, and only that call does: a search with minrecall in a partition that was never calibrated raises NotTrained.

Opening. open_project reads partition_members once, in _id order, to rebuild the view of each partition, and rebuilds each partition graph from partition_graph with its saved BeamSearch, hints and calibrated levels. A partition graph that holds fewer members than its view, because the process stopped between the global graph and the partition graphs, gets the rest from the next index!. Until then the partition is searched with a scan if it has no graph yet.

Measurement. Measured on 2026-11-18 with 16 threads over 200,000 synthetic vectors of 128 dimensions in 200 clusters, with 200 queries and k = 10, each partition a random subset:

members exact scan own graph recall of the own graph global graph and filter, 10,000 candidates
200 0.010 ms 0.015 ms 0.95 recall 0.18
2,000 0.12 ms 0.016 ms 0.89 recall 0.84
20,000 3.7 ms 0.039 ms 0.96 recall 0.99
60,000 10.5 ms 0.096 ms 0.96 recall 0.99

The own graphs were tuned with MinRecall(0.9). The global graph was not tuned, so the last column also reflects its own recall. A measurement on real embeddings will set the default threshold again.

Quantized Dense Indexes

A dense project created with storage=Quantized(SQ(bits)) stores the codes of a scalar quantizer of SimilaritySearch.ScalarQuant instead of Float32 vectors (issue #1). The index is the one the project was created with, Graph or Exhaustive, built over a QuantDatabase. A query is rotated and prepared once by encodequery, and then evaluated against the codes with the distance of ScalarQuant that corresponds to the distance of the project: SqL2, L2, L1, Cosine or NormCosine.

  • Quantizers. SQ(bits) has 8, 4 or 2 bits per coordinate. SQ(bits; range=GlobalRange()), the default, uses one range for every coordinate of every vector. SQ(bits; range=PerVectorRange()) uses one range per vector, which costs 8 bytes per vector.
  • Rotation. rotation=NoRotation() is the default. It works for the output of most modern neural embedding models, whose coordinates have similar scales: on SISAP 2025 ccnews, a QR rotation changed recall@10 by less than 0.01 at every width. rotation=QRRotation() gives every coordinate the same scale. Use it for vectors that are not normalized, for vectors of several models in one project, for features that a neural model did not produce, or when the recall on a sample of queries is clearly below the exact search. It costs dim² operations for each query and each inserted vector, and 4 dim² bytes of storage. rotation=HadamardRotation() costs dim log dim operations, and the dimension must be a power of two.
  • Fitting. The first index! fits the encoder on samplesize staged vectors, chosen at random. Before 2026-11-23 the sample was built with reduce(hcat, ...) over a generator, which copies the matrix at each column: the first index! of 603,664 vectors of dimension 384 took 5 to 7 s, and it takes 2 to 3 s now. A global quantizer estimates its range from them, unless GlobalRange(minmax=(lo, hi)) gives it. A per-vector quantizer calibrates how it rounds each range. fit_quantizer!(h; rng) fits the encoder without encoding. The fitted encoder, with its rotation matrix, is saved in the engine field :encoder.
  • Storage. The codes are in dense_codes.mmapdb, a memory-mapped file with one row of bytes per vector. The ranges of a per-vector quantizer are in dense_code_ranges.mmapdb, two Float32 per vector. index! reads, encodes and inserts the staged vectors in blocks of QUANT_ENCODE_BLOCK (16,384). With keep_vectors=false, the default, index! then removes dense_vectors.mmapdb, and the next append_items! starts a new one. The engine field :raw_offset holds the number of items before its first row.
  • Reading back. fetch_items returns the vector of an item whose Float32 vector is still on disk: every item with keep_vectors=true, and an item not yet encoded otherwise. It returns nothing as the payload of any other item, because the codes do not give back the vector that was appended.
  • Opening. open_project reads the encoder, maps the codes file, and on SearchGraph restores the graph from the adjacency store. The staged vectors not yet encoded are the rows of dense_vectors.mmapdb after :raw_offset plus the number of codes. A file whose rows are all encoded, in a project that does not keep them, is what an interrupted index! leaves, and it is removed.
  • Memory. The codes stay in the mapped file, and only the code sums (8 bytes per vector) and, for a per-vector quantizer, the ranges (8 bytes per vector) are in memory. A Float32 project holds every vector in memory: a graph project and an exact project copy the vectors out of dense_vectors.mmapdb when they are opened. Measured on 2026-11-20 with 200,000 vectors of dimension 256 (test quantized project: resident memory follows the size of the codes): opening the project and running one search added 403 MB of resident memory for the Float32 vectors of a graph project, and 50 MB for the 8-bit codes, whose file holds 51 MB.

Sketched Dense Indexes

A dense project created with storage=Sketched(hyperplanes; bits) stores a sketch of each vector instead of the vector (PLAN.md §5.14). The sketch is built by SimilaritySearch.Projections:

  • An AnchoredDistantHyperplanes model selects hyperplanes pairs of vectors of a sample, the anchors. Each pair (a, b) defines a hyperplane: the vectors closer to a than to b under the distance of the project are on one side.
  • A QuantSketch encodes the signed margin of a vector v against each pair, d(v, b) - d(v, a), divided by d(a, b), at bits bits. At 1 bit it keeps the sign, in UInt64 words compared with the Hamming distance. At 2, 4 and 8 bits it keeps a UInt8 code of the margin, and the codes are compared with the squared Euclidean distance of SQgu2, SQgu4 or SQgu8.

A sketch takes hyperplanes × bits / 8 bytes. The index of the project, Graph or Exhaustive, is built over the sketches, and a query is sketched as the vectors are. The model uses only distances, so the distance of the project can be any SemiMetric. A scalar quantizer takes only SqL2, L2, L1, Cosine and NormCosine.

  • Second evaluation. rerank=r searches r × k candidates among the sketches, evaluates them again with the distance of the project and the Float32 vectors, and returns the best k. It needs keep_vectors=true. It applies to search, searchbatch, a search of one partition, and a search of a view of a partition follower. Without it, a result has the distance between sketches, which orders the results and is not the distance of the project.
  • Centering. center=true subtracts the mean of the fitting sample from every vector and every query. Under L2 and SqL2 it changes no distance. Under Cosine and NormCosine it changes the angles between the vectors. It is off by default. A rotation changes no distance, so Sketched has no rotation.
  • Fitting. The first index! fits the encoder on at most samplesize staged vectors. The model evaluates hsel candidate pairs on henc vectors of the sample, which costs 2 × hsel × henc distances. It keeps the pairs whose sides have an entropy above the entquantile quantile, about hsel × (1 - entquantile) of them, and selects the hyperplanes most diverse of those. Sketched refuses options that keep fewer pairs than hyperplanes. The encoder needs more than 64 staged vectors. With fewer, index! leaves them staged, and search raises NotTrained. The encoder saves only the anchors its hyperplanes use, not the sample, in the engine field :encoder.
  • Random numbers. AnchoredDistantHyperplanes and QuantSketch draw their samples from the default random generator of Julia. The rng of fit_quantizer! selects only the rows of the sample, so two fittings of the same data can select other anchors.
  • Ties. At 1 and 2 bits, many distances between sketches are equal. A graph reopened from disk can order the tied results differently, because it visits the neighbors of a vertex in another order. The distances are the same.
  • Storage. As in a quantized project: the sketches are in dense_codes.mmapdb, keep_vectors decides whether dense_vectors.mmapdb stays, and fetch_items returns the vector only when it is still on disk. sketch_info(h) reports the storage, whether the encoder is fitted, the dimension, the range of the codes, and the bytes per vector in memory and on disk.

Measurements. Measured on 2026-11-23 on SISAP 2025 ccnews (dev): 603,664 vectors of dimension 384, NormCosine, the first 1,000 otest queries, an exact search over the sketches, and 32 threads of a Xeon Silver 4216. Recall@10 is the fraction of the exact 10 nearest neighbors in the results, without a second evaluation. The rotations in this table are QuantSketch over RandomProjections: a random orthogonal matrix (the QR factorization of a matrix of normal values), and a PCA fitted on the sample. The hyperplanes used hsel=16m, henc=4096 and entquantile=0.9.

bytes per vector AnchoredDistantHyperplanes random orthogonal projection PCA
64 (256 components, 2 bits) 0.388 0.580 0.579
128 (256 components, 4 bits) 0.430 0.714 0.805
256 (256 components, 8 bits) 0.432 0.734 0.929
384 (384 components, 8 bits) 0.456 0.988 0.951

At the same memory, the hyperplanes gave the lowest recall at every width. Through the engine on the same data, Quantized(SQ(8)) (384 bytes) gave 0.988, and Quantized(SQ(4)) (192 bytes) gave 0.909. For the vectors of a language model, use Quantized.

Defaults. The defaults are Sketched(256; bits=8, rerank=0, keep_vectors=false, center=false, samplesize=16_384, hsel=16hyperplanes, henc=1024, entquantile=0.5, anchorpolicy=:random). On the same data:

  • henc from 1,024 to 8,192 and samplesize from 4,096 to 65,536 changed recall@10 by less than 0.015, with one seed.
  • entquantile=0.5 raised recall@10 by 0.06 to 0.075 over 0.9, at the same cost.
  • With the defaults, over 3 seeds, recall@10 was 0.483 to 0.493, and 0.73 to 0.74 with rerank=4. The fitting took 0.1 s at 256 hyperplanes, 0.8 s at 1,024, 2.6 to 3.9 s at 2,048 and 8.2 to 11.9 s at 4,096, independent of the size of the collection.
  • At 256 bytes per vector, more hyperplanes with fewer bits gave more recall: 0.49 with 256 × 8 bits, 0.53 with 512 × 4, 0.56 with 1,024 × 2, and 0.55 with 2,048 × 1. Encoding a vector costs 2 × hyperplanes distances: 1.2 µs per vector at 256 hyperplanes and 15.5 µs at 2,048, with 32 threads.
  • The defaults of AnchoredDistantHyperplanes in SimilaritySearch (hsel=1024m, henc=8192, entquantile=0.9) gave 0.03 to 0.04 more recall@10 with a fitting 100 to 140 times as long: 10 s at 256 hyperplanes and 41 s at 1,024. SimilaritySearch issue #153 proposes the defaults of the engine for the library.

External Identifier Resolution

doc_id is the identifier supplied by the caller. It is resolved through the idx_docid column family, not by scanning records. Keys are composite: the bytes of doc_id followed by the four bytes of _id. This allows several items to share one doc_id. fetch_items returns every record that carries the requested identifier, in ascending _id order, and exists reports the identifier as deleted only when all of those records are deleted. On a project of 50,000 items, resolving an external identifier takes 0.12 ms through this index, compared with 59 ms for the scan it replaces.

A project written before this index existed is migrated the first time it is opened for writing. Project.backfill_docid_index! performs one pass over records and writes a marker key, so that later opens do not repeat the pass. A read-only handle opened on a project that has not been migrated uses the scan instead.

Compaction

Bulk writes leave a write-ahead log, and the next open must replay it. Compaction therefore affects the latency of opening a project, not the latency of writing to it. close_project! compacts every column family of the project before closing, unless the handle is read-only, the session performed no writes, or the caller passes compact=false. compact_project! performs the same operation while the project remains open. On a dense project of 50,000 vectors, reopening takes 2.97 s without compaction and 0.28 s with it, and the compaction itself takes 0.03 s.

Storage Subsystems

  1. EngineStore (Engine Field State):
    • Stores the spec of the project (:spec) and the engine state as individual key-value entries (:opt_beamsearch, :beamsearch, :deleted_ids, :profile).
    • :beamsearch is the BeamSearch of a graph: the parameters of the beam search that a query without minrecall uses. index! tunes it while the graph grows, and calibrate! leaves the last level it tuned. Both calls save it.
    • :hints are the starting points of a search in the graph. index! picks them and saves them.
    • Mutations (e.g., updating deleted IDs or storing calibration results) rewrite only their specific keys.
  2. Dense Vector Storage (dense_vectors.mmapdb):
    • Dense vectors are stored in a dedicated memory-mapped binary file managed by MMapMatrixDatabase. Every dense project writes it: a graph project, an exact project of Float32 vectors, and a quantized or sketched project until index! encodes the vectors.
    • Avoids key-value serialization. Appends are sequential, and random access reads the vector without copying it.
  3. Quantized and Sketched Code Storage (dense_codes.mmapdb, dense_code_ranges.mmapdb):
    • The codes of a quantized project or the sketches of a sketched project, and the ranges of a per-vector quantizer. See Quantized Dense Indexes and Sketched Dense Indexes.
  4. AdjacencyStore (Graph Topology):
    • Graph adjacencies are persisted incrementally through CallbackLog observer hooks during index!.
    • Stores only forward (direct) edges; reverse edges are reconstructed dynamically in memory during project reopening to ensure idempotency.
  5. StagedTextStore and InvertedFileObjectStore:
    • StagedTextStore holds un-encoded raw text lines.
    • InvertedFileObjectStore stores contiguous blocks of encoded posting-list objects.

Project Reopening Lifecycle

When a project is reopened, the stored forward edges are read again and the reverse links are regenerated. Then the saved BeamSearch and hints are set on the graph. The reverse links are rebuilt in one pass, while index! added them in batches, so the order of the neighbors of a vertex can differ from the graph before the reopen. On 4,000 random vectors of 16 dimensions, measured 2026-11-18, 19 of 20 queries took the same distance evaluations and all 20 returned the same results before and after a reopen. The other query took 394 evaluations instead of 384.

Before 2026-11-18, neither was saved. A reopened graph searched with the default BeamSearch of SimilaritySearch, from random starting points. On 20,000 random vectors of 64 dimensions, a query took 2,534 distance evaluations before the project was closed and 350 after it was reopened, with a lower recall. A project saved before that date has neither field. It keeps the default until its next index! that indexes new items, or its next calibrate!.

Leader and Follower Datasets

A follower is a dataset that organizes the items of another dataset, its leader (issue #5, server/PLAN.md §5.11). It reads the items of the leader and does not copy them. It stores its own structure, expressed with the _ids of the leader. A leader can have several followers, and each one is created, rebuilt and deleted without a change to the items of the leader.

The engine includes the framework of followers and two kinds, the partition follower and the keyword follower, since 2026-11-22.

Concepts

  • Key source. A key source is the part of an item that a follower uses: Keywords(), Refs(), DocId() or MetaValue("field"). keys_of(source, item) returns the keys of one item: nothing, a string, or a list of strings. A key is a non-empty string. A key source that reads the payload says so with needs_payload, because a copy of each vector costs time and memory.
  • Kind of follower. A kind is a subtype of FollowerSpec. It holds its key source and its options, and it implements a small interface: create and open its state, process a block of items, and report its statistics. The docstring of FollowerSpec lists the functions.
  • Position. The position of a follower is the last _id of the leader that it processed. A follower processes the items of the leader up to IndexEngine.indexed_length of the leader: the items that a search of the leader can return. A staged item that index! has not indexed is not processed.
  • Generation. The leader saves a random identifier of the numbering of its items in the engine field :generation. A rebuild of the server creates a new project, which can change the _ids, and the new project has a new generation. A follower saves the generation it was built from. When the two differ, open_follower raises StaleFollower, and rebuild_follower! builds the follower again.

Names and Storage

The canonical name of a follower is leader/follower, and the name of a follower restricted to one value is leader/follower=value. open_follower(h, "by_repo=unicach") returns a FollowerView restricted to that value.

A follower is stored in <workdir>/<leader>.followers/<follower>/, a RocksDB database with the column family engine and the column families of its kind. It is not inside the directory of the leader, because that directory is the database of the leader. A dataset id of the server cannot contain ., so this directory is never taken for a dataset.

The engine fields of a follower are the name of its leader, the generation of the leader, its position, a description of its kind for followers(h), the name of its plugin, and its spec and policy. All of them except the spec and the policy are plain values, which can be read without the plugin. The leader saves the names of its followers in :followers.

Processing

sync!(f) reads the records and the meta of the items of the leader after the position of the follower, computes their keys, and passes them to the kind. It works in blocks of FOLLOWER_SYNC_BLOCK (16,384) items and saves the position after each block. An interruption repeats at most one block, so a kind must give the same result when it processes the same items twice. Deletes are not processed: a result of a follower is an _id of the leader, and the leader marks a deleted item in each result.

A policy says when a follower processes the new items:

policy when
OnIndex() (default) after each index! of the leader
OnWrite() after each append_items! of the leader; on a leader that stages its items, nothing is indexed at that point
Periodic(; seconds, items) in the server, as a task of serve; the engine treats it as Manual()
Manual() only at sync!

open_follower registers the follower in the handle of its leader. index! and append_items! of the leader call sync! on the registered followers whose policy applies, after the leader has saved its own work. When sync! of a follower raises, the other followers are processed, and the first error is raised afterwards. close_project! of the leader closes its followers first. open_follower processes nothing: a follower that lags behind its leader stays behind until its policy or sync! processes the new items. follower_status(f) and followers(h) report the position, the lag and whether a follower is synchronized.

A follower that cannot process an item stops before the block of that item. It does not skip the item, so the next sync! tries it again. An item stops a follower when its key source returns a value that is not a key, for example a number in meta, or several keys for a disjoint partition follower. Each failure of sync! is written to the log as an error, with the name of the follower and its position, and follower_status(f).error holds its message until a sync! succeeds. The leader keeps the item, and its searches return it.

A follower accepts no direct write. append_items!, delete_item! and index! on a follower raise UnsupportedOperation, and the message names the leader.

Plugins

A spec or a key source whose type is defined outside the engine belongs to a module registered with register_plugin!. The engine saves the spec with Serialization, and a value of a type from a module that is not loaded cannot be read back. A follower saves the name of its plugin as a plain value, and open_follower raises PluginNotLoaded before it reads the spec in a process that has not registered the plugin. create_follower refuses a type from a module that is not registered.

Partition Followers

PartitionFollower(source; disjoint=true, graph_min=nothing) divides the items of a text or a dense leader into partitions, one per key of source. In a disjoint follower an item has at most one key, and an item with several keys raises PayloadMismatch. A non-disjoint follower, disjoint=false, puts an item in each partition it names: an author of ReposMx belongs to each institution where they have documents.

The follower holds the column families of the partitions inside a project, partition_table, partition_members, partition_postings and partition_graph, with the same keys and values, in its own database. It reads everything else from its leader.

  • Text leader. For each block of items, the follower reads the token ids of each document from the document vectors of the leader, which are in memory, and appends the document to the list of each of its partitions and tokens. It does not read or tokenize text. A search in a partition builds the index of the leader with the lists of the partition in place of the global ones, as for the partitions inside a project. A document therefore gets the same score in the partition search and in the global search.
  • Dense leader. A partition is a view of the vectors of the leader. A partition with fewer than graph_min members, and every partition of an exact leader, is searched with an exact scan. A larger partition has its own graph, built and extended under the write lock of the leader, whose vectors it reads. The direct neighbors of each range are saved in partition_graph, and the number of members each graph holds in the engine field :partition_graph_len of the follower. calibrate! on a partition saves its levels in the follower.

open_follower(h, "name=value") returns the partition value, and search, ftsearch and calibrate! accept it. A partition name that the follower does not hold raises UnknownPartition, with the closest names. partitions(f) lists the partitions with the number of items of each one, and follower_status(f).stats gives the number of partitions, the number of memberships, the smallest, median and largest partition, and the number of graphs.

Processing a block again gives the same structures. The members of an item that already has an entry in partition_members are not counted again. An id that is not larger than the last id of a posting list is not appended to it. A dense partition does not take an id that its list already ends with or exceeds. When a follower is opened, a dense partition takes the members of the processed items only, and a graph that holds members of an unprocessed block keeps its first members, because a graph saves only the links of each member to earlier members.

migrate_partitions!(h, name; disjoint) moves the partitions inside a project to a partition follower over MetaValue(field), with the graph_min of the project. It builds the follower from the items of the leader. Then it empties the partition column families of the project and deletes its partition fields. The calibrated levels of the partition graphs are not moved. With disjoint=true and a field that holds a list, it raises PayloadMismatch, and the project keeps its partitions. After the migration, a search with partition on the project raises InvalidOption, and the message names its followers.

Keyword Followers

KeywordFollower(source=Keywords(); distance=Dist.Sets.Jaccard()) indexes the keys of each item of its leader in a DictInvertedFile of SimilaritySearch: an inverted file whose posting lists are keyed by the key itself, a String, so it needs no vocabulary of its own. The leader can be a project of any kind.

  • It indexes one object per item of the leader, the set of keys of the item, empty when the item has none. The numbers of the inverted file are therefore the _ids of the leader, and its posting lists hold them.
  • The keys of each processed item are stored in the column family keyword_items of the follower, under the big-endian _id. open_follower rebuilds the inverted file in memory from them, in one block. Items are inserted in blocks because the inverted file sorts every posting list after each block.
  • search(f, keys, k; t) merges the posting lists of the query keys. t is the number of lists an item must appear in. Dist.Sets.Jaccard, Dice, Intersection and CosineSet are computed from the sizes of the two sets and of their intersection during the merge. Another distance is evaluated on the stored keys of each candidate. A key that no item holds is ignored.
  • A keyword follower has no restriction to one value, and it lists no keys. follower_status(f).stats gives the number of keys, the total length of the posting lists, the shortest, median and longest list, and the number of items without keys.

posting_list(h, key; limit) returns the _ids of the items that hold one key, in ascending order, for every index with posting lists: a keyword follower (a key), a text project (a token of its vocabulary, read from invfile_postings through the cache of lists) and a sparse project (a dimension). With limit=n it returns the first n ids, without a cursor. Deleted items are in the lists. A dense project has no posting lists and raises UnsupportedOperation.

Failure Reporting: Typed Errors and Their Boundaries

Every failure that the engine raises is an EngineError. The type of the error, not its message, is the interface. There are four abstract categories, and one or more concrete types under each of them:

category meaning concrete types
InvalidRequest the call cannot be honoured as written; retrying it unchanged fails again PayloadMismatch, WrongDimension, UnknownBackend, InvalidOption, UnsupportedOperation
NotFound something the call named does not exist ProfileNotInstalled, UnknownPartition, UnknownFollower, PluginNotLoaded
ConflictingState the request is well formed but the project is not in a state that can serve it; the same call succeeds later PendingBacklog, NothingStaged, NoIndex, NotTrained, EmptyProject, ProjectClosed, StaleFollower, HasFollowers
StorageFailure what was read back cannot be interpreted CorruptedStorage

ProjectClosed is raised by every function that takes a handle after close_project! closed it. That handle stays closed, and the same call succeeds on a new handle from open_project. A follower raises it after close_follower!, or after close_project! of its leader.

The concrete types carry the values a caller can use. PendingBacklog reports the number of staged items and the number of indexed items, WrongDimension reports the expected and the received length, and InvalidOption reports the keyword that was rejected.

The mapping is defined at each interface, not in the engine. The engine contains no reference to HTTP status codes or to process exit codes. Each consumer performs the translation:

try
    search(handle, query, 10)
catch e
    e isa ConflictingState && return retry_after_indexing()
    e isa NotFound && return not_found()
    rethrow()
end

SimilaritySearchServer maps the categories to status codes: NotFound to 404, ConflictingState to 409, InvalidRequest to 400, and any other failure to 500. Its command lines map the same categories to exit codes 4, 5, 2 and 70, so that a shell script can select a branch without reading the output text. This mapping is the only coupling between the two packages of this repository, and the server manual states it in one table.

The alternative, error("...") with a message, requires every consumer to classify the failure by its text. Such a classification fails when the wording changes, and it fails without any error being reported. This had occurred in this repository: the concurrency test identified a rejected operation with occursin("requires no pending backlog", e.msg). It now matches the type PendingBacklog.

Logging Channels: Reporters and Observers

A context maintains two separate logging channels: - Reporters (ctx.reporters): Receive progress messages via INFORM and output formatted status lines to stderr or custom IO streams. Throttled to prevent console flooding. - Observers (ctx.observers): Receive structural mutation events (:add!) via OBSERVE. Execute un-throttled callbacks that trigger persistence updates (CallbackLog).

Soft Deletions and Dataset Operations

  • Soft deletions: delete_item! records document identifiers in deleted_ids. The index is not reorganized. A query evaluates such candidates and reports them with the field deleted::Bool of SearchResult.
  • Operations over an entire collection: allknn, fft, closestpairs and bichromatic_kclosestpairs operate on the index in memory, using multithreaded batch routines over the whole collection.
