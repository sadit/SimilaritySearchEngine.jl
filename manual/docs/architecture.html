Architecture

This page describes how SimilaritySearchEngine.jl is put together: its module map, the engine type hierarchy that replaces name/enum-based dispatch with real Julia types, the staging-vs-indexing split that lets a project decouple insertion from the expensive graph-connection/encoding step (dense and full-text alike), the concurrency model that lets searches run in parallel while staying safe from concurrent inserts, and the RocksDB-column-families-plus-one-mmap-file layout that makes persistence incremental instead of a single ever-growing blob.

Module map

The package is five source files, four of them real submodules (Schema, Project, IndexEngine, Persistence) plus embedded.jl, which defines EmbeddedEngine and the top-level functions (create_project, append_items!, search, …) directly in the SimilaritySearchEngine module itself — the friendly surface a script actually calls.

IndexEngine and Persistence are deliberately independent of Project/Schema and of each other: IndexEngine knows nothing about RocksDB (its persistence hook is a plain (index, sp, ep) -> nothing callback), and Persistence knows nothing about metadata schemas or search engines (it stores plain Julia values under string keys). embedded.jl is the one place that wires all four together — every other module could, in principle, be reused on its own.

Schema/Project have no per-project typed-field schema to declare anymore: every project has exactly the same fixed-shape Schema.MetadataRecord (_id, doc_id, keywords, refs) plus a free-form meta JSON blob for everything else appended with an item — _id is the internal, sequential, always-present handle (the same id space the engine’s own vector/text store uses); doc_id is the caller’s own external id, if any; keywords/refs are the only two fields with a secondary index (Project’s fixed idx_keywords/idx_refs column families), everything else lives in meta, looked up straight from Project, never indexed.

Engine type hierarchy

A project is two decisions, and the hierarchy keeps them apart: an engine says what the project holds, and a backend says which index holds it.

create_project(w, ds)                                              # dense vectors, SearchGraph
create_project(w, ds; engine=DenseEngine, backend=ExhaustiveSearch)
create_project(w, ds; engine=SparseEngine, dimension=50_000)
create_project(w, ds; engine=FullTextEngine, backend=BM25InvertedFile,
                      textmodel=DefaultProfile(:es))

Three engines, because there are three kinds of thing a caller can hand over — a dense vector, a sparse vector, a string — and each needs a different amount of machinery to accept it. Four backends, because there are four ways to hold an index and they carry different state. There is still no enum tag anywhere: the concrete Julia type is what add_item!, search_live and every other generic function dispatch on, and DenseEngine{B} dispatches on its backend too.

A few design choices worth calling out:

  • The split exists because of SparseEngine. Before it, the hierarchy was one struct per index kind — a SearchGraphEngine, a GenericEngine{IndexType}, a BM25Engine, an InvertedFileEngine — which sorted projects by the thing a caller is least likely to know and most likely to change. It also left a hole: an InvertedFile and its distance were reachable only through a text engine, so a caller who already held sparse vectors had to pretend to have text — fit a profile it did not want, stage strings it did not have. SparseEngine is that missing layer, and separating the two decisions is what made it expressible.
  • payload_kind(engine) returns :dense, :sparse or :text, and is what guards ask instead of the is_text_index predicate they used to. With two kinds, “not text” meant “dense”; with three that reading is simply false.
  • BACKENDS is the table of legal pairings, read three ways — to default a backend, to check one, and to name the alternatives in the error when a check fails. InvertedFile appears under both SparseEngine and FullTextEngine on purpose: the same library index serves sparse vectors a caller encoded and text this package encodes, and engine is what says which. Three methods instead of one table would drift; the table cannot.
  • BM25 is not one of SparseEngine’s distances, which is the one asymmetry worth explaining. BM25InvertedFile holds a Vocabulary and scores from getndocs/avgdoclen: BM25 is a scoring rule over a corpus, not a metric over sparse vectors. So it stays with FullTextEngine, which has the corpus statistics, and SparseEngine takes the distances that read a vector — cosine over the weights, or one of Dist.Sets.* over the nonzero positions.
  • minrecall/opt_beamsearch live on GraphBackend and nowhere else — only a SearchGraph autotunes a BeamSearch toward a target recall. On the engine they would be two fields every exact and every inverted-file project could only ever leave empty.
  • SparseBackend records the dimension it was created with, and create_project requires it for a sparse project. An InvertedFile is a fixed array of posting lists: the dimension is structural, not descriptive, so it has to be known before the first item and every item appended has to agree with it.
  • FullTextEngine carries its whole text model in one field, profile::Union{Nothing, TextProfile} — vocabulary and weights (profile.model) plus the corpus-produced artifacts (stopword set, lemma map, query-expansion network) and the lineage saying how it was produced. That replaced a voc/model pair carried before TextSearch 1.1 published TextProfile, and the reason to prefer it is structural: an artifact has exactly one home, and the TextConfig the tokenizer runs is derived from the profile, so an index cannot end up tokenizing documents through a different lemma map than the one it saves.
  • A text project is created from an AbstractTextModelSpec: three answers to “where does the vocabulary come from”, not variations on one setting. BaseProfile(profile) trains it at creation. DefaultProfile(:es) and FitFromCorpus(textconfig; …) leave it untrained and store the recipe in fitspec, for the first index! call to carry out — the first by loading the published profile for that language and refitting it against the staged corpus, the second by delegating a fit of it to TextSearch.fit_profile. index === nothing exactly while profile === nothing. There is no separate training entry point: add_item!/append_items! always just stage raw text into staged (never an error, trained or not — see “Staging vs. indexing” below).
  • Fitting is the library’s job, not this package’s. train_profile is a dispatcher over the two deferred specs and nothing more: one calls TextSearch.fit_profile, the other TextSearch.load_profile + TextSearch.refit_profile. This package used to fit a vocabulary and weights itself, and every line of that was a second implementation of something the library does. What delegation costs is that a fit is now the full pipeline — LSI, expansion network, lemma clustering — with no cheap variant, which is why FitFromCorpus caps its sample at max_documents and why the recommended path avoids fitting altogether.
  • create_project requires the spec for a text project and refuses nothing, and the other two kinds refuse a spec rather than ignoring one. Both directions are deliberate. The fit-from-corpus form freezes the vocabulary at the first index! call, so every term a later batch introduces is dropped from then on — nothing about the project’s behaviour afterwards distinguishes “I chose this” from “I never said”, which is exactly why it cannot be a default. In the other direction, a text model handed to an index of vectors has no reading under which it does anything, so swallowing it is how a project ends up not being the kind its author thought it was. Each spec is a type carrying its own options, so an option that only means something on one path cannot be handed to the other — the same reason this hierarchy discriminates on concrete types instead of an enum tag.
  • Query-side orthographic bridging is the library’s too. This engine used to derive and cache a variant map itself (musica → música) in a variants field. TextSearch 1.1 builds that map inside the index’s own QueryPipeline, so the field is gone and a QueryPolicy passed to ftsearch modifies how the existing map is applied rather than rebuilding it. One map, in the index that owns it.
  • Every engine shares three fields regardless of what else it carries: deleted_ids::Set{UInt32} (logically deleted document ids — UInt32 uniformly, matching the id type search results actually come back as), lock::ReadWriteLock, and search_ctx_pool::ContextPool (see below).

Staging vs. indexing: a graph and a text project have the split, the rest index on insertion

append_items!/add_item! only ever stages an item for a graph-backed dense project and for a text one; search_live/ftsearch/allknn/fft/closestpairs/bichromatic_kclosestpairs only ever see items an explicit index! call has actually processed, not merely staged.

The other two backends have no split to speak of. An exact index (ExhaustiveSearch/ ParallelExhaustiveSearch) always evaluates directly against db, and an InvertedFile builds its posting lists on insertion, so for both of them append_items! makes an item searchable immediately. index! is still defined for them, as a no-op: the same four lines — create_project, append_items!, index!, search — should mean the same thing for every kind of project, and a caller should not have to know which backends need the third one. The cost is a call that does nothing, which is the cheaper mistake; the alternative made switching a project from a graph to a brute-force scan a change to every script that fed it.

SimilaritySearch.jl’s own SearchGraph separates staging raw vectors into its database from the (expensive) graph-connection work, and this package extends that same split to the text backends, which have no such native support of their own to lean on:

  • graph-backed dense: insert_dense!(index::SearchGraph, ctx, item) = push_item!(index.db, item) only ever appends item to index.db — cheap, and durable the instant it happens (see Persistence below), but index.adj (the graph itself) is untouched. IndexEngine.index!(engine::DenseEngine{GraphBackend}) is the explicit, idempotent step that actually builds graph connections for whatever has been staged since the last call (or since creation) — it delegates to SimilaritySearch.index!(engine.index, engine.ctx), which itself only ever processes the backlog (length(engine.index)+1:length(database(engine.index))), so calling it repeatedly, or with nothing new staged, is a cheap no-op.

  • text: add_item! just pushes raw text onto engine.staged — the text-engine counterpart of index.db, since TextSearch.jl’s inverted-file types have no raw-item staging area of their own to reuse. IndexEngine.index!(engine) (no corpus argument) catches up the exact same backlog range ((engine.index === nothing ? 0 : length(engine.index))+1:length(engine.staged)), encoding each staged text (bagofwords for BM25; for the weighted engine, handing the text straight to TextInvertedFile, whose own push_item! vectorizes through the profile’s model) and push_item!ing it into the real index — with one extra twist on its first call for a project created without a profile: since neither index kind can even be constructed without a Vocabulary, that call runs the engine’s fitspec over what is staged so far and builds the real index against the resulting TextProfile, before running the same backlog loop. Every later call is a plain catch-up, identical in shape to the graph’s.

    A project created from a BaseProfile skips that entirely, and the difference is not only when the work happens: a vocabulary fitted from a sample of the first batch is frozen there, so every term appended later that it never saw is out-of-vocabulary and silently dropped. Starting from a profile fitted over the language — DefaultProfile(:es), or a BaseProfile of one you hold — is what makes an incrementally-grown text project behave.

This decouples when an item becomes durable (immediately, on append_items!) from when it becomes searchable (only after an explicit index!), so a caller controls when the expensive graph-connection/encoding cost is paid — once per big batch, on a schedule, or right before the next round of queries — instead of paying it synchronously on every single insert the way an exact or an inverted-file backend does.

Concurrency model

None of the underlying index kinds tolerates a search running concurrently with an insertion into the same index — a search reading index.adj/index.db while add_item! resizes/appends to those same arrays is exactly the kind of concurrent read-during-mutation none of them are built for. But all of them do safely support running multiple searches concurrently against the same index, since that is exactly what their own searchbatch/allknn parallel paths already rely on internally.

ReadWriteLock

Each engine’s lock is a custom reader/writer lock (built from a Threads.Condition plus a reader count), not a plain ReentrantLock: search_live/current_beamsearch take it as a read lock (any number of readers concurrently), while add_item!/index!/ mark_deleted!/calibrate! take it as a write lock (exclusive of every reader and every other writer).

A read-to-write “upgrade” on the same logical operation would deadlock (the write lock waits for the reader count to hit zero, including the reader this same call is itself holding) — so a graph backend’s minrecall-driven auto-calibrate! inside search_live is always resolved before the read lock is acquired, never nested inside it.

ContextPool

Guarding the index data isn’t enough by itself: SearchGraphContext/GenericContext/ InvertedFileContext are all mutable, reused scratch spaces (beam buffers, visited-vertices state, per-batch cost counters, …), and two concurrent searches sharing the same context object corrupt each other’s scratch state — confirmed directly by a segfault inside SearchGraph’s own beam search when two threads raced on a shared context.

ContextPool avoids both bad alternatives — sharing one context (unsafe) and allocating a fresh one on every single call (wasteful, since these contexts are non-trivial to allocate) — by handing each concurrent search_live call its own checked-out context, returned to the pool when done:

The pool grows lazily to (and then stays at) however many concurrent searches an engine has actually seen at once — never pre-allocated speculatively, never shrunk either. ctx itself (the engine’s own field) is never touched by search_live; it stays reserved for insertion, which already runs under an exclusive write_lock, so sharing it there is safe.

Persistence: one storage unit per concern

Earlier iterations of this design re-serialized the entire engine state — including the whole index — on every mutation. The current design instead gives each kind of state its own RocksDB column family (or, for a SearchGraph’s raw vectors, its own file outside RocksDB entirely — see below), so a mutation only ever rewrites the storage it actually touched.

Every RocksDB column family above lives in the same directory/connection as the project’s metadata store (Project.ProjectManager.db) — Project.open_project’s extra_cf_names keyword is how IndexEngine’s persistence layer gets its own column families listed alongside Project’s, since every column family that exists on disk must be named at opendb time on every open, not only the first. dense_vectors.mmapdb is the one exception: a plain file, alongside (not inside) the RocksDB directory – raw text has no fixed-size-record shape to exploit that way, so staged_text stays a RocksDB column family, structured exactly like sparse_db (append-only, blocks keyed by starting position) but holding raw, un-encoded text instead of already-encoded objects.

EngineStore: per-field keys, not one blob

EngineStore is a field_name::Symbol => value map, one RocksDB key per struct field. save_field!/load_field touch exactly one key; save_fields! is only used for rare, one-shot multi-field transitions (right after create_engine, or the moment a text engine’s vocabulary is first trained). A soft delete only ever rewrites :deleted_ids; a calibrate! call only ever rewrites :opt_beamsearch.

Dense vectors: a memory-mapped file, not a RocksDB column family

A graph-backed project’s raw vectors are fixed-dimension Float32 data — exactly what SimilaritySearch.MMapMatrixDatabase is for, and its own append-only counter/growth/fsync discipline already gives durable, in-order, crash-safe storage with no need for RocksDB’s batch-keying scheme, at a much cheaper per-vector read than a RocksDB point lookup (confirmed empirically against VectorDatabase/BlockMatrixDatabase in SimilaritySearch.jl’s own test suite). append_items! writes staged vectors directly into this file, at stage time — not through CallbackLog at all, unlike everything else in this section — since a vector is durable-worthy the moment it’s staged, long before any graph-linking work happens. The file (dense_vectors.mmapdb) is created lazily, on the first dense append, since its dimension isn’t known before then.

Batch size matters a lot here: MMapMatrixDatabase fsyncs once per append_items! call, never per individual vector, so the number of calls a caller makes (not the total vector count) drives wall-clock time — confirmed empirically, 200,000 128-dim vectors as one 200,000-item call took ~0.10s; the same total split into calls of 10 items took ~2.1s; one call per single item measured roughly 1000x slower than the all-at-once case. Prefer fewer, larger append_items! calls over many small ones.

Incremental adjacency/posting-list persistence: different shapes, by necessity

The graph/posting-list structure itself is the other expensive, ever-growing part, so it is never saved as a single value either. Its incremental format is driven by SimilaritySearch.CallbackLog, an observer that fires a flush(index, sp, ep) callback on every :add! event a mutating call reports — SimilaritySearch.jl standardizes every index kind’s structural events onto this one name, regardless of which entry point triggered it, and the observation channel carries nothing else, so CallbackLog never has to branch on the event itself. What does differ by index kind is the shape of what gets saved, and when this callback fires relative to append_items!.

For a SearchGraph, LOG fires before connect_reverse_links! runs for that range — so what’s captured at that instant is exactly the direct-links-only slice. This is by design, not a bug to route around: connect_reverse_links! isn’t idempotent (re-running it on an already-complete graph would duplicate reverse edges), so the on-disk format never saves reverse links at all. :graph_len (how far graph-indexing actually got, which can lag behind how many vectors are staged in dense_vectors.mmapdb if the process closed between an append_items! and its follow-up index!) lets reloading resume exactly where indexing left off, over the same, already-fully-restored .db.

The inverted-file backends — BM25InvertedFile and TextInvertedFile for a text project, InvertedFile for a sparse one — have no direct/reverse-link hazard: their own LOG only fires after a push_item! call’s mutation is fully done, so InvertedFileObjectStore simply appends the raw encoded objects just inserted (invertedfile_objects) as a new block. For a text project that LOG fires from inside an index! call’s backlog loop (see “Staging vs. indexing” above) rather than from append_items! directly — append_items! only ever writes to StagedTextStore, the raw-text counterpart of dense_vectors.mmapdb, and sparse_db’s already-encoded blocks only grow once an index! call actually catches the backlog up. For a sparse project there is no such indirection and no StagedTextStore at all: the caller handed over the encoded vector itself, so the insertion is the encoding and the block is written on append_items!. Reloading index itself still rebuilds the whole thing by replaying every saved encoded object back through the library’s own push_item! — a rebuild-by-reinsertion design, not a real on-disk posting-list format — while staged (every raw text ever staged, whether or not it’s been encoded yet) is restored separately, straight from StagedTextStore, and handed to restore_engine alongside object_blocks. This is a deliberate scaling limit, not an oversight: it’s fine up to a few million documents, since the whole corpus and the whole rebuilt index have to fit in memory and reloading costs the full original indexing time again. It is not a design for billion-document corpora, which need genuinely disk-backed, paged-on-demand posting lists.

An exact backend (ExhaustiveSearch/ParallelExhaustiveSearch) has no incremental format of its own — its on_change just flags pending_flush[], and embedded.jl saves the whole index as a single :index value right after the triggering add_item! call returns. This is acceptable for these exact, in-memory-only index kinds, which have no adjacency or posting-list structure to split apart in the first place, and index synchronously on every add_item!.

Reopening a project

graph_len can be <= length(index.db): every staged vector is always fully restored into .db (that’s durable from the moment it was staged), but only the first graph_len of them were ever graph-indexed before the project last closed — if it closed between an append_items! and its follow-up index! call, the gap is restored as staged-but-not-yet- searchable, waiting on a future index!(handle) call to catch it up, exactly as it was before closing.

restore_engine dispatches on Val(state.kind) — :dense, :sparse or :text — and each branch then reads state.backend to pick the index within that kind. Both are symbols, not Julia types, and that is what makes a saved project survive this file being rewritten: the previous shape persisted the type BM25Engine into the project’s own store, so renaming the types (which this restructuring did to every one of them) made every existing project unreadable by construction. A symbol cuts that tie, and an unrecognised one maps to an error naming the ones the reader does know instead of a MethodError about a type it has never heard of.

IndexEngine.extra_state_fields only covers the exact backends, and covers them with () — their whole index is a single :index field, so there is nothing extra to list. No other backend has such a field at all: each needs its own combination of EngineStore reads (:minrecall/:opt_beamsearch for a graph; :distance/:dimension for a sparse project; :profile/:fitspec/:distance for a text one) plus its own dedicated block-store reads (vector_blocks/load_neighbors/graph_len for a graph; object_blocks/staged for the inverted-file kinds), assembled by hand in open_project rather than driven by a generic per-kind field list.

Logging: informative output and persistence are independent

Every engine’s context carries two logging slots, and that split is what makes the independence structural instead of a convention to remember. This engine used to hand-roll it — one slot holding three backends of two different kinds, with a comment explaining which of them could affect persistence — until SimilaritySearch.jl grew the distinction itself.

  • ctx.reporters — where progress goes to be read. Always at least one InformativeLog printing a throttled status line to stderr; a log_io adds a second one writing the same line to any caller-given IO (an open file handle, or stdout/stderr). Purely informative, and it cannot be anything else: a reporter is only ever handed a message.
  • ctx.observers — what reacts to a structural change. A CallbackLog here forwards every :add! report, untouched by any throttling, to whatever on_change closure embedded.jl installed. This is the actual persistence trigger.

The two channels cannot interfere. Silencing the console is reporters=[], and persistence continues untouched; conversely no observer can be lost by turning output down, because turning output down does not reach that slot.

Soft deletes

mark_deleted! adds a document’s id to deleted_ids and nothing else — the underlying index is never touched, so no rebuild or backfill is needed. search_live reports a deleted flag per candidate instead of silently dropping deleted candidates and backfilling with the next-best live one: compensating for deletions by overfetching would have to grow with the total number of deletions, and it would hide from the caller which ids were even considered. A caller that wants k live results after filtering is expected to page for more (e.g. via a cursor over successive top-k' windows) at a layer above this one — SimilaritySearchServer, not this package.

Whole-dataset operations

allknn, fft, closestpairs, and bichromatic_kclosestpairs all run synchronously, in-process, directly against a dense project’s index — no job queue, unlike the HTTP API’s POST /api/v1/jobs/allknn. Each does real work proportional to the whole dataset (or two datasets, for the bichromatic case): allknn is every item’s own top-k neighbors at once; fft (Farthest-First-Traversal) picks k well-separated items for diverse sampling; closestpairs finds the k globally closest pairs within one project (near-duplicate/echo detection); bichromatic_kclosestpairs finds the k closest pairs between a project’s own index and a second, unindexed collection of vectors. All four require a graph-backed dense project that’s had index! run at least once — none apply to a text project.

Where this leaves SimilaritySearchServer

This package covers project lifecycle, core CRUD, calibration, and the whole-dataset operations above. Pagination policy over soft-deleted results, HTTP/CLI surfaces, job queues, and telemetry all live one layer up, in the sibling SimilaritySearchServer package, which depends on this one and is kept in sync with it as this package’s design settles.
