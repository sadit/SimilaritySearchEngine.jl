Server Manual

SimilaritySearchServer: the REST API, the job queue and the two command lines

SimilaritySearchServer provides access to SimilaritySearchEngine, the embedded engine documented in the rest of this site, through a REST API, two command lines and an asynchronous job queue. It implements no indexing logic. Storage, indexing and search are implemented in the engine. This package translates HTTP requests and command lines into engine calls, and engine results and failures into responses and exit codes.

This division determines where each subject is documented. Questions about projects, persistence, text profiles or the behavior of a search are answered in the engine’s architecture guide. The two packages are documented on one site because the interface between them is the public API of the engine, and both sides of that interface are described here.

1. What this package contains

file what it does
config.jl, cli.jl, ctl.jl TOML configuration, and the two ArgParse command lines (similarity-search, similarity-search-admin)
cli_handlers.jl, ctl_handlers.jl one function per subcommand: build, search, searchbatch, allknn, fft, neardup, hsp, closestpair, describe, rebuild, dump, load
server.jl the HTTP API (Oxygen), one EmbeddedEngine per dataset, and the request/response mapping
jobs.jl, executors.jl the job spool: an atomic directory tree (queued/, running/, completed/, failed/) of .job.toml files, dispatched as independent Julia subprocesses
tokens.jl, telemetry.jl, cursors.jl access tokens, the op_log operation history, and server-side result cursors for pagination
interactive.jl guided invocation through REPL.TerminalMenus
apps/ the three installable app entry points

The schema, the persistence layer, the index engine and project management are not part of this package. They are SimilaritySearchEngine.Schema, .Persistence, .IndexEngine and .Project.

2. How a dataset is held

The server holds one SimilaritySearchEngine.EmbeddedEngine per dataset identifier, in AppState.handles. That handle contains the two parts of a project, its RocksDB metadata store and its search engine, which keeps them consistent across a restart. reload_datasets! opens every dataset under <workdir>/datasets/ with open_project, and a reopened dataset preserves its index, its text profile, its staged items and its deletion marks.

There is no snapshot file. Earlier versions of this package wrote one JLD2 snapshot per dataset and read it on demand, because the engine did not store its own index. The engine stores it now, and a dataset is the directory that contains it.

A job that operates on an entire dataset runs as a subprocess and opens its project in read-only mode, because the serving process may hold the project open, and the RocksDB write lock is exclusive per process.

3. Kinds of project

The parameter index_kind of the API names a pair: the type of data a project holds, and the structure that indexes it:

index_kind engine backend notes
searchgraph DenseEngine SearchGraph approximate, adjusts its own parameters; the default
exhaustive_search DenseEngine ExhaustiveSearch exact, linear scan
parallel_exhaustive_search DenseEngine ParallelExhaustiveSearch exact, data-parallel
bm25_invfile FullTextEngine BM25InvertedFile BM25 scoring
invfile FullTextEngine TextInvertedFile TF-IDF cosine
sparse_invfile SparseEngine InvertedFile sparse vectors encoded by the caller; requires dimension

A text project is created with FitFromCorpus. Its vocabulary is fitted from the documents the dataset has received when index! is called for the first time. Sending a pre-computed text profile to the server is not available over HTTP.

4. REST API (base endpoints)

Control

  • GET /readyz — health.
  • GET /metrics — metrics in Prometheus format: the number of documents and of deleted records per dataset, the jobs in progress, and the counters the operation log feeds — requests per dataset and operation, distance computations, items inserted, and a histogram of request durations.

The counters cover the running process and start at zero when it starts, which is what a Prometheus counter is expected to do; simsearch_process_start_time_seconds reports when that was. They are accumulated as each request is recorded, not read back from the operation log: a collector polls every few seconds, and reading a column family that grows with every request would cost more than the requests it measures. The log remains the durable record and is read through GET /api/v1/datasets/{id}/log.

Datasets

  • POST /api/v1/datasets — creates one. Accepts id, index_kind (see above), distance, dimension, and the join-group fields join_group, holds_metadata, key.
  • DELETE /api/v1/datasets/{id} — destroys it.
  • POST /api/v1/datasets/{id}/unload and /reload — closes or reopens a dataset without restarting the server. The rebuild subcommand of the command line requires this, because the RocksDB write lock is exclusive per process.

Search and indexing

  • POST /api/v1/datasets/{id}/append — inserts items. A dense item contains vector, a text item contains text, and a sparse item contains indices and values. The fields doc_id, keywords and refs, and any other field, become the metadata of the item.
  • POST /api/v1/datasets/{id}/search — dense and sparse search, with optional filter, page_size and beamsearch_overrides.
  • POST /api/v1/datasets/{id}/ftsearch — text search.
  • POST /api/v1/datasets/{id}/fetch and GET /api/v1/datasets/{id}/exists — records by identifier, and whether an identifier exists.
  • POST /api/v1/datasets/{id}/delete — logical deletion.
  • POST /api/v1/datasets/{id}/calibrate — recall calibration for a graph-backed project.
  • POST /api/v1/search/hybrid and POST /api/v1/search/group — reciprocal rank fusion over two datasets, and a text query sent to every dataset of a join group.

An operation on one dataset is addressed under that dataset. The two queries that read more than one are under /api/v1/search/, which is the only place where a route is not about a single dataset. The earlier prefix /api/v1/simsearch/ was removed on 2026-09-13: it marked a distinction that the API stopped making.

Telemetry

  • GET /api/v1/datasets/{id}/log?offset=&limit= — the dataset’s op_log: one record per search/ftsearch/append/delete, with elapsed time and distance_evaluations.

The number of distance computations of a search is obtained from the engine, in a SimilaritySearchEngine.SearchStats instance that _run_search passes to search and to ftsearch. It is not obtained by reading a context before and after the call: a search uses a context taken from a pool of the engine, so a counter read from this package includes the work of any other search executed since. For append the second method is correct, because an insertion uses the engine’s own context under an exclusive write lock.

Asynchronous jobs

  • POST /api/v1/jobs/{kind} — enqueues a job (allknn, fft, neardup, hsp, searchbatch, closestpair, build, dump, load). Returns 202 and a job_id.
  • GET /api/v1/jobs/{job_id} and /result — the state of the job, and its output.

Authentication

Every /api/v1 endpoint requires a token when [auth] enabled is true in config.toml. /healthz, /readyz and /metrics answer without one, so a supervisor and a metrics collector work without credentials. The default is false, which is the behavior of a server that has never had authentication.

The token travels in the Authorization header, as Bearer <token> or as the bare token. A permission is operation:dataset:

operation grants includes
read the queries and the GET endpoints —
write append, delete, calibrate, job submission read
admin dataset creation and deletion, the token endpoints, job control, the operation log write and read

dataset is a dataset id or *. A route that is not about one dataset — listing datasets, the job endpoints, the token endpoints, /api/v1/search/group — requires the operation over *, so a token restricted to one dataset uses that dataset and cannot enumerate the rest. admin:* grants everything. A request without a valid token is answered 401; a valid token without the permission is answered 403, and the body names the permission that was required.

The first token is created against the working directory, because a server with authentication enabled refuses to start while no token exists, and the endpoint that creates tokens is itself behind authentication:

similarity-search add-token --user admin --permissions "admin:*" --workdir ./workdir

Later tokens are created with POST /api/v1/admin/tokens or with similarity-search-ctl add-token, which is the same endpoint. A token may carry an expires_at, an ISO 8601 timestamp that is verified when the token is created and again on every request.

5. How failures are reported

The engine raises typed errors. This package maps them by category, never by the text of the message:

engine category HTTP CLI exit code
NotFound 404 4
ConflictingState (staged backlog, untrained profile, empty project) 409 5
InvalidRequest (wrong payload, wrong dimension, bad option) 400 2
StorageFailure 500 70

Two status codes come from this package rather than from the engine: 401 when a request carries no valid token, and 403 when its token lacks the permission the route requires.

An error response contains two fields: error, the message, intended for a person, and kind, the concrete engine type, intended for a client that selects a behavior. Failures detected by a command line itself, such as a dataset directory that does not exist or an input file that cannot be read, return exit code 1. They are detected before the engine is called.

6. Configuration

config.toml (or .similarity-search-server.toml):

[paths]
workdir = "./workdir"

[server]
host = "127.0.0.1"
port = 8080

[resources]
query_threads_pct = 80
batch_threads_pct = 20

[resources] divides this server’s threads between answering queries and executing jobs. A job runs as its own process, so the reserved share is spent as a number of processes and a number of threads each: at most four jobs at once, each with its part of floor(threads × batch_threads_pct / 100), and never more than that share in total. The remaining threads stay with the server. serve prints the resulting numbers when it starts, for example at most 4 concurrent job(s), 3 thread(s) each (20.0% of this server's 64 thread(s)).

The number of threads the server itself has is the one given to Julia when it starts (julia -t auto), not a value in this file.

7. Tests

Two levels, selected with test_args=["full"] or SSE_TEST_LEVEL=full:

  • light (50 assertions, approximately 5 s): the interface with the engine. It verifies the mapping from the names used in requests to engine types, from engine errors to status codes and exit codes, and from the items of a request to engine items. No server is started and no subprocess is created. This level detects a change in the engine on the day it is made.
  • full (585 assertions, approximately 19 minutes): the end-to-end suites for the API, the jobs and the command lines. They start servers and execute subprocesses. Near the end, the run produces no output for about ten minutes, while the command-line suite waits for jobs to expire. The run has not stopped.
julia --project=server -e 'using Pkg; Pkg.develop(path="."); Pkg.test()'
julia --project=server -e 'using Pkg; Pkg.test(test_args=["full"])'
