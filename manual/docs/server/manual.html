Server Manual

SimilaritySearchServer: the REST API, the job queue and the two command lines

SimilaritySearchServer provides access to SimilaritySearchEngine, the embedded engine documented in the rest of this site, through a REST API, two command lines and an asynchronous job queue. It implements no indexing logic. Storage, indexing and search are implemented in the engine. This package translates HTTP requests and command lines into engine calls, and engine results and failures into responses and exit codes.

This division determines where each subject is documented. Questions about projects, persistence, text profiles or the behavior of a search are answered in the engine’s architecture guide. The two packages are documented on one site because the interface between them is the public API of the engine, and both sides of that interface are described here.

1. What this package contains

file what it does
config.jl, cli.jl, ctl.jl TOML configuration, and the two ArgParse command lines (similarity-search, similarity-search-admin)
cli_handlers.jl, ctl_handlers.jl one function per subcommand: build, search, searchbatch, allknn, fft, neardup, hsp, closestpair, describe, rebuild, dump, load, the follower commands and postings
server.jl the HTTP API (Oxygen), one EmbeddedEngine per dataset, and the request/response mapping
followers_api.jl the routes of followers, and the task of serve that processes the periodic followers
plugins.jl loading the plugins of [plugins], and the wire names of their key sources and kinds of follower
jobs.jl, executors.jl the job spool: an atomic directory tree (queued/, running/, completed/, failed/) of .job.toml files, dispatched as independent Julia subprocesses
tokens.jl, telemetry.jl, cursors.jl access tokens, the op_log operation history, and server-side result cursors for pagination
interactive.jl guided invocation through REPL.TerminalMenus
apps/ the three installable app entry points

Two clients of the HTTP API are in this directory and are separate packages: python/, for Python, and julia/, the Julia client, whose functions have the names of the engine’s functions.

The schema, the persistence layer, the index engine and project management are not part of this package. They are SimilaritySearchEngine.Schema, .Persistence, .IndexEngine and .Project.

2. How a dataset is held

The server holds one SimilaritySearchEngine.EmbeddedEngine per dataset identifier, in AppState.handles. That handle contains the two parts of a project, its RocksDB metadata store and its search engine, which keeps them consistent across a restart. reload_datasets! opens every dataset under <workdir>/datasets/ with open_project, and a reopened dataset preserves its index, its text profile, its staged items and its deletion marks.

There is no snapshot file. Earlier versions of this package wrote one JLD2 snapshot per dataset and read it on demand, because the engine did not store its own index. The engine stores it now, and a dataset is the directory that contains it.

A job that operates on an entire dataset runs as a subprocess and opens its project in read-only mode, because the serving process may hold the project open, and the RocksDB write lock is exclusive per process.

3. Kinds of project

The parameter index_kind of the API names a pair: the type of data a project holds, and the structure that indexes it:

index_kind engine spec notes
searchgraph DenseVectors(distance; index=Graph()) approximate, adjusts its own parameters; the default
exhaustive_search DenseVectors(distance; index=Exhaustive()) exact, linear scan
parallel_exhaustive_search DenseVectors(distance; index=Exhaustive(parallel=true)) exact, data-parallel
bm25_invfile TextDocuments(FitFromCorpus(); index=BM25()) BM25 scoring
invfile TextDocuments(FitFromCorpus(); index=VectorSpace(distance)) TF-IDF cosine
sparse_invfile SparseVectors(dimension, distance) sparse vectors encoded by the caller; requires dimension

The server builds the spec from the fields of the request with dataset_spec(index_kind, distance, dimension, storage). When the request gives no distance, a dense dataset uses SqL2, and invfile and sparse_invfile use NormCosine. BM25 scoring does not use a distance. See Project Specifications in the engine manual.

The names of distance are L2, SqL2, Cosine, NormCosine, Angle and NormAngle, in upper or lower case. L2 is computed as SqL2, which orders the results in the same way. Another name is refused with 400 and the kind InvalidOption. Until 2026-11-23 the server also listed jaccard, and a dataset created with it failed with 500. storage selects how a dense dataset stores its vectors (see “Storage of Dense Vectors”).

A text project is created with FitFromCorpus. Its vocabulary is fitted from the documents the dataset has received when index! is called for the first time. Sending a pre-computed text profile to the server is not available over HTTP.

4. REST API (base endpoints)

Every response of this API is JSON. A response that succeeded carries status; one that failed carries error and kind (section 5). The bodies below are real responses, not sketches.

Two names identify an item, everywhere and with one meaning each: doc_id is the identifier the caller gave it, which may be absent, and _id is the integer the engine assigned, which is always there. A search result, a stored record and the operation log all use them that way. Until 2026-09-14 a search result called the first id and the second doc_id, so result.doc_id and record.doc_id were different things; that is corrected, with no alias for the old names.

At the top level of a response, id is the dataset: {"status":"appended","id":"ds"}.

Control

  • GET /healthz — the process answers HTTP.
  • GET /readyz — the process is ready to serve. {"status":"ok"}.
  • GET /metrics — metrics in Prometheus text format: documents and deleted records per dataset, jobs in progress, searches running and waiting, and the counters the operation log feeds — requests per dataset and operation, distance computations, items inserted, and a histogram of request durations.

The counters cover the running process and start at zero when it starts, which is what a Prometheus counter is expected to do; simsearch_process_start_time_seconds reports when that was. They are accumulated as each request is recorded, not read back from the operation log: a collector polls every few seconds, and reading a column family that grows with every request would cost more than the requests it measures. The log remains the durable record and is read through GET /api/v1/datasets/{id}/log.

Datasets

  • POST /api/v1/datasets — creates one. Accepts id, index_kind (see section 3), distance, dimension, an optional meta_schema, edit_correction for a text dataset, partition_by for a text or dense dataset, partition_graph_min for a dense dataset with partition_by, and storage for a dense dataset. Answers 201. The fields join_group, holds_metadata and key were removed on 2026-11-10, and a request that contains one of them answers 400 (see “Searching Several Text Fields”).
  • GET /api/v1/datasets?offset=&limit= — every dataset on disk, loaded or not.
  • GET /api/v1/datasets/{id} — one of them. A dataset with followers also has followers, the status of each one (see “Followers”).
  • DELETE /api/v1/datasets/{id} — destroys it. A dataset with followers answers 409 with the kind HasFollowers: its followers are deleted first.
  • POST /api/v1/admin/datasets/{id}/unload and /reload — closes or reopens a dataset without restarting the server. The rebuild subcommand of the command line requires this, because the RocksDB write lock is exclusive per process. /reload accepts an optional body {"edit_correction": true} or false, which changes that setting and reopens the dataset with it.
POST /api/v1/datasets          {"status":"created","id":"ds"}
DELETE /api/v1/datasets/{id}   {"status":"deleted","id":"ds"}
POST .../unload                {"status":"unloaded","id":"ds"}
POST .../reload                {"status":"reloaded","id":"ds"}

GET /api/v1/datasets/{id}
{"id":"ds", "index_kind":"searchgraph", "distance":"L2",
 "created_at":"2026-09-14T19:41:57.059", "loaded":true,
 "doc_count":5, "tombstone_count":0, "tombstone_ratio":0,
 "edit_correction":false,
 "meta_schema":[{"name":"year","type":"int64"}], "partition_by":null,
 "beamsearch_baseline":{"bsize":4,"delta":1,"maxvisits":1000000},
 "storage":{"kind":"float32"}, "encoder":null}

GET /api/v1/datasets wraps a list of those objects: {"status":"ok", "datasets":[...], "total":2, "offset":0, "limit":2}. doc_count, tombstone_count, tombstone_ratio, meta_schema, partition_by, partition_graph_min, beamsearch_baseline, storage and encoder are reported for a dataset that is open; beamsearch_baseline is null for one that is not backed by a graph, meta_schema is null for one that declares nothing, and storage and encoder are null for one that is not dense. encoder is null for a dense dataset of Float32 vectors.

meta_schema declares which fields of an item’s metadata the dataset expects and what each one holds:

{"id": "papers", "index_kind": "bm25_invfile",
 "meta_schema": [{"name": "year", "type": "int64"},
                 {"name": "published", "type": "timestamp"}]}

The types are string, int64, float64, bool and timestamp. An append is refused with 400 when a declared field carries another type. Declaring is additive: a field that is not declared is stored as it arrives, and a dataset that declares nothing behaves as before. The declared fields are not indexed; what the declaration changes is that a filter compares in the declared type, so a timestamp is compared as an instant rather than as the text that stores it. The engine holds the declaration inside the project, which is why it survives a restart and travels with dump.

edit_correction applies to a text dataset (bm25_invfile or invfile). When it is true, ftsearch corrects a query token that is absent from the vocabulary to the only vocabulary token at Damerau-Levenshtein distance 1 from it. For example, Frankenstien is searched as Frankenstein. The Damerau-Levenshtein distance counts insertions, deletions, substitutions and exchanges of two adjacent letters. If two or more vocabulary tokens are at distance 1, the query token is not replaced.

The default is false because the correction has a cost. The server builds an edit index from the vocabulary each time it opens the dataset: at startup, and at each /reload. Measured on 2026-09-24 over a vocabulary of 730,320 tokens, building it took 1.2 s with 64 threads and 5.0 s with one thread, and it used 81 MiB. A query with one token absent from the vocabulary took 18.7 ms to resolve instead of 7.3 µs. A query whose tokens are all in the vocabulary is not slower.

The value is stored in descriptor.json, next to the project, and it travels with dump and load. true for a dataset that does not hold text is refused with 400, at creation and at /reload; a refused /reload leaves the dataset loaded as it was.

The command line has the same option for a batch of queries: similarity-search searchbatch --edit-correction. It does not read descriptor.json: the flag decides it for that run. On a dataset without text the command exits with code 2.

partition_by names a metadata field of a text dataset as its partition field. Each value of that field is a partition. A text search can then name one partition, and it evaluates only the items of that partition. Each result has the score that the search over the whole dataset gives it. The value of the field in an item is a non-empty string or a list of them. An item whose value is anything else is refused with 400 and the kind PayloadMismatch, and no item of that request is stored. The engine stores the field inside the project, so it is not in descriptor.json, and dump, load and rebuild keep it. partition_by on a sparse dataset is refused with 400.

On a dense dataset, a search can name one partition too (since 2026-11-18). A partition shares the vectors of the dataset and copies none.

  • A partition with fewer than partition_graph_min indexed members is searched with an exact scan of its members. The default is 4,096.
  • A larger partition of a searchgraph dataset has its own graph, which each append builds or extends. Its results are approximate, as those of the dataset’s own graph.
  • Every partition of an exact dataset (exhaustive_search, parallel_exhaustive_search) is scanned.

partition_graph_min is stored inside the project. It is refused with 400 on a dataset that is not dense, without partition_by, or when it is not an integer.

  • GET /api/v1/datasets/{id}/partitions — the partition field and the partitions, sorted by name, each with the number of items appended to it and graph, whether it has its own graph. Deleted items and items not indexed yet are counted. graph is false for every partition of a text dataset, and partition_graph_min is null for one. A dataset without a partition field answers 400.
{"status":"ok","id":"ds","partition_by":"repo","partition_graph_min":150,
 "partitions":[{"name":"otro","items":200,"graph":true},
               {"name":"tres","items":100,"graph":false}]}

The command line has similarity-search build --partition-by <field>, similarity-search build --partition-graph-min <n> for a dense dataset, and similarity-search searchbatch --partition <name>.

A partition follower (see “Followers”) divides the items in the same way, outside the project. A dataset can have several, and migrate-partitions moves the partitions of partition_by to one.

Storage of Dense Vectors

A dense dataset stores each vector in one of three forms. The field storage of POST /api/v1/datasets selects the form, and only its kind is required. The default is float32. The engine manual describes each form in Quantized Dense Indexes and Sketched Dense Indexes.

kind engine storage bytes per vector of dimension d
float32 Float32Vectors() 4 d
quantized Quantized(SQ(bits; range); rotation, keep_vectors) d × bits / 8, and 8 more with the range per_vector
sketched Sketched(hyperplanes; bits, rerank, keep_vectors, center, ...) hyperplanes × bits / 8 
{"id": "papers", "index_kind": "searchgraph", "distance": "NormCosine",
 "storage": {"kind": "quantized", "bits": 4}}

The fields of quantized:

field value default
bits 8, 4 or 2 bits per coordinate 8
range global, one range for every coordinate of every vector, or per_vector, one range for each vector global
minmax [lo, hi], the range of global, given instead of estimated null
samplesize the number of vectors the range is estimated from 4096
rotation none, qr or hadamard none
keep_vectors keep the Float32 vectors on disk next to the codes false

The fields of sketched:

field value default
hyperplanes the number of hyperplanes, a multiple of 64 256
bits 1, 2, 4 or 8 bits per hyperplane 8
rerank 0, or the number of candidates, as a multiple of k, that are evaluated again with the Float32 vectors; a value above 0 needs keep_vectors 0
keep_vectors keep the Float32 vectors on disk next to the sketches false
center subtract the mean of the fitting sample from each vector and each query false
samplesize, hsel, henc, entquantile, anchorpolicy the options of the fitting, described in the engine manual 16384, 16 × hyperplanes, 1024, 0.5, random

A field that is absent takes the default of the engine. GET /api/v1/datasets/{id} reports storage with every field, and encoder:

{"id":"vecs", "index_kind":"exhaustive_search", "distance":"NormCosine", ...,
 "storage":{"kind":"quantized", "bits":8, "range":"global", "minmax":null,
            "samplesize":4096, "rotation":"none", "keep_vectors":false},
 "encoder":{"fitted":true, "dimension":4, "min":0.0, "max":1.7000009,
            "bytes_per_vector":4, "staged":0}}
  • fitted is whether the encoder exists.
  • dimension is the dimension of the vectors, or null before the encoder exists.
  • min and max are the range of a global quantizer or of sketches of 2 to 8 bits, and null otherwise.
  • bytes_per_vector is the size of one code.
  • staged is the number of appended vectors that are not encoded yet.
  • A sketched dataset also reports bytes_on_disk_per_vector, which includes the kept vectors.

The storage and the encoder are saved inside the project, not in descriptor.json. dump, load and rebuild keep the storage, and dump and load also keep the fitted encoder.

Measurements. Measured on 2026-11-23 on SISAP 2025 ccnews (dev): 603,664 vectors of dimension 384, the distance NormCosine, an exhaustive_search dataset, and the first 1,000 otest queries. Recall@10 is the fraction of the exact 10 nearest neighbors in the results. The engine ran with 32 threads on a Xeon Silver 4216. The column searchbatch divides the time of one batch of 1,000 queries by 1,000. The column search is the time of one query, which an exact scan answers with one thread. The disk column is the whole project directory.

storage bytes per vector recall@10 searchbatch, ms search, ms disk
float32 1,536 0.999 5.36 110 1,593 MB
quantized, 8 bits 384 0.988 1.95 36 441 MB
quantized, 4 bits 192 0.909 2.06 28 249 MB
quantized, 2 bits 96 0.757 3.37 28 153 MB
sketched, the defaults (256 hyperplanes, 8 bits) 256 0.490 0.92 19 313 MB
sketched, the defaults, rerank 4, keep_vectors 256 0.734 0.86 23 1,849 MB

Encoding the 603,664 vectors took 2 to 3 s for a quantized dataset and 2 to 7 s for a sketched one.

Which storage to use. For the vectors of a language model, use quantized. On ccnews, 8 bits kept a recall@10 of 0.988 with a quarter of the bytes, and 4 bits kept 0.909 with an eighth. At the same memory, sketches gave a lower recall: 0.49 with 256 bytes per vector. A sketch is defined by distances only, so sketched takes the distances that quantized does not: Angle and NormAngle. quantized takes L2, SqL2, Cosine and NormCosine. A second evaluation (rerank) raises the recall of sketches, but it needs the Float32 vectors on disk.

Rotation and centering. Both are off by default. Whether to use them is a decision of the user, and the facts are these:

  • rotation applies to quantized. A random rotation gives every coordinate the same scale before the quantization. The coordinates of the vectors of most neural embedding models already have similar scales: on ccnews, a QR rotation changed recall@10 by less than 0.01 at every width. Use qr for vectors that are not normalized, for vectors of several models in one dataset, for features that a neural model did not produce, or when the recall on a sample of queries is clearly below that of an exact search. qr costs d² operations for each query and each inserted vector, and 4 d² bytes of storage: 4 MB at dimension 1024. hadamard costs d log d operations, and the dimension must be a power of two.
  • center applies to sketched. It subtracts the mean of the fitting sample from every vector and every query. Under L2 and SqL2 it changes no distance, because those distances do not change when every vector moves by the same amount. Under Cosine and NormCosine it changes the angles between the vectors. The vectors of a language model seldom need it. A rotation changes no distance, so sketched has no rotation.

Fitting. An append indexes its items, so the first append fits the encoder on its own vectors, on at most samplesize of them. A quantized dataset whose first request has a few vectors estimates its range from those few. Send at least samplesize vectors in the first request, 4096 with the defaults, or give minmax. A sketched dataset fits its encoder on more than 64 vectors. Before that, its vectors stay staged, encoder.staged counts them, and a search answers 409:

{"kind":"NotTrained","error":"this sketched project holds 1 staged vector(s) and no encoder: the encoder is fitted at an index! with more than 64 staged vectors, and until then the project has nothing to search"}

Distances of the results. A quantized dataset reports the distance between the query, in Float32, and the codes, which is close to the distance of the dataset. A sketched dataset without rerank reports the distance between sketches: the number of different bits at 1 bit, and the squared Euclidean distance between the codes at 2, 4 and 8 bits. That distance orders the results, and it is not the distance of the dataset. With rerank above 0, the results have the distance of the dataset.

The Float32 vectors. With keep_vectors set to false, the default, the Float32 vectors are removed once they are encoded. fetch does not return the vector of an item with any storage. rebuild encodes the kept vectors again with a new encoder. It refuses a quantized or sketched dataset without them, exits with code 2, and leaves the dataset as it was.

Errors. A storage is refused with 400 and the kind InvalidOption when its kind or one of its fields is unknown, when a value has the wrong type or is out of range, when the dataset is not dense, or when the storage does not take the distance:

{"kind":"InvalidOption","error":"the storage quantized has no field(s) bitz; it takes bits, range, minmax, samplesize, rotation, keep_vectors"}
{"kind":"InvalidOption","error":"a quantized project searches with SqL2, L2, L1, Cosine or NormCosine; Angle has no distance over codes"}

The command line takes the same object: similarity-search build --storage '{"kind": "quantized", "bits": 4}'. describe reports the distance of the dataset, storage and encoder. Its distance_stats search with the kept vectors, and they are null without them or for a sketched dataset without rerank.

Search and indexing

  • POST /api/v1/datasets/{id}/append — inserts items. A dense item contains vector, a text item contains text, and a sparse item contains indices and values. The fields doc_id, keywords and refs, and any other field, become the metadata of the item.
  • POST /api/v1/datasets/{id}/search — dense and sparse search, with optional filter, page_size, beamsearch_overrides, and partition for a dense dataset with a partition field. filter applies to the results of the partition. A partition name the dataset does not hold answers 404 with the kind UnknownPartition. partition on a dataset without a partition field, or together with beamsearch_overrides, answers 400: the overrides apply to the graph of the whole dataset.
  • POST /api/v1/datasets/{id}/ftsearch — text search. Accepts text, k, an optional filter in the format of search, and partition for a dataset with a partition field. text must be a string. A filtered text search reads the same bounded number of candidates as a filtered search. A partition name the dataset does not hold answers 404 with the kind UnknownPartition, and the message lists the closest names. partition on a dataset without a partition field answers 400.
  • POST /api/v1/datasets/{id}/fetch and GET /api/v1/datasets/{id}/exists?ids= — records by identifier, and whether an identifier exists.
  • POST /api/v1/datasets/{id}/delete — logical deletion. Takes _id, the integer a search or a fetch reported.
  • POST /api/v1/datasets/{id}/calibrate — recall calibration for a graph-backed project. Accepts minrecall, numqueries, ksearch, queries, and the shape of the tuning goal, tradeoff and transition (see the calibrate! section of the getting-started tutorial). The response reports the configuration as baseline and the recall it reaches as calibration, measured on queries that took no part in the tuning, with a 95% interval. partition calibrates the graph of one partition of a dense dataset instead. Its levels are stored apart, the response carries partition, and beamsearch_baseline of the dataset does not change. A partition without its own graph answers 400 with the kind InvalidOption, because an exact scan has nothing to calibrate.
  • POST /api/v1/search/hybrid — reciprocal rank fusion over two datasets.
POST .../append     {"status":"appended","id":"ds","inserted":5}
POST .../delete     {"status":"soft_deleted","id":"ds","_id":1}
POST .../calibrate  {"status":"calibrated","id":"ds",
                     "baseline":{"bsize":12,"delta":1.05,"maxvisits":934},
                     "calibration":{"minrecall":0.9,"recall":0.9323,"recall_lo":0.9062,

A fetch result merges the item’s metadata into the record, which is why year sits beside keywords above. In exists, id is the string that was asked about, which may be either identifier; doc_id and _id are what it resolved to, and are null when nothing did. A search over a text dataset reports a BM25 score with its sign inverted, under the name distance, which is the convention of the library: a smaller value is a closer match. A filtered search that could not fill k adds "insufficient_results":true, since it reads a bounded number of candidates before applying the filter.

An operation on one dataset is addressed under that dataset. The two queries that read more than one are under /api/v1/search/, which is the only place where a route is not about a single dataset. The earlier prefix /api/v1/simsearch/ was removed on 2026-09-13: it marked a distinction that the API stopped making.

Followers

A follower is a dataset that organizes the items of another dataset, its leader. It reads the items of the leader and does not copy them. It is stored in <workdir>/datasets/<leader>.followers/<name>/, outside the directory of the leader, and it is created and deleted without a change to the items of the leader. There are two kinds:

  • A partition follower divides the items of a text or a dense dataset into partitions, one per key. A search in one partition evaluates only the items of that partition. Each result has the score or the distance that the search over the whole dataset gives it.
  • A keyword follower indexes the keys of each item in an inverted file. It searches the items by a set of keys, and it returns the posting list of one key: the _ids of the items that hold it. The leader can be a dataset of any kind.

The source of a follower says where the keys of an item come from: keywords, refs, doc_id, or meta:<field>, a field of the metadata of the item. A key is a non-empty string. A follower cannot process an item whose source holds another value, such as a number. When the follower is created, the request answers 400 with the kind PayloadMismatch, and the follower is not created. When such an item arrives after the follower exists, the leader stores it, and the follower stays at the item before it. The append answers 200, and the status of the follower has the error. POST .../followers/{name}/sync answers the error. The architecture page describes how the engine stores and processes followers.

POST /api/v1/datasets/{id}/followers creates a follower and processes every indexed item of the leader before it answers:

{"name": "by_section", "kind": "partition", "source": "meta:section",
 "disjoint": true, "policy": "on_index"}
field values
name letters, digits, _ and -, at most 128 characters
kind partition or keyword
source keywords, refs, doc_id, or meta:<field>
disjoint a partition follower only. true (the default): an item has at most one key, and an item with several keys raises PayloadMismatch, as a value that is not a string does. false: an item belongs to the partition of each of its keys
graph_min a partition follower of a dense dataset only: the number of members from which a partition has its own graph, as partition_graph_min
distance a keyword follower only: jaccard (the default), dice, intersection or cosine_set
policy on_index (the default), on_write, manual, or {"periodic": {"seconds": 60, "items": 1000}}

A field or a value that the server does not know answers 400. A follower accepts no direct write: append and delete go to the leader. A deleted item stays in the structures of a follower, and the server removes it from each result, as it does for the leader.

The position of a follower is the last _id of the leader that it processed, and its lag is the number of indexed items of the leader after that position. A follower that lags answers with the items it has processed. The policy says when it processes the new items:

policy when
on_index inside each append, after the leader indexes the new items. The response of append comes after the follower is processed
on_write another name of on_index since 2026-11-23
manual only at POST .../followers/{name}/sync
periodic inside an append that leaves the follower items or more items behind its leader. In a task of serve, when seconds have passed since its last processing, or when its lag reaches items. The task checks every [followers] check_seconds seconds (section 6)

Before 2026-11-23, on_write processed the new items after the leader stored them and before it indexed them. A follower processes indexed items only, so a follower of a searchgraph or a text dataset processed them at the next append. A follower created with on_write keeps the name, and it processes the items as on_index.

A follower that fails during an append does not undo the write of the leader, and it does not change the response of the append. The append answers 200 with the number of items it stored. The follower stays at the item it could not process, the server writes the error to its log, and the status of the follower has error. Before 2026-11-23, the append answered the error of the follower, and a client that sent the request again stored the items twice.

The routes of a follower are under its leader. {f} is the name of a follower, or name=value for one partition, with a character that a path segment does not allow encoded with %. The permission is the one of the leader:

route permission what it does
POST /datasets/{id}/followers admin creates a follower; 201 with its status
GET /datasets/{id}/followers read the status of every follower
GET /datasets/{id}/followers/{f} read the status of one follower
DELETE /datasets/{id}/followers/{f} admin deletes a follower
POST /datasets/{id}/followers/{f}/sync write processes the new items now

POST /datasets/{id}/followers/{f}=value/search read search in one partition of a dense dataset: vector, k, filter, minrecall, page_size

All routes are under /api/v1. The searches answer in the shape of the searches of a dataset. t is the number of keys of the query that an item must hold to be a candidate; the default is 1. A posting list holds the _ids in ascending order, and limit=n returns the first n. A posting list of a frequent key in a large dataset can hold most of the items of the dataset, and it is sent in one response. There is no route that lists the keys of a keyword follower.

A status has the fields of the engine’s FollowerStatus. kind, source and policy are the text of the engine, such as PartitionFollower, MetaValue("section") and Periodic(seconds=60.0, items=nothing). stale is true when the leader was rebuilt after the follower processed its items. missing is true when the leader lists the follower and its directory does not exist. stats holds the statistics of the kind: for a partition follower, partitions, memberships, smallest, median, largest and graphs. A follower whose last processing failed, or that serve could not open, has error, the message of its last failure. GET /api/v1/datasets/{id} has followers, the status of each follower.

serve opens the followers of each dataset when it loads or reloads the dataset. A follower that cannot be opened stays closed, its status has error, and the leader stays available. DELETE /api/v1/datasets/{id} of a leader with followers answers 409 with the kind HasFollowers, and the message names each follower. Each one is deleted first.

The errors of a follower have kinds of their own:

kind status when
UnknownFollower 404 the leader has no follower with that name
UnknownPartition 404 the partition follower has no partition with that value; the message lists the closest names
PluginNotLoaded 404 the follower needs a plugin that this server has not loaded
StaleFollower 409 the leader was rebuilt after the follower processed its items; rebuild of the follower builds it again
HasFollowers 409 a leader with followers cannot be deleted

A partition follower is an alternative to partition_by. The partitions of partition_by are in the project of the dataset, and an item has one partition per value. A partition follower is outside the project, a dataset can have several, and a non-disjoint one puts an item in each partition it names. POST /api/v1/datasets/{id}/migrate-partitions moves the partitions of partition_by to a partition follower over meta:<field>, with the same partition_graph_min. disjoint has no default. After the migration the dataset has no partition field, and a search with partition answers 400 with a message that names the followers.

The command line similarity-search has the same operations on a working directory:

similarity-search follower-create --dataset demo --name kw --kind keyword --source keywords
similarity-search follower-create --dataset demo --name by_section --kind partition \
      --source meta:section [--non-disjoint] [--graph-min N] [--policy manual]
similarity-search follower-list --dataset demo
similarity-search follower-sync --dataset demo --name kw
similarity-search follower-rebuild --dataset demo --name kw
similarity-search follower-delete --dataset demo --name kw
similarity-search migrate-partitions --dataset vec --name group --disjoint true
similarity-search postings --dataset demo --follower kw --key gato [--limit N]
similarity-search searchbatch --dataset demo --queries q.jsonl --output out.jsonl --follower by_section=calle

searchbatch --follower name=value searches one partition. searchbatch --follower name of a keyword follower reads keys, and optionally t, from each query line. describe lists the followers. follower-list, postings, describe and searchbatch open the dataset read-only, so they run while a server holds it. The other commands write the dataset: when another process holds it, such as a running server, they exit with code 5 and say to use similarity-search-ctl. similarity-search-ctl has followers (the group view), follower-create, follower-sync, follower-rebuild, follower-delete and migrate-partitions, with the same arguments, and calls the routes above.

rebuild creates a new project, so the _ids of the items can change. It attaches the followers to the new project and prints the state of each one. A follower of the new project is stale until it is rebuilt, and --rebuild-followers rebuilds every one in the same command:

Rebuild completed for 'demo': 4 item(s) reindexed into ./workdir/datasets/demo
  follower demo/by_section: stale; build it again with similarity-search follower-rebuild --dataset demo --name by_section
  follower demo/kw: stale; build it again with similarity-search follower-rebuild --dataset demo --name kw

dump copies the followers to followers/ of the bundle, and manifest.json lists them. It copies them before the project. A server can append items during a dump, and this order ensures that a follower in the bundle has not processed an item that the project in the bundle does not have. load copies the followers next to the new dataset and attaches them to it. The project and its followers come from the same bundle, so the followers are not stale.

Plugins

A plugin is a Julia module that adds key sources and kinds of follower to the server. It is a .jl file or a package. A plugin that needs a program outside Julia calls it from its own code, for example with run. The code of a plugin runs in the process of the server, with the permissions of that process, and only the configuration file declares plugins.

A plugin is declared in config.toml:

[plugins.Decades]
path = "plugins/decades.jl"     # a file that defines `module Decades`, relative to this file
# package = "Decades"           # or a package of the active environment: one of the two

[plugins.Decades.settings]      # optional; passed to Decades.setup(settings)
labels = "short"

The name of the table is the name of the module, and the name of the plugin. serve loads the plugins when it starts, before it opens any dataset. For each one, it includes the file into Main or loads the package, calls the function setup of the module with the settings if the module has one, registers the module in the engine with register_plugin!, and reads the wire names that the module declares. A plugin is loaded once per process. There is no route that loads a plugin: a new plugin needs a restart of serve.

A plugin that cannot be loaded stops the start, and serve prints the reason:

Error: the plugin Decades was not loaded: the file /srv/search/plugins/decades.jl does not exist; `path` is relative to the directory of the configuration file
Correct or remove [plugins.Decades] in config.toml, and start the server again.

The module does not depend on the server. It declares its wire names with two constants, read by their names:

module Decades

using SimilaritySearchEngine
const SSE = SimilaritySearchEngine

"The decade of an integer field of `meta`: 1987 is 1980s."
struct Decade <: SSE.KeySource
    field::String
end

function SSE.keys_of(s::Decade, item::SSE.StoredItem)
    year = get(item.meta, s.field, nothing)
    year isa Integer ? string(10 * fld(year, 10), "s") : nothing
end

# Optional: the settings of [plugins.Decades.settings].
setup(settings::Dict{String,Any}) = nothing

# The wire names. Each constructor takes the options of the request.
const KEY_SOURCES = Dict{String,Function}("decade" => opts -> Decade(opts["field"]))
const FOLLOWER_KINDS = Dict{String,Function}()   # name => (source, opts) -> FollowerSpec

end

A key source is a subtype of KeySource with a method of keys_of, which returns nothing, a string or a list of strings for one item. A kind of follower is a subtype of FollowerSpec that implements the functions of the engine listed in the docstring of FollowerSpec. The architecture page describes both. The same module works in an application that uses the engine alone: it registers the module with register_plugin! and ignores the two constants.

A request names a key source or a kind of a plugin as Plugin.name. With options, it is an object with name and the options:

{"name": "by_decade", "kind": "partition",
 "source": {"name": "Decades.decade", "field": "year"}}

{"name": "counts", "kind": {"name": "Counts.key_counts", "min_count": 2},
 "source": "keywords"}

A source that starts with meta: is the engine’s, even when the name of its field has a dot. A key source of a plugin works with the kinds of the engine, and disjoint, graph_min, distance and policy keep their meaning. A kind of a plugin takes the options in the object kind, and a request that adds disjoint, graph_min or distance to it answers 400.

case status kind
the plugin is not loaded 404 PluginNotLoaded; the message names [plugins.<Plugin>] and the loaded plugins
the plugin has no such name 400 the message lists the names it has
the constructor refuses the options 400 the message of the constructor; an EngineError keeps its kind

A follower of a kind of a plugin is created, processed, rebuilt, deleted and reported as any other. Its plugin field names the plugin. The search routes and postings call the functions of the engine, which do not know a kind of a plugin, so they answer 400 with the kind UnsupportedOperation. A server that has not loaded the plugin of a follower does not open the follower: its status has open false and the error, a search answers 404 with PluginNotLoaded, and the leader stays available.

  • GET /api/v1/plugins — the plugins of this process, with the permission read over *. It lists the configuration of the server, not data.
GET /api/v1/plugins
{"status":"ok",
 "plugins":[{"name":"Decades","path":"/srv/search/plugins/decades.jl",
             "key_sources":["Decades.decade"],"follower_kinds":[]}]}

similarity-search loads the plugins of the file of --config, config.toml by default, before the commands that open a follower: follower-create, follower-sync, follower-rebuild, rebuild --rebuild-followers, and searchbatch and postings with --follower. The other commands do not load them, because loading a plugin compiles its code. A missing file is not an error; a follower that needs a plugin then fails with exit code 4, and the message names the file. follower-create takes the options of a plugin type as JSON:

similarity-search --config config.toml follower-create --dataset papers --name by_decade \
      --kind partition --source Decades.decade --source-options '{"field": "year"}'

--kind-options gives the options of a kind of a plugin in the same way. similarity-search-ctl plugins calls GET /api/v1/plugins.

Searching Several Text Fields

A record can have several text fields, for example a title and an abstract. Each field is a text dataset of its own. Each dataset has its own vocabulary, document frequencies and BM25 length statistics, so a short title is compared with the length of other titles.

  • Append each record to every field dataset with the same doc_id. Each search result carries that doc_id.
  • The client keeps the map from field name to dataset id. The server does not keep it.
  • The other metadata of the record can be stored in one of the datasets. A fetch to that dataset with the doc_ids of the results returns it.

The Python client sends one ftsearch per field and returns the results by field name:

from similarity_search import SimilaritySearchClient, AsyncSimilaritySearchClient
from similarity_search import ftsearch_fields, ftsearch_fields_async

fields = {"title": "papers_title", "abstract": "papers_abstract"}
client = SimilaritySearchClient("http://127.0.0.1:8080")
hits = ftsearch_fields(client, fields, "redes neuronales", k=5)
# {"title": [{"doc_id": ..., "_id": ..., "distance": ...}, ...], "abstract": [...]}
meta = client.fetch("papers_title", [r["doc_id"] for r in hits["abstract"]])

async with AsyncSimilaritySearchClient("http://127.0.0.1:8080") as aclient:
    hits = await ftsearch_fields_async(aclient, fields, "redes neuronales", k=5)

ftsearch_fields sends the requests one after the other. ftsearch_fields_async sends them at the same time, so it takes the time of the slowest request.

Until 2026-11-10 the server grouped field datasets with the fields join_group, key and holds_metadata, and searched the group with POST /api/v1/search/group. That route and GET /api/v1/datasets/{id}/join_group were removed. A descriptor written before the removal loses the three fields when it is read, and load ignores them in a bundle.

Vocabulary

  • GET /api/v1/datasets/{id}/vocab?scan=&sample= — what a text dataset’s vocabulary covers.
{"id":"txt", "vocsize":3, "trainsize":3, "numtokens":9, "avgdoclen":3,
 "top_tokens":[{"token":"gato","ndocs":3,"occs":3}],
 "queries":1, "query_tokens":1, "query_oov_tokens":0, "query_oov_rate":0}

With scan=true, six more fields:

{"live_tokens":9, "live_oov_tokens":0, "live_oov_rate":0,
 "live_documents_scanned":3, "live_documents_total":3, "live_sampled":false}

A vocabulary is fitted once and does not grow. The rate over the queries says the words being asked for are missing, and the rate over the documents says the words the dataset already holds are missing; the second is what rebuild corrects, by refitting the vocabulary over the documents the dataset has now.

The query counters cost nothing and are always reported. The reading over the documents is asked for with scan=true, and it is bounded: at most sample documents are read, spread evenly over the dataset, and live_sampled says whether it read all of them. The default sample takes about a second whatever the dataset’s size; sample=0 reads every document, which on a large dataset takes minutes and is better asked for offline with describe. 409 for a dataset that holds no text or was never indexed.

Telemetry

  • GET /api/v1/datasets/{id}/log?offset=&limit= — the dataset’s op_log: one record per search, ftsearch, append or delete.
{"status":"ok","total":4,"offset":0,"limit":1,
 "entries":[{"operation":"delete","timestamp":"2026-09-14T19:42:11.195",
             "details":{"index_uuid":"ds","_id":1,
                        "user":"alice","token_fingerprint":"703ffec26b6db7b1"}}]}

A search entry carries more in details: distance_name, dimension, distance_evaluations and elapsed_seconds; an append entry carries items_inserted.

user is the name on the token the request carried, and is present when that token was valid. token_fingerprint is the first eight bytes of the token’s SHA-256: enough to tell two tokens of one user apart and to match an entry against a token someone holds, and not enough to present as one. Until 2026-09-14 this field was the token itself, which put live credentials in a column family of the dataset and in every dump of it. The endpoint still requires admin, because the log says who did what, which is an audit surface rather than a reading of the dataset.

The number of distance computations of a search is obtained from the engine, in a SimilaritySearchEngine.SearchStats instance that _run_search passes to search and to ftsearch. It is not obtained by reading a context before and after the call: a search uses a context taken from a pool of the engine, so a counter read from this package includes the work of any other search executed since. For append the second method is correct, because an insertion uses the engine’s own context under an exclusive write lock.

Asynchronous jobs

  • POST /api/v1/jobs/{kind} — enqueues a job (allknn, fft, neardup, hsp, searchbatch, closestpair, build, dump, load). Answers 202.
  • GET /api/v1/jobs?offset=&limit=, GET /api/v1/jobs/{job_id} and /result — the jobs, the state of one, and its output.
  • POST /api/v1/jobs/{job_id}/block, /resume, /kill, and DELETE /api/v1/jobs/{job_id}.
  • POST /api/v1/admin/jobs/gc — removes the jobs and cursors that have expired.
POST /api/v1/jobs/allknn  [202]   {"status":"accepted","job_id":"fe3198116091f825"}

GET /api/v1/jobs
{"status":"ok","total":1,"offset":0,"limit":1,
 "jobs":[{"id":"fe3198116091f825","kind":"allknn","status":"queued"}]}

POST /api/v1/admin/jobs/gc
{"status":"ok","jobs_purged":[],"cursors_purged":[],"cursors_expired":[]}

A job’s state is queued, running, blocked, completed or failed. GET /api/v1/jobs/{job_id}/result streams the file the job wrote, except for dump, whose result is a directory: for that one it answers {"bundle_dir": ..., "manifest": {...}}.

The result of allknn has one line per item: {"id", "neighbors", "dists"}. The result of fft is one object with centers, assign, dists, covering, separation, costdists and costblocks. The result of neardup has centers, assign, dists, duplicate_count, covering, epsilon, costdists and costblocks. The cost fields of both and the covering and epsilon of neardup were added on 2026-11-19, so that a client can build the engine’s result types from them.

The record of a failed job (GET /api/v1/jobs/{job_id}) has error and, since 2026-11-19, exit_code: the exit status of the job’s process. The command line exits with a code per category of engine error (section 5), so exit_code tells a client why the job failed. The message of the engine error is in the output of the process on the server, which the API does not return.

Tokens

  • POST /api/v1/admin/tokens — creates one. Accepts user, permissions and an optional expires_at.
  • GET /api/v1/admin/tokens — every token stored, expired or not.
  • DELETE /api/v1/admin/tokens/{token} — revokes one.
  • POST /api/v1/admin/tokens/prune — removes the expired ones.
POST /api/v1/admin/tokens  [201]
{"status":"created","token":"703ffec26b6db7b1...","permissions":["read:*"]}

GET /api/v1/admin/tokens
{"status":"ok",
 "tokens":[{"token":"703ffec26b6db7b1...","user":"alice","permissions":["read:*"],
            "created_at":"2026-09-14T19:42:20.595","expires_at":null}]}

The token string is returned once, when it is created. GET /api/v1/admin/tokens is an audit listing and reports them in full, which is why it requires admin.

Authentication

Every /api/v1 endpoint requires a token when [auth] enabled is true in config.toml. /healthz, /readyz and /metrics answer without one, so a supervisor and a metrics collector work without credentials. The default is false, which is the behavior of a server that has never had authentication.

The token travels in the Authorization header, as Bearer <token> or as the bare token. A permission is operation:dataset:

operation grants includes
read the queries and the GET endpoints —
write append, delete, calibrate, job submission read
admin dataset creation and deletion, the token endpoints, job control, the operation log write and read

dataset is a dataset id or *. A route that is not about one dataset — listing datasets, the job endpoints, the token endpoints — requires the operation over *, so a token restricted to one dataset uses that dataset and cannot enumerate the rest. admin:* grants everything. A request without a valid token is answered 401; a valid token without the permission is answered 403, and the body names the permission that was required.

The first token is created against the working directory, because a server with authentication enabled refuses to start while no token exists, and the endpoint that creates tokens is itself behind authentication:

similarity-search add-token --user admin --permissions "admin:*" --workdir ./workdir

Later tokens are created with POST /api/v1/admin/tokens or with similarity-search-ctl add-token, which is the same endpoint. A token may carry an expires_at, an ISO 8601 timestamp that is verified when the token is created and again on every request.

5. How failures are reported

The engine raises typed errors. This package maps them by category, never by the text of the message:

engine category HTTP CLI exit code
NotFound 404 4
ConflictingState (staged backlog, untrained profile, empty project) 409 5
InvalidRequest (wrong payload, wrong dimension, bad option) 400 2
StorageFailure 500 70

Two status codes come from this package rather than from the engine: 401 when a request carries no valid token, and 403 when its token lacks the permission the route requires.

An error response contains two fields: error, the message, intended for a person, and kind, the concrete engine type, intended for a client that selects a behavior. Failures detected by a command line itself, such as a dataset directory that does not exist or an input file that cannot be read, return exit code 1. They are detected before the engine is called.

6. Configuration

config.toml (or .similarity-search-server.toml):

[paths]
workdir = "./workdir"

[server]
host = "127.0.0.1"
port = 8080

[resources]
query_threads_pct = 80
batch_threads_pct = 20
max_concurrent_queries = 0

[followers]
check_seconds = 10

check_seconds is how often the task of serve looks for periodic followers to process (see “Followers”). The section [plugins] declares the plugins that serve loads when it starts (see “Plugins”). A follower with {"periodic": {"seconds": 60}} is therefore processed between 60 and 70 seconds after its last processing. A value that is not a positive number is replaced by the default, 10.

max_concurrent_queries bounds how many searches run at once. 0 derives it from the split below: the threads that job execution did not reserve. A request that arrives when every slot is taken waits for one; it is not refused, because a caller that asked for a search wants the search. /metrics reports simsearch_queries_running, simsearch_queries_waiting, simsearch_query_slots and simsearch_query_wait_seconds_total, which is what says whether the bound is ever reached.

The bound exists because unbounded concurrency buys no throughput and does cost memory. Past the number of threads, more concurrent searches share the same cores and each one gets slower; and every concurrent search holds a context from the engine’s pool, which grows to the highest concurrency ever reached and does not shrink.

The same split governs the work that runs inside this process rather than in a job. Indexing and calibration divide their work into batches, one task each, and the engine takes the batch count from the number of threads; this server caps it at the share reserved for batch work, so that an append that triggers index! does not spread over the threads answering queries. A job needs no such cap: it is a subprocess started with its share in JULIA_NUM_THREADS. serve prints both numbers when it starts. PLAN.md §2 proposed a request collector for this: a channel and a pool of worker tasks that every search would pass through. This is the bound without that structure, and the measurements a collector would be justified by are the ones above.

[resources] divides this server’s threads between answering queries and executing jobs. A job runs as its own process, so the reserved share is spent as a number of processes and a number of threads each: at most four jobs at once, each with its part of floor(threads × batch_threads_pct / 100), and never more than that share in total. The remaining threads stay with the server. serve prints the resulting numbers when it starts, for example at most 4 concurrent job(s), 3 thread(s) each (20.0% of this server's 64 thread(s)).

The number of threads the server itself has is the one given to Julia when it starts (julia -t auto), not a value in this file.

7. Tests

The suite has two levels. A run can also select some of its files.

  • light (321 assertions, approximately 28 s, measured on 2026-11-23): the interface with the engine. It verifies the mapping from the names used in requests to engine types, from engine errors to status codes and exit codes, and from the items of a request to engine items. It also verifies that the Julia client has every error type of the engine. No server is started and no subprocess is created. This level detects a change in the engine on the day it is made.
  • full (1,372 assertions, approximately 39 minutes, measured on 2026-11-23): the end-to-end suites for the API, the jobs, the command lines and the Julia client. They start servers and execute subprocesses. Near the end, the run produces no output for about ten minutes, while the command-line suite waits for jobs to expire. The run has not stopped.
julia --project=server -e 'using Pkg; Pkg.develop(path="."); Pkg.test()'
julia --project=server -e 'using Pkg; Pkg.test(test_args=["full"])'

Each test file has a name and a list of tags. The table TEST_FILES in server/test/runtests.jl lists them. The names are config, boundary, dispatcher, e2e, api/01 to api/20 and cli/01 to cli/08. Examples of tags are jobs, cursors, client, partitions, followers, plugins, storage, auth and cli. A run that receives names or tags includes only the files that match one of them. The word light adds the files of the light level.

julia --project=server -e 'using Pkg; Pkg.test(test_args=["jobs", "client"])'
julia --project=server -e 'using Pkg; Pkg.test(test_args=["light", "api/17"])'
SSE_TEST_SELECT="api/13 api/17" julia --project=server -e 'using Pkg; Pkg.test()'

A name or tag that matches no file stops the run with an error, which lists the valid names and tags. Each file creates its own datasets, so a file can run without the files before it. The engine’s suite uses the same selection: its files are dense, text, persistence, text_partitions and others, listed in test/runtests.jl.
