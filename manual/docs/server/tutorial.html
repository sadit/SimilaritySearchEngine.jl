Server Tutorial

From an empty working directory to a query over HTTP, an asynchronous job, and the equivalent command line

This tutorial starts the server, creates a dataset, indexes documents, searches them, and executes an asynchronous job. It assumes a local copy of this repository. SimilaritySearchServer is the package in server/, and the engine it uses is the package at the root, whose tutorial is Getting started.

Every operation below is performed over HTTP or from a command line, and none of them is implemented in this package: each endpoint translates one engine call. Reading both tutorials together shows which part performs each operation.

Julia 1.12 or later is required.

Step 1: Set up the environment

The server uses the engine from this repository, so the engine is added by path once:

julia --project=server -e 'using Pkg; Pkg.develop(path="."); Pkg.instantiate()'

Step 2: Start the server

julia --project=server -t auto -m SimilaritySearchServer serve

On its first execution, the server writes a default configuration and accepts connections on http://127.0.0.1:8080. Every dataset is stored under <workdir>/datasets/, and the server opens all of them when it starts, so a restart preserves their contents.

The three applications (similarity-search, similarity-search-admin, similarity-search-serve) can be installed into ~/.julia/bin, so that Julia does not have to be invoked explicitly:

julia -e 'using Pkg; Pkg.Apps.develop(path="server")'

Step 3: Create a dataset and index documents

curl -s -X POST localhost:8080/api/v1/datasets \
     -H 'Content-Type: application/json' \
     -d '{"id": "demo", "index_kind": "bm25_invfile"}'

curl -s -X POST localhost:8080/api/v1/datasets/demo/append \
     -H 'Content-Type: application/json' \
     -d '{"items": [
           {"doc_id": "d1", "text": "el gato duerme sobre el tejado", "keywords": ["gato"],
            "section": "casa"},
           {"doc_id": "d2", "text": "un perro ladra en la calle", "keywords": ["perro"],
            "year": 2024, "section": "calle"},
           {"doc_id": "d3", "text": "el gato y el perro juegan en la calle",
            "keywords": ["gato", "perro"], "section": "calle"}
         ]}'

index_kind names the type of data the project holds and the structure that indexes it: searchgraph for dense vectors, which is the default; bm25_invfile or invfile for text; and sparse_invfile for sparse vectors encoded by the caller, which also requires dimension. Any field other than doc_id, keywords, refs, text, vector, indices and values becomes metadata of the item, such as year and section in the example above.

The insertion indexes the documents, so they can be searched when the call returns.

Step 4: Search

curl -s -X POST localhost:8080/api/v1/datasets/demo/ftsearch \
     -H 'Content-Type: application/json' \
     -d '{"text": "gato tejado", "k": 5}'

A dense project uses /api/v1/datasets/{id}/search, which receives a vector and accepts a metadata filter:

{"vector": [0.1, 0.2, 0.3], "k": 10, "filter": {"year": {"$gte": 2024}}}

A filtered search reads a limited number of candidates before applying the filter, so it can return fewer than k results. The response reports this condition in the field insufficient_results.

A search answers its k results in one response. k is at most max_k of the dataset, 100 by default. A dataset that needs more is created with "max_k": 1000 in Step 3, and the server manual describes how to change it later. A large response is compressed with gzip when the request accepts it: curl --compressed asks for it and decompresses it.

Step 5: Read failures

Failures are typed, and the status code identifies the class of the failure without the message being read:

status meaning example
400 the request cannot be executed as written a dense vector sent to a text project
404 an object named in the request does not exist an unknown dataset identifier
409 the project is not in a state that allows the request a job over the entire dataset while items are staged
500 the stored data could not be read —

The body contains error, the message, and kind, the concrete error type of the engine, so that a client can select a behavior from kind without comparing text.

Step 6: Run a heavy job

An operation that reads the entire collection is executed as a job. The HTTP call enqueues the job and returns immediately, and a dispatcher executes it in a separate Julia subprocess.

JOB=$(curl -s -X POST localhost:8080/api/v1/jobs/allknn \
      -H 'Content-Type: application/json' \
      -d '{"dataset": "demo", "k": 5}' | jq -r .job_id)

curl -s localhost:8080/api/v1/jobs/$JOB          # queued | running | completed | failed
curl -s localhost:8080/api/v1/jobs/$JOB/result   # once completed

A job opens its dataset in read-only mode, so it can run while the server continues to answer queries on that dataset.

Step 7: The same thing from the command line

Every operation is also available as a subcommand, applied to a working directory instead of a URL:

julia --project=server -m SimilaritySearchServer build \
      --dataset demo_cli --input corpus.jsonl --index-kind bm25_invfile --workdir ./workdir

julia --project=server -m SimilaritySearchServer describe --dataset demo_cli --workdir ./workdir

The exit codes of the command line correspond to the status codes above: 2 for an invalid request, 4 for an object that does not exist, 5 for a conflicting state, and 70 for a storage failure. Code 1 is reserved for failures detected by the command itself, such as a dataset that does not exist or an input file that cannot be read. A script can select a branch from these codes without reading the output.

Step 8: The Python client

cd server/python
pip install -r requirements.txt
export PYTHONPATH=$(pwd)
from similarity_search.client import SimilaritySearchClient
from similarity_search.jobs import run_job

client = SimilaritySearchClient("http://127.0.0.1:8080")
print(client.readyz())                      # {'status': 'ok'}

ds_id = client.create_dataset()
result = run_job(client, kind="allknn", command=["--dataset", ds_id, "--k", "5"])

stress_client.py executes the same sequence under concurrent load:

python stress_client.py --jobs 3

Step 9: Store dense vectors in fewer bytes

A dense dataset stores Float32 vectors by default: 4 bytes per coordinate. With storage, it stores the codes of a scalar quantizer instead. At 8 bits a vector takes a quarter of the bytes:

curl -s -X POST localhost:8080/api/v1/datasets \
     -H 'Content-Type: application/json' \
     -d '{"id": "vecs", "index_kind": "exhaustive_search", "distance": "NormCosine",
          "storage": {"kind": "quantized", "bits": 8}}'

curl -s -X POST localhost:8080/api/v1/datasets/vecs/append \
     -H 'Content-Type: application/json' \
     -d '{"items": [
           {"doc_id": "v1", "vector": [1.0, 0.0, 0.0, 0.0]},
           {"doc_id": "v2", "vector": [0.8, 0.6, 0.0, 0.0]},
           {"doc_id": "v3", "vector": [0.0, 1.0, 0.0, 0.0]},
           {"doc_id": "v4", "vector": [0.0, 0.0, 0.6, 0.8]}
         ]}'

curl -s -X POST localhost:8080/api/v1/datasets/vecs/search \
     -H 'Content-Type: application/json' \
     -d '{"vector": [0.9, 0.1, 0.0, 0.0], "k": 2}'

The search returns v1 at distance 0.09999955 and v2 at 0.21999598. The exact distances are 0.1 and 0.22: the codes give distances close to those of the Float32 vectors.

The first append fits the encoder on its own vectors, here 4 of them. A real dataset sends at least 4096 vectors in its first request, which is the default samplesize of the quantizer. GET /api/v1/datasets/vecs reports the storage with every field, and the encoder:

"storage": {"kind": "quantized", "bits": 8, "range": "global", "minmax": null,
            "samplesize": 4096, "rotation": "none", "keep_vectors": false},
"encoder": {"fitted": true, "dimension": 4, "min": 0.0, "max": 1.7000009,
            "bytes_per_vector": 4, "staged": 0}

With keep_vectors set to false, the default, the Float32 vectors are removed once they are encoded. The server manual describes the other fields, the sketches ("kind": "sketched"), and the recall of each storage on a collection of 603,664 vectors. The command line takes the same object: build --storage '{"kind": "quantized", "bits": 4}'.

Step 10: Organize the items with followers

A follower reads the items of a dataset and organizes them by keys. A partition follower restricts a search to the items with one key. Here the key is the metadata field section:

curl -s -X POST localhost:8080/api/v1/datasets/demo/followers \
     -H 'Content-Type: application/json' \
     -d '{"name": "by_section", "kind": "partition", "source": "meta:section"}'

curl -s -X POST localhost:8080/api/v1/datasets/demo/followers/by_section=calle/ftsearch \
     -H 'Content-Type: application/json' \
     -d '{"text": "gato", "k": 5}'

The search returns d3 only. d1 also contains gato, but its section is casa.

A keyword follower indexes the keywords of each item:

curl -s -X POST localhost:8080/api/v1/datasets/demo/followers \
     -H 'Content-Type: application/json' \
     -d '{"name": "kw", "kind": "keyword", "source": "keywords"}'

curl -s -X POST localhost:8080/api/v1/datasets/demo/followers/kw/search \
     -H 'Content-Type: application/json' \
     -d '{"keys": ["gato", "perro"], "k": 5}'

curl -s 'localhost:8080/api/v1/datasets/demo/followers/kw/postings?key=gato'

The search ranks d3 first, at Jaccard distance 0, because it holds both keys. d1 and d2 follow at distance 0.5. postings returns [1, 3], the _ids of the items that hold gato.

Each append to demo processes both followers before it answers. GET /api/v1/datasets/demo/followers reports the position and the lag of each one. A follower that cannot process an item does not change the answer of the append: the leader stores the item, the append answers 200, and the status of the follower has error. For example, an item whose section is a number is not a key of by_section. A dataset with followers cannot be deleted until its followers are deleted. The server manual describes the policies, the routes and the command lines.

Step 11: Add a key source with a plugin

The keys of a follower come from keywords, refs, doc_id or a field of meta. A plugin adds other key sources. A plugin is a Julia module. This one makes the decade of the field year a key. Save it as plugins/decades.jl, in the directory of config.toml:

module Decades

using SimilaritySearchEngine
const SSE = SimilaritySearchEngine

"The decade of an integer field of `meta`: 1987 is 1980s."
struct Decade <: SSE.KeySource
    field::String
end

function SSE.keys_of(s::Decade, item::SSE.StoredItem)
    year = get(item.meta, s.field, nothing)
    year isa Integer ? string(10 * fld(year, 10), "s") : nothing
end

const KEY_SOURCES = Dict{String,Function}("decade" => opts -> Decade(opts["field"]))

end

Declare it in config.toml, then stop the server and start it again:

[plugins.Decades]
path = "plugins/decades.jl"

The server loads the plugin before it opens the datasets, and GET /api/v1/plugins lists it. A request names the key source as Decades.decade, with its options in an object:

curl -s -X POST localhost:8080/api/v1/datasets/demo/followers \
     -H 'Content-Type: application/json' \
     -d '{"name": "by_decade", "kind": "partition",
          "source": {"name": "Decades.decade", "field": "year"}}'

curl -s localhost:8080/api/v1/datasets/demo/followers/by_decade/partitions

The only partition is 2020s, with one item: d2 has the year 2024, and d1 and d3 have no year, so they have no key. A plugin that cannot be loaded stops the start of the server, and the message names the plugin. The server manual describes the plugins, their kinds of follower and the command lines.

Step 12: Require a token

Everything above answered without credentials, which is the default. To require a token on every /api/v1 endpoint, create the first token against the working directory and enable authentication:

similarity-search add-token --user admin --permissions "admin:*" --workdir ./workdir
[auth]
enabled = true

The command prints the token once. A server started with enabled = true and no token refuses to start, because no request could be answered. From then on, each request carries it:

curl -s -H "Authorization: Bearer $TOKEN" \
     -X POST localhost:8080/api/v1/datasets/demo/ftsearch \
     -H 'Content-Type: application/json' \
     -d '{"text": "gato tejado", "k": 5}'

A permission is operation:dataset, with read, write or admin as the operation and a dataset id or * as the scope. A token for an ingestion process is --permissions "write:demo", which also reads demo and reaches nothing else. /healthz, /readyz and /metrics keep answering without a token. See the server manual for the complete table.
