Server Tutorial

From an empty working directory to a query over HTTP, an asynchronous job, and the equivalent command line

This tutorial starts the server, creates a dataset, indexes documents, searches them, and executes an asynchronous job. It assumes a local copy of this repository. SimilaritySearchServer is the package in server/, and the engine it uses is the package at the root, whose tutorial is Getting started.

Every operation below is performed over HTTP or from a command line, and none of them is implemented in this package: each endpoint translates one engine call. Reading both tutorials together shows which part performs each operation.

Julia 1.12 or later is required.

Step 1: Set up the environment

The server uses the engine from this repository, so the engine is added by path once:

julia --project=server -e 'using Pkg; Pkg.develop(path="."); Pkg.instantiate()'

Step 2: Start the server

julia --project=server -t auto -m SimilaritySearchServer serve

On its first execution, the server writes a default configuration and accepts connections on http://127.0.0.1:8080. Every dataset is stored under <workdir>/datasets/, and the server opens all of them when it starts, so a restart preserves their contents.

The three applications (similarity-search, similarity-search-admin, similarity-search-serve) can be installed into ~/.julia/bin, so that Julia does not have to be invoked explicitly:

julia -e 'using Pkg; Pkg.Apps.develop(path="server")'

Step 3: Create a dataset and index documents

curl -s -X POST localhost:8080/api/v1/datasets \
     -H 'Content-Type: application/json' \
     -d '{"id": "demo", "index_kind": "bm25_invfile"}'

curl -s -X POST localhost:8080/api/v1/simsearch/demo/append \
     -H 'Content-Type: application/json' \
     -d '{"items": [
           {"doc_id": "d1", "text": "el gato duerme sobre el tejado", "keywords": ["gato"]},
           {"doc_id": "d2", "text": "un perro ladra en la calle", "year": 2024}
         ]}'

index_kind names the type of data the project holds and the structure that indexes it: searchgraph for dense vectors, which is the default; bm25_invfile or invfile for text; and sparse_invfile for sparse vectors encoded by the caller, which also requires dimension. Any field other than doc_id, keywords, refs, text, vector, indices and values becomes metadata of the item, such as year in the example above.

The insertion indexes the documents, so they can be searched when the call returns.

Step 4: Search

curl -s -X POST localhost:8080/api/v1/simsearch/demo/ftsearch \
     -H 'Content-Type: application/json' \
     -d '{"text": "gato tejado", "k": 5}'

A dense project uses /search, which receives a vector and accepts a metadata filter:

{"vector": [0.1, 0.2, 0.3], "k": 10, "filter": {"year": {"$gte": 2024}}}

A filtered search reads a limited number of candidates before applying the filter, so it can return fewer than k results. The response reports this condition in the field insufficient_results.

Step 5: Read failures

Failures are typed, and the status code identifies the class of the failure without the message being read:

status meaning example
400 the request cannot be executed as written a dense vector sent to a text project
404 an object named in the request does not exist an unknown dataset identifier
409 the project is not in a state that allows the request a job over the entire dataset while items are staged
500 the stored data could not be read —

The body contains error, the message, and kind, the concrete error type of the engine, so that a client can select a behavior from kind without comparing text.

Step 6: Run a heavy job

An operation that reads the entire collection is executed as a job. The HTTP call enqueues the job and returns immediately, and a dispatcher executes it in a separate Julia subprocess.

JOB=$(curl -s -X POST localhost:8080/api/v1/jobs/allknn \
      -H 'Content-Type: application/json' \
      -d '{"dataset": "demo", "k": 5}' | jq -r .job_id)

curl -s localhost:8080/api/v1/jobs/$JOB          # queued | running | completed | failed
curl -s localhost:8080/api/v1/jobs/$JOB/result   # once completed

A job opens its dataset in read-only mode, so it can run while the server continues to answer queries on that dataset.

Step 7: The same thing from the command line

Every operation is also available as a subcommand, applied to a working directory instead of a URL:

julia --project=server -m SimilaritySearchServer build \
      --dataset demo_cli --input corpus.jsonl --index-kind bm25_invfile --workdir ./workdir

julia --project=server -m SimilaritySearchServer describe --dataset demo_cli --workdir ./workdir

The exit codes of the command line correspond to the status codes above: 2 for an invalid request, 4 for an object that does not exist, 5 for a conflicting state, and 70 for a storage failure. Code 1 is reserved for failures detected by the command itself, such as a dataset that does not exist or an input file that cannot be read. A script can select a branch from these codes without reading the output.

Step 8: The Python client

cd server/python
pip install -r requirements.txt
export PYTHONPATH=$(pwd)
from similarity_search.client import SimilaritySearchClient
from similarity_search.jobs import run_job

client = SimilaritySearchClient("http://127.0.0.1:8080")
print(client.readyz())                      # {'status': 'ok'}

ds_id = client.create_dataset()
result = run_job(client, kind="allknn", command=["--dataset", ds_id, "--k", "5"])

stress_client.py executes the same sequence under concurrent load:

python stress_client.py --jobs 3
