Julia Client

SimilaritySearchClient: the engine’s functions over the HTTP API of a remote server

SimilaritySearchClient is a Julia package in server/julia/ of this repository. It sends requests to the HTTP API of a running similarity-search-serve process. It depends on HTTP.jl and JSON3 only. It does not load the engine, SimilaritySearch, TextSearch or RocksDB, so it installs on a computer that has none of them.

The functions have the names, the arguments and the result types of the engine’s functions. A script written for the engine runs against a remote server when it opens its project with a Connection instead of a directory. Section 3 lists the differences.

1. Installation

The package is not registered. Add it from a copy of this repository, or from the repository URL with its subdirectory:

using Pkg
Pkg.develop(path="server/julia")
# or
Pkg.add(url="https://github.com/sadit/SimilaritySearchEngine.jl", subdir="server/julia")

2. Use

using SimilaritySearchClient

conn = Connection("http://127.0.0.1:8080")             # token="..." if the server requires one
h = create_project(conn, "papers"; index_type="searchgraph", partition_by="repo")
append_items!(h, [DenseItem(v; doc_id="p$i", meta=Dict("repo" => r))
                  for (i, (v, r)) in enumerate(zip(vectors, repos))])

search(h, q, 10)                                       # Vector{SearchResult}
search(h, q, 10; partition="repo-a")                   # one partition
search(h, q, 10; filter=Dict("year" => Dict("gte" => 2020)))
search(h, queries, 10)                                 # one inner vector per query
fetch_items(h, ["p1", "p2"])                           # Vector{StoredItem}
exists(h, ["p1", 3])                                   # Vector{ExistsResult}
delete_item!(h, 3)
calibrate!(h; levels=0.9)                              # Vector{CalibrationLevel}, one element
partitions(h)                                          # (name, items, graph) per partition

t = create_project(conn, "papers_text"; index_type="bm25_invfile")
append_items!(t, [TextItem(s; doc_id="p$i") for (i, s) in enumerate(texts)])
ftsearch(t, "redes neuronales", 5)
hybrid_search(h, t; vector=q, text="redes neuronales", k=5)

open_project(conn, "papers") returns the handle of a dataset that already exists. list_projects(conn) returns the ids of the datasets of the server. project_info(h) returns the descriptor of a dataset. delete_project!(h) deletes a dataset.

The index types are searchgraph, exhaustive_search, parallel_exhaustive_search, bm25_invfile, invfile and sparse_invfile. Section 3 of the server manual describes them. A keyword of create_project that is nothing is not sent, and the server applies its own default.

3. Differences with the Engine

The client sends each call to the server. The server does not accept every argument of the engine, and it does not return every field. The differences are these:

function in the engine in the client
append_items! appends; index! indexes appends and indexes; index! does nothing
search, ftsearch filter is a (record, meta) -> Bool function filter is a filter object of the server, such as Dict("year" => Dict("gte" => 2020))
search, ftsearch minrecall, candidates, stats not accepted
search, ftsearch a deleted item is returned with deleted=true the server does not return deleted items
search with several queries one parallel pass under the write lock one request per query, at most ntasks at a time
search beamsearch_overrides, for example (bsize=64,), as in the HTTP API
ftsearch a string or a list of tokens a string
fetch_items payload is the vector or the text payload is nothing
calibrate! several levels in one call one level per call
close_project! closes the RocksDB database does nothing
allknn, fft, neardup run in the calling process run as a job on the server (section 5)
fft start and verbose keywords not accepted

A filtered search on the server reads max(5k, k+20) candidates before it applies the filter, so a result can have fewer than k items.

4. Errors

The client raises the error types of the engine, with the same names and the same four categories: InvalidRequest, NotFound, ConflictingState and StorageFailure. A script that catches NotFound works the same against an embedded project and against a remote one.

try
    search(h, q, 10; partition="repo-x")
catch e
    e isa UnknownPartition || rethrow()
    println(e.msg)                # the message lists the closest partition names
end

The server sends the name of the engine’s type in the kind field of its error responses, and the client raises the type with that name. Every type has two fields: status, the HTTP status, and msg, the message of the server. A response without a kind raises the generic type of its category:

status type category
400 RequestRejected InvalidRequest
404 ResourceNotFound, for example a dataset that does not exist NotFound
409 StateConflict ConflictingState
401, 403 Unauthenticated, Forbidden AccessDenied
500 ServerFailure none
other UnexpectedResponse none

All of them are subtypes of RemoteError. A connection that fails, for example because no server listens on the address, raises the exception of HTTP.jl.

The server’s test suite checks that the client has a type for every error type of the engine, in the same category. A new error type in the engine makes that test fail until the client has it.

5. Jobs

allknn, fft and neardup have the arguments and the result types of the engine: a Vector{KnnRow}, a CenterSelectionResult and a NearDupResult. On the server, each one runs as a job: a separate Julia process. The call submits the job, asks for its state every poll_interval seconds (1 by default), and reads its result when it completes. The call takes at least the time that the server needs to start a Julia process.

rows = allknn(h; k=16)                         # Vector{KnnRow}
r = fft(h, 100)                                # CenterSelectionResult
d = neardup(h, 0.05)                           # NearDupResult

# Several jobs at the same time, one task each.
t1 = @async allknn(h1; k=16)
t2 = @async allknn(h2; k=16)
rows1, rows2 = fetch(t1), fetch(t2)

A job that fails raises JobFailed. Its exit_code is the exit status of the job’s process, and its category is the engine error category that this status names: 2 is InvalidRequest, 4 is NotFound, 5 is ConflictingState and 70 is StorageFailure. Other statuses have no category; 1 is a dataset directory that does not exist. For example, fft on a text dataset fails with exit_code == 2 and category === InvalidRequest. The message of the engine error stays in the output of the process on the server.

dump_project(h) writes a copy of the dataset to a bundle directory on the server, and load_project(conn, bundle_dir, "copy") creates a dataset from it and loads it. The bundle is not sent over HTTP: bundle_dir is a path on the server’s file system. load_project needs the admin permission.

The functions that work with any job are these:

function what it does
submit_job(conn, kind; params...) submits a job, for example submit_job(conn, "hsp"; dataset="papers", queries="/data/q.jsonl"), and returns its id
wait_job(conn, id; poll_interval, timeout) waits for the job and returns its record; raises JobFailed, or JobTimeout after timeout seconds
job_info(conn, id) the state of the job (:queued, :running, :blocked, :completed, :failed) and its record
job_result(conn, id) the result of a completed job, as the text the server sends
list_jobs(conn; status, kind) the jobs of the server
cancel_job!, kill_job!, block_job!, resume_job! the control routes; they need the admin permission

6. Pages of a Search

search_pages runs a dense or sparse search on the server and receives its results in pages, through a cursor of the server. It returns an iterator of Vector{SearchResult}, one per page:

for page in search_pages(h, q, 10_000; page_size=500)
    # page::Vector{SearchResult}
end

The server computes all k results at once. Each page after the first is one request. The iterator can be read once, and the cursor expires 300 seconds after the search. A page requested after that, or a second pass, raises StateConflict. The engine has no counterpart, because it returns every result at once.

7. Followers

A follower of a dataset reads the items of the dataset and organizes them by keys. A partition follower restricts a search to the items of one key. A keyword follower indexes the keys of each item in an inverted file. The architecture page describes both kinds. The client has the functions of the engine for them:

f = create_follower(h, "by_repo"; kind="partition", source="meta:repo", disjoint=false)
kw = create_follower(t, "kw"; kind="keyword", source="keywords", policy="manual")

v = open_follower(h, "by_repo=unicach")          # RemoteFollowerView
search(v, q, 10)                                 # one partition of a dense dataset
ftsearch(open_follower(t, "by_repo=unicach"), "redes neuronales", 10)  # a text dataset
calibrate!(v; levels=0.9)                        # the graph of the partition
partitions(f)                                    # (name, items, graph) per partition

search(kw, ["Elizabeth", "Geneva"], 10; t=1)     # items ranked by their keys
posting_list(kw, "Elizabeth"; limit=100)         # Vector{Int32}, in ascending order
posting_list(t, "monster")                       # a token of a text dataset

followers(h)                                     # Vector{FollowerStatus}
follower_status(kw).lag                          # items not processed yet
sync!(kw)                                        # processes them; returns their number
rebuild_follower!(t, "kw")
delete_follower!(t, "kw")
migrate_partitions!(h, "repo"; disjoint=true)    # the partitions of partition_by, to a follower

create_follower, rebuild_follower!, delete_follower! and migrate_partitions! need the admin permission. sync! and calibrate! need the write permission.

posting_list of a frequent key in a large dataset can return most of the items of the dataset in one response. Pass limit when only some of them are needed.

The differences with the engine are these:

function in the engine in the client
create_follower a spec, such as PartitionFollower(MetaValue("repo"); disjoint=false) the names of the HTTP API: kind="partition", source="meta:repo", disjoint=false
open_follower(h, "name=value") raises UnknownPartition for a value that is not a partition does not check the value; the first search with it raises UnknownPartition
search of a view a filter function, minrecall, candidates, stats a filter object and minrecall
FollowerStatus error is the last failure of sync! error also reports a follower that the server could not open
close_follower! closes the database of the follower does nothing
attach_follower! exists not available; the commands rebuild and load of similarity-search use it

The client does not declare the spec types of the engine, PartitionFollower and KeywordFollower. A follower is created with the names of the HTTP API, as create_project creates a dataset.

A key source or a kind of a plugin of the server is named Plugin.name. With options, it is a Dict. plugins(conn) lists the plugins of the server and their names:

plugins(conn)                       # [Dict("name" => "Decades", "key_sources" => ["Decades.decade"], ...)]
f = create_follower(h, "by_decade"; kind="partition",
                    source=Dict("name" => "Decades.decade", "field" => "year"))

A plugin that the server has not loaded raises PluginNotLoaded. The server manual describes the plugins.

8. What the Client Does Not Cover Yet

  • The administration routes: tokens, unloading and reloading a dataset, and the operation log. The Python client in server/python/ covers them.
  • The jobs searchbatch, closestpair and build have no function of their own. The server accepts them with an explicit command line, which submit_job(conn, kind; command=[...]) sends.

9. Tests

The package’s own tests need no server: they check the error mapping, the shape of the items sent, and the options checked before a request. The tests against a server are part of the full level of the server’s suite (server/test/api/test_17_julia_client.jl), which starts one.

julia --project=server/julia -e 'using Pkg; Pkg.test()'
