SimilaritySearchEngine.jl

An embedded similarity-search engine for Julia, and the service layer built on it

This site documents one repository with two packages. They are developed together, tested together and released together, and the line between them is deliberate:

SimilaritySearchEngine SimilaritySearchServer
where the repository root server/
what it is an embedded, in-process library: storage, indexing and search a REST API, two command lines, and an asynchronous job queue
what it knows RocksDB column families, inverted files, proximity graphs HTTP status codes, exit codes, job spools, access tokens
what it does not know HTTP, processes, tokens anything about how an index is built or stored

Everything about storing, indexing and searching lives in the engine. The server calls its public API and nothing beneath it; in return, the engine never learns what a status code is. That is the whole architecture of the repository, and it is why a failure in the engine travels as a typed error rather than as a message: each frontier — HTTP, CLI, or a Julia caller — decides on its own what that category means to its audience.

Which half do you need?

Searching inside your own Julia process. The engine is the whole answer: a working directory, a project handle, and function calls. No daemon, no ports, no serialization between you and the index; access control is the file permissions of the working directory.

: Start with Getting started, then Architecture.

Serving search to other processes, machines or languages. The server wraps the same engine in a service: one EmbeddedEngine per dataset, endpoints that translate one request into one engine call, and whole-collection operations dispatched as independent Julia subprocesses so that a query never waits behind an allknn.

: Start with the server tutorial, then the server manual.

Both halves are in one reference, generated from the docstrings: Engine API and Server API.

Installation

Neither package is in the General registry yet, so both are installed from this repository. The engine’s dependencies — SimilaritySearch.jl, TextSearch.jl, RocksDB.jl and the RocksDB_jll binaries — are all registered, so nothing else has to be cloned or built:

using Pkg
Pkg.add(url="https://github.com/sadit/SimilaritySearchEngine.jl")

The server is the same repository’s server/ subdirectory, and it reaches the engine by path:

git clone https://github.com/sadit/SimilaritySearchEngine.jl
cd SimilaritySearchEngine.jl
julia --project=server -e 'using Pkg; Pkg.develop(path="."); Pkg.instantiate()'
julia --project=server -t auto -m SimilaritySearchServer serve

Julia 1.12 or later is required by both. No Manifest.toml is committed for the engine, so Pkg.instantiate() resolves the base libraries from the registry unless you develop them by path as well.

What the engine provides

  • Project Lifecycle Management: Functions create_project, open_project, and close_project! manage the on-disk RocksDB directory and the associated live search engine.
  • Engine and Backend Separation:
    • Payload Engines: DenseEngine, SparseEngine, and FullTextEngine specify the stored data domain.
    • Index Backends: SearchGraph, ExhaustiveSearch, InvertedFile, and BM25InvertedFile define the underlying indexing data structures.
    • The function payload_kind(engine) identifies the data domain, and the BACKENDS registry enforces valid engine-backend pairings.
  • Dense Vector Search: Approximate nearest-neighbor search via SearchGraph with dynamic beam-search tuning, or exact brute-force search via ExhaustiveSearch and ParallelExhaustiveSearch. For SearchGraph, insertions (append_items!) and graph construction (index!) are decoupled to give callers explicit control over indexing latency.
  • Sparse Vector Search: Native inverted index search (InvertedFile) over user-encoded sparse representations of fixed dimension. Distance functions include cosine distance over weights and discrete set metrics (Dist.Sets.*) over non-zero coordinate supports.
  • Full-Text Retrieval: Lexical search backed by BM25InvertedFile or TF-IDF-weighted TextInvertedFile. The initial index! call fits or initializes a TextProfile from staged texts, establishing the vocabulary and linguistic weighting model.
  • Explicit Text Modeling: Text projects require an explicit AbstractTextModelSpec:
    • DefaultProfile(:lang): Resolves a pre-trained language profile and refits vocabulary frequencies against the staged corpus.
    • BaseProfile(p): Utilizes an existing, pre-computed TextProfile.
    • FitFromCorpus(cfg): Fits a new profile directly from the staged corpus, bounded by max_documents.
    • Query execution accepts a QueryPolicy to control automatic orthographic correction and semantic query expansion.
  • Strongly Typed Interface: Inputs are encapsulated in typed containers (DenseItem, SparseItem, TextItem), and queries return structured results (SearchResult, StoredItem, ExistsResult).
  • Logical Deletions: The delete_item! function marks documents as logically deleted without mutating the underlying search index. Queries return candidates alongside an explicit deleted flag.
  • Target Recall Calibration: The calibrate! function executes hyperparameter optimization to calibrate beam-search configurations for target recall constraints (minrecall), and SearchStats reports what a query actually cost in distance computations.
  • Whole-Dataset Metric Operations: Synchronous, in-process execution of all-pairs nearest neighbors (allknn), diverse center selection (fft), closest pair discovery (closestpairs), and cross-dataset closest pairs (bichromatic_kclosestpairs).
  • Granular Storage Persistence: High-throughput persistence utilizing a hybrid layout of RocksDB column families and dedicated memory-mapped vector files (dense_vectors.mmapdb).
  • Typed Errors: Deliberate failures are raised as EngineError subtypes grouped into four categories (InvalidRequest, NotFound, ConflictingState, StorageFailure), so a caller can act on a failure without interpreting its message.

What the server adds

  • REST API: dataset lifecycle, append, dense/sparse/text search with metadata filters, soft deletes, recall calibration, and cross-dataset fusion (hybrid, ftsearch_group).
  • Asynchronous jobs: allknn, fft, neardup, hsp, searchbatch, closestpair, build, dump and load are enqueued and dispatched as independent Julia subprocesses, each opening its dataset read-only so that serving continues while they run.
  • Two command lines: similarity-search for the data plane against a working directory, similarity-search-ctl for the control plane against a running server — installable as apps with Pkg.Apps.
  • Operational surface: access tokens, a per-dataset operation log (whose distance-evaluation counts come from the engine’s SearchStats), result cursors for pagination, health and metrics endpoints, and hot unload/reload of a single dataset.
  • One error vocabulary: the engine’s four categories become HTTP status codes and CLI exit codes by category, never by message — the boundary described above, made concrete.
