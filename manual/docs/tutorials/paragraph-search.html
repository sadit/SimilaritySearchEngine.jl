Multilingual Paragraph Search over Books and Wikipedia

This tutorial applies full-text retrieval to corpora in several languages. The Getting Started tutorial uses one novel in English; this one indexes three corpora:

Corpus Identifier Source Collection Language Volume Retrieval Unit
gutenberg-en Project Gutenberg English 100 volumes Paragraph
gutenberg-es Project Gutenberg Spanish 100 volumes Paragraph
wikipedia-en Wikipedia (2023-11-01 dump) English 1,000 articles Paragraph

Motivation for Paragraph-Level Granularity

Indexing a long document, such as a complete book or an encyclopedia article, as a single unit reduces precision. A long document covers several topics, and the document frequency of a term carries little information when most terms of the vocabulary occur in almost every document. A paragraph is a shorter unit, restricted to one topic, and is therefore appropriate both for matching a query and for fitting a text model.

Dataset Preparation

The datasets and the text profiles used in this tutorial are produced by tutorials/prepare.jl. The script downloads texts in the public domain, divides them into paragraphs, fits the text profiles, and indexes the corpora:

# Complete build (approximately one hour)
julia -t 8 --project=tutorials tutorials/prepare.jl

# Reduced build, for verification (approximately five minutes)
julia -t 8 --project=tutorials tutorials/prepare.jl --smoke

Each stage (corpora, profiles, projects) writes its result to disk, so a later execution repeats only the stages that are missing. A single stage can also be requested by name, and --force rebuilds it: julia -t 8 --project=tutorials tutorials/prepare.jl projects --force.

The times reported in this page were measured with 8 threads. Indexing uses them, so a different number of threads changes the values in the last table.

Linguistic Profiles (TextProfile)

A text project requires a TextProfile, which defines the tokenization of the vocabulary, the term weighting, the stopword list, the lemma map, and the query-expansion network.

The preparation script fits the profiles with the procedure of TextSearch.jl (textsearch fit). That procedure applies Latent Semantic Indexing (LSI) to obtain word embeddings, and builds the query-expansion structures from them.

Normalization Policy: Preserving Case and Diacritics

The corpora are processed under the following normalization configuration:

[normalization]
del_diac = false      # Preserve diacritical marks (e.g., accents)
lc = false            # Preserve character casing
del_punc = true       # Remove punctuation marks
group_num = true      # Normalize numeric sequences
group_url = true      # Normalize URL strings

Preserving case and diacritics preserves distinctions in meaning, for example between a proper noun and a common noun, or between two words of a Romance language that differ only in an accent. The query is resolved against this vocabulary, and a query written without accents is mapped to the accented form at search time.

Applied vs. Carried Artifacts

A fitted profile stores its lemma clusters and its expansion network, and does not apply them by default. Applying one of them modifies the tokenization, and the project configuration selects it explicitly. The stopwords are marked as applied because the vocabulary frequencies were computed with the stopwords removed.

Orthographic Query Correction

Because linguistic profiles preserve diacritics, unaccented search terms (e.g., musica) do not match accented vocabulary entries (música) by default.

Under the default QueryPolicy(correction=:auto), the query resolution engine identifies unaccented query terms and maps them to their most probable accented vocabulary counterparts:

Query: la musica del corazon
  ~ musica is in 9 documents against música's 724, so it reads as a misspelling; searched as música (variant), Música (variant) instead

Query: el pais y la republica
  ~ republica is in 3 documents against República's 307, so it reads as a misspelling; searched as República (variant), república (variant) instead

ftexplain reports the token substitutions that were applied. A query written with correct orthography produces no substitution:

ftexplain output on correctly typed query: String[]

To enforce exact literal matching without orthographic correction, set correction=:off:

Semantic Query Expansion

Query expansion adds to each query term its nearest neighbors in the LSI embedding space:

anarchism      -> anarchist, capitalism, individualist, Individualist, anarcho, anarchists
philosophy     -> metaphysics, philosophical, epistemology, Immanuel, Sramana, Sramanas
revolution     -> revolutions, Enlightenment, revolutionary, monde, mentalités, autonomy

Query expansion increases recall, because it adds related terms to the query:

Programmatic Project Lifecycle

The following example performs the complete sequence over a subset of one corpus:

# 1. Ingest slice of paragraph records
slice = map(Iterators.take(eachline(corpus_file("gutenberg-en")), 2000)) do line
    o = JSON3.read(line)
    meta = Dict{String,Any}(String(k) => v for (k, v) in pairs(o) if k !== :text && k !== :doc_id)
    SSE.TextItem(String(o.text); doc_id=String(o.doc_id), meta)
end

# 2. Create project using a pre-computed BaseProfile
workdir = mktempdir()
h = SSE.create_project(workdir, "sample_project";
        engine    = SSE.FullTextEngine,
        backend   = TextSearch.BM25InvertedFile,
        textmodel = SSE.BaseProfile(profiles["gutenberg-en"]))

# 3. Stage items (durable on disk, pending indexing)
SSE.append_items!(h, slice)

# 4. Construct inverted file postings over staged backlog
quiet() do
    SSE.index!(h)
end

# 5. Execute full-text query
results = SSE.ftsearch(h, "the whale", 3)

Empirical Benchmark Analysis

The following table reports the construction and indexing times measured over the three corpora:

Project Paragraphs Vocabulary Create (s) Append (s) Index (s) Indexing Latency (ms/doc) Disk Footprint
gutenberg-en 265,424 136,716 1s 4s 22s 0.08 102 MB
gutenberg-es 216,247 337,336 2s 3s 15s 0.07 91 MB
wikipedia-en 41,279 139,776 1s 1s 5s 0.13 32 MB

Performance Observations

  • Cost of persistence: writing each document to RocksDB adds little time compared with an indexing loop in memory, and the data survive an interruption of the process.
  • Compilation time: the first execution in Julia includes the compilation of the code. Later batches show the rate of the compiled code.
  • Storage of the profile: creating a project with a fitted profile writes that profile into the RocksDB store of the project, so the project can be copied to another machine without additional files.
  • Storage of the index: a text project stores the inverted index, so opening it does not index the corpus again. The architecture guide reports the difference: 1.4 s against 20.4 s for the largest of these corpora.
