Paragraph search over books and Wikipedia

This is the tutorial to read after Getting started. That one used one novel and took every default; this one uses three real corpora, in two languages, each indexed against a text model fitted for it — which is where the decisions that matter start mattering.

corpus source language documents retrieval unit
gutenberg-en Project Gutenberg English 100 books paragraph
gutenberg-es Project Gutenberg Spanish 100 books paragraph
wikipedia-en Wikipedia 2023-11-01 English 1000 articles paragraph

Paragraphs, not documents. A search here answers with the paragraph that contains the answer, not with the book it appears in. That choice runs all the way down: it is the unit the corpora are built in, the unit the profiles are fitted on, and the unit the projects index. Retrieving whole books would be close to useless — Moby-Dick is “about” almost anything you can ask — and it is also a worse model, because a document frequency computed over books says nothing (nearly every word is in nearly every book) while one computed over paragraphs is informative.

Before you start

Everything below reads what tutorials/prepare.jl builds. That script downloads the books, extracts the Wikipedia articles, fits a profile per corpus and indexes each into a project. It is measured in tens of minutes and hundreds of megabytes, which is exactly why it is a script and not a section of this page:

# from the repository root
julia --project=tutorials tutorials/prepare.jl            # the documented scale, ~1 hour
julia --project=tutorials tutorials/prepare.jl --smoke    # a few books and articles, ~5 minutes

Each step (corpora, profiles, projects) is separately runnable and caches to disk, so a run that fails halfway resumes instead of restarting.

NoteRendering this page yourself

Quarto’s Julia engine needs a writable runtime directory. On a machine where /run/user/$UID is not writable, quarto render fails with PermissionDenied ... mkdir '/run/user/…/julia' before running a single cell. Point it somewhere else:

XDG_RUNTIME_DIR=$(mktemp -d) quarto render manual

The corpora

true

prepare.jl writes one JSONL file per corpus, one paragraph per line, and records what it measured. Everything this page reports about the build is read back from that record rather than typed into the prose — a number in a document goes stale silently; a number read from the file the build wrote is either current or missing.

corpus language documents paragraphs per document JSONL
gutenberg-en en 100 265,424 2654.2 120.1 MB
gutenberg-es es 100 216,247 2162.5 89.2 MB
wikipedia-en en 1,000 41,279 41.3 30.2 MB

Two things in that table are worth pausing on.

Wikipedia yields far more paragraphs per article than you would expect. The dump is ordered longest-article-first, so the first shard — which is what a thousand articles come from — is the densest part of the corpus. TextSearch’s own measurements put the corpus-wide figure near 7 paragraphs per article; take them from the front and you get an order of magnitude more. Sampling the convenient slice and extrapolating is how corpus-size estimates go wrong.

Books vary enormously, and the average hides it. A hundred Gutenberg volumes is not a hundred comparable things. The English hundred runs from 87 paragraphs to 36,096 — a Complete Works of William Shakespeare that is 13.6% of the corpus on its own — against a median book of 1,859. The Spanish hundred’s largest contributor is not a novel at all but a Diccionario Ingles-Español-Tagalog at 17,682 paragraphs, 8.2% of that corpus. The per-document average in the table above is therefore a number no actual book resembles, and what it costs you shows up in Searching below.

Each record carries the paragraph plus enough metadata to say where it came from:

keys: doc_id, text, source, lang, book_id, title, author, paragraph

doc_id: gutenberg-es-61851-p1
title:  El crimen y el castigo — Dostoyevsky, Fyodor
text:   Se ha respetado la ortografía y la acentuación del original.…

doc_id is the caller’s own identifier; the engine hands it back on every hit. Everything except text, vector, keywords, ref and doc_id goes into the record’s metadata, which is what a filtered search reads.

Profiles

A text project needs to know how to turn text into tokens and how to weight them. That is a TextProfile: a vocabulary and weights, plus whatever a corpus produced — a stopword set, a lemma map, a query-expansion network — plus the lineage saying how it was made.

prepare.jl fits one per corpus with TextSearch’s own textsearch fit, and not with this package’s fit_profile. The difference is what you get: fit_profile produces a vocabulary and weights, which is all an indexing corpus can yield on its own, while textsearch fit additionally runs an LSI over the corpus and derives a query-expansion network and a lemma map from it. Those artifacts are the reason the two query-side sections below demonstrate something instead of describing it.

The configuration used for every corpus is worth reading, because one line in it drives most of this page:

[normalization]
del_diac = false      # keep diacritics
lc = false            # keep case
del_punc = true
group_num = true
group_url = true

Keeping case and diacritics is a deliberate cost. Folding them is cheaper and gives a smaller vocabulary, and it is what the default TextConfig() does — but it also collapses leon and León into one token before the index ever sees them, which leaves the query side with nothing to work with. Everything in Correcting a query below exists only because these are false.

profile vocabulary stopwords lemmas expansion fit
gutenberg-en 136,716 9 (applied) 28,465 136,716 265s
gutenberg-es 337,336 0 83,792 337,336 476s
wikipedia-en 139,776 18 (applied) 23,186 139,776 129s

Note the (applied) markers, or rather where they are missing. A freshly fitted profile carries its lemma map and its expansion network without applying them. That is not an oversight, it is the distinction the type exists to make: computing an artifact and deciding to use it are different acts, and the second belongs to whoever indexes with the profile. Stopwords are applied because the vocabulary was counted with them already removed — un-applying those would mean refitting.

Installing, listing and describing profiles

This tutorial loads profiles from plain files on disk, with load_profile(path), because that needs nothing installed and keeps every path in this page explicit. For day-to-day use TextSearch’s CLI manages a profile library under ~/.textsearch/profiles/ instead:

textsearch install tutorials/profiles/gutenberg-es.zip gutenberg-es   # copy in under a nickname
textsearch install tutorials/profiles/gutenberg-es.zip                # nickname defaults to the filename
textsearch list                                                       # what is installed
textsearch info gutenberg-es                                          # vocabulary, artifacts, lineage
textsearch uninstall gutenberg-es                                     # reports what it *would* delete
textsearch uninstall gutenberg-es --force                             # actually deletes it

The nickname is a positional argument, not a flag, and defaults to the zip’s filename. Note what uninstall does without --force: it prints the path, the size and the command that would delete it, and removes nothing. Here the registration is the file — a profile can represent hours of compute and the installed copy may be the only one left — so the destructive reading of the word has to be asked for.

Once installed, a nickname works anywhere a path does in the CLI’s own commands. The file itself sits at ~/.textsearch/profiles/<nickname>.zip (or under $TEXTSEARCH_HOME), and load_profile takes that path like any other. Nothing below depends on having installed anything.

The distances are BM25 scores, negated so that smaller is better — the same convention every index kind in SimilaritySearch.jl uses, so a caller never has to ask whether high or low wins.

Nothing about the calls above is language-specific. The language lives in the profile the project was created with; ftsearch is the same function in all three.

If a dictionary entry outranked the novel you were expecting, that is the corpus and the scoring function telling you something true. Gutenberg’s popularity ranking is not a balanced sample: the Spanish top hundred’s single biggest contributor is a Diccionario Ingles-Español-Tagalog, 17,682 paragraphs — 8.2% of the corpus, and 1.7× the largest volume of prose in it. BM25 normalises by document length, and a two-line dictionary entry sharing one query term with you scores far above a hundred-word paragraph of prose sharing three. So a corpus with one dictionary in it has, in effect, seventeen thousand tiny documents competing for every query that touches their headwords. Neither the index nor the profile is misbehaving — a corpus assembled by popularity is simply not a corpus assembled for retrieval, and this is what that looks like before anyone filters it.

Correcting a query

Because the profiles keep case and diacritics, a Spanish query typed without accents is not the same query the corpus contains. QueryPolicy’s default handles that, and can explain itself:

query: la musica del corazon
  ~ musica is in 9 documents against música's 724, so it reads as a misspelling; searched as música (variant), Música (variant) instead

query: el pais y la republica
  ~ republica is in 3 documents against República's 307, so it reads as a misspelling; searched as República (variant), república (variant) instead

Each line is a token the search replaced, with the evidence for replacing it. A correction happens only where the evidence says the typed spelling is wrong — it is absent from the vocabulary, or far rarer than another spelling of the same word. A correctly typed query produces no lines at all:

ftexplain on a correctly typed query: String[]

A search that silently substitutes what was asked for owes the person a way back, which is correction=:off:

[gutenberg-es]  la musica del corazon
  1. Diccionario Bagobo-Español                  -121.829
     Pipit ca casócot.--Menudear, repitir la petición.

     Ca-polao.--Letargo, pertubación del jucio.

Expanding a query

The expansion network relates each vocabulary token to its nearest neighbours in the LSI space the fit computed. prepare.jl turns it on when it creates each project — fit leaves it carried, and applying it is the indexer’s decision:

base = load_profile("tutorials/profiles/wikipedia-en.zip")
prof = TextSearch.with_applied(base; query_expansion=true)
create_project(dir, "wikipedia-en"; engine=FullTextEngine, backend=BM25InvertedFile, textmodel=BaseProfile(prof))

What the network holds for a few terms:

anarchism    -> anarchist, capitalism, individualist, Individualist, anarcho, anarchists
philosophy   -> metaphysics, philosophical, epistemology, Immanuel, Sramana, Sramanas
revolution   -> revolutions, Enlightenment, revolutionary, monde, mentalités, autonomy

Expansion widens reach at the cost of precision, which is why it is a property of the query rather than of the index: the same project answers both ways, one keyword apart. expansion_k takes only the nearest few neighbours per token instead of the whole list, which is the middle setting between the two.

Building a project from scratch

Everything above opened projects prepare.jl had already built. Here is the whole path, live, on a small slice — this is what prepare.jl does, minus the scale:

slice = map(Iterators.take(eachline(corpus_file("gutenberg-en")), 2000)) do line
    o = JSON3.read(line)
    meta = Dict{String,Any}(String(k) => v for (k, v) in pairs(o) if k !== :text && k !== :doc_id)
    SSE.TextItem(String(o.text); doc_id=String(o.doc_id), meta)   # typed in, typed out
end

workdir = mktempdir()
h = SSE.create_project(workdir, "slice";
        engine    = SSE.FullTextEngine,
        backend   = TextSearch.BM25InvertedFile,
        textmodel = SSE.BaseProfile(profiles["gutenberg-en"]))

SSE.append_items!(h, slice)          # stages: durable, but nothing is searchable yet
isempty(SSE.ftsearch(h, "the whale", 3))
true
quiet() do                           # see the note below on the engine's progress log
    SSE.index!(h)                    # encodes and indexes the backlog
end
[r.doc_id for r in SSE.ftsearch(h, "the whale", 3)]
3-element Vector{String}:
 "gutenberg-en-2701-p576"
 "gutenberg-en-2701-p1200"
 "gutenberg-en-2701-p775"

quiet there is this page’s own helper, redirect_stderr(devnull) do … end. Every index kind installs an InformativeLog that reports insertion progress on stderr, which is the right default for a build that runs for an hour and the wrong one for a document. Nothing about it is configurable through create_project; redirecting the stream is how you turn it off.

The split between the two cells is the engine’s staging model: append_items! makes an item durable immediately and searchable never; index! is the explicit, idempotent step that makes it searchable. It is why the first cell finds nothing and the second finds everything, and it is what lets a caller decide when to pay for indexing.

Reusing a profile a project already fitted is the same two lines in the other direction:

TextSearch.save_profile(joinpath(workdir, "exported"), SSE.text_profile(h))
reloaded = TextSearch.load_profile(joinpath(workdir, "exported"))
exported vocabulary: 136,716 tokens

The two alternatives, and why this page takes neither

Every project on this page was created from a BaseProfile, because prepare.jl had just fitted the profile and held it in hand. The other two forms matter more for a project you are starting from nothing.

DefaultProfile is the one to reach for, and it is what this page would use if it were not building its own profiles as it goes:

create_project(workdir, "noticias"; engine=FullTextEngine, backend=BM25InvertedFile,
               textmodel=DefaultProfile(:es))

At the first index! call it loads the published Spanish paragraph profile — the same wiki20231101-es-paragraphs this tutorial’s own fits are modelled on — and refits it against whatever you staged: counts blended, weights recomputed, stopwords and lemmas and the expansion network inherited. It resolves from the profile library textsearch install maintains, and says how to install the profile if it is not there.

The refit narrows the vocabulary to your corpus rather than keeping the language’s: measured on the English base, 335,336 tokens become 12,238 against an 800-document sample. What it buys is calibration and artifacts, not coverage; refit=false keeps the base whole if coverage is what you are after. DefaultProfile’s docstring has the numbers.

FitFromCorpus says, deliberately, that there is no pre-fitted model and one should be fitted from the project’s own corpus:

create_project(workdir, "self-fitted"; engine=FullTextEngine, backend=BM25InvertedFile,
               textmodel=FitFromCorpus(TextConfig(language=:en); min_ndocs=3, stopwords=0.9))

There is no default among the three, and the reason is a trap. That fit is delegated whole to TextSearch.fit_profile, which has no cheap variant — it always runs the LSI, the expansion network and the lemma clustering — so it is bounded by max_documents (1,000 by default) instead of by the corpus. Which means its vocabulary is fitted from a sample: every term appended later that the sample never held is out-of-vocabulary and silently dropped, forever. Nothing about the project’s behaviour afterwards distinguishes “I chose this” from “I never said”, which is exactly why it cannot be arrived at by omission — create_project refuses a text project with no textmodel.

The profiles table above is what that trap costs in the other direction: the fits on this page took 129 to 476 seconds each, on corpora of 41,000 to 265,000 paragraphs. That is the price of a real profile, paid once, by a script — and the reason a project should be handed one rather than asked to produce it during its first index!.

What building this cost

The numbers below were measured by the build, not estimated:

project paragraphs vocabulary create append index ms/paragraph on disk
gutenberg-en 265,424 136,716 3s 5s 96s 0.36 278 MB
gutenberg-es 216,247 337,336 2s 4s 44s 0.20 201 MB
wikipedia-en 41,279 139,776 1s 1s 7s 0.17 66 MB

Three things in that table are worth naming.

Incremental persistence is cheap, and the first project pays for the whole run. Every push_item! reports an :add! event and the project’s callback writes that paragraph’s encoded object to RocksDB as its own record, which sounds expensive and is not: measured warm on 3,000 paragraphs, the raw TextSearch push loop takes 0.08 ms per paragraph and the engine’s index! takes 0.129 — 1.6× for durability at every step.

The index! column is worth reading with that in mind, because the first row is not comparable with the others. Julia compiles the indexing path on its first execution, and the first project built absorbs all of it: an earlier measurement here reported thirty times the library’s cost per paragraph, and it was measuring compilation. The lesson generalises past this table — the first timing in a fresh Julia session is a compilation measurement wearing a throughput measurement’s clothes.

A search hit carries an id and a score, and nothing else. ftsearch answers with [SearchResult]s — _id, doc_id, distance, deleted — and getting from there to the paragraph means one fetch_items call per hit, as show_hits above does. That is one metadata read and one payload read per result, and a caller displaying a page of ten hits pays for ten of each.

Writing this page is what found that: the first version of it could not print a paragraph at all. fetch_items used to return a Dict{String,Any} of the record merged with its metadata, and the paragraph was in neither — text was a reserved key, stripped on the way in — so the page reached through handle.engine.staged[…] into a private field. Both halves are fixed now: fetch_items returns a typed StoredItem whose payload is the indexed text or vector, read through the public IndexEngine.stored_payload.

Creating a project against a large profile writes the whole profile into it. The create column is not project setup; it is the profile being serialised into the project’s own store so that reopening needs nothing but the project directory. That is the right default — a project that depends on a file somewhere else is a project that breaks when the file moves — but it does mean a shared profile is stored once per project that uses it.
