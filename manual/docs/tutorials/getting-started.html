Getting Started

This tutorial provides an end-to-end walkthrough of SimilaritySearchEngine.jl. Using paragraphs from Mary Shelley’s Frankenstein (included in the package test fixtures), we examine: - Dense vector similarity search using Latent Semantic Indexing (LSI) embeddings and SearchGraph. - Sparse vector indexing with InvertedFile. - Full-text retrieval with BM25 and TF-IDF models. - Logical soft deletions and metadata filtering. - Target recall calibration with calibrate!. - Closing and reopening persistent projects. - Whole-dataset metric operations (allknn, fft, closestpairs, and bichromatic_kclosestpairs).

Installation

SimilaritySearchEngine.jl is not in the General registry yet, so it is installed from its repository. Everything it depends on is registered, so the command below is the whole installation — no local checkouts of SimilaritySearch.jl/TextSearch.jl/RocksDB.jl, and no build step for the RocksDB binaries:

using Pkg
Pkg.add(url="https://github.com/sadit/SimilaritySearchEngine.jl")

If you intend to modify the package while following this tutorial, clone it and develop the clone instead:

using Pkg
Pkg.develop(path="path/to/SimilaritySearchEngine.jl")

This tutorial reads its corpus from the package’s own test/data/, so a cloned copy is the convenient way to follow it verbatim; with the Pkg.add form, point the paths below at any JSONL file of your own with the same fields.

The Reference Dataset: Frankenstein

The test directory contains test/data/frankenstein.jsonl, which provides the complete novel partitioned into 724 paragraphs with metadata annotations:

using JSON

items = [JSON.parse(l) for l in readlines("test/data/frankenstein.jsonl")]
length(items)  # 724 paragraphs
first(keys(items[1]))

Each JSON object defines the following fields: - "text": The raw paragraph string. - "doc_id": An external string identifier (e.g., "frankenstein_1"). - "keywords": Named entities and character names identified in the paragraph (e.g., ["Elizabeth", "Victor"]). - "ref": The doc_id of the preceding paragraph, representing narrative sequence. - "word_count", "verb_count": Arbitrary quantitative metadata stored in the free-form meta JSON dictionary.

Dense Vector Search with LSI (SearchGraph)

1. Creating a Dense Project

To initialize a project on disk, call create_project:

using SimilaritySearchEngine

workdir = mktempdir()
h = create_project(workdir, "frankenstein_dense"; engine=DenseEngine, backend=SearchGraph, minrecall=0.9)

The engine keyword specifies the payload domain (DenseEngine), while backend defines the indexing algorithm (SearchGraph).

2. Generating Semantic Embeddings via LSI

To generate continuous vector representations directly from text without external dependencies, we use Latent Semantic Indexing (LSI) from TextSearch.jl:

using TextSearch: LatentSemanticIndexing, outdim
using TextSearch.LSI: vectorize

corpus = [it["text"] for it in items]
lsi = LatentSemanticIndexing(corpus; maxoutdim=128, verbose=false)
outdim(lsi)  # 128 dimensions

3. Staging Vector Items

We partition the dataset, appending the first half (362 paragraphs) to the project and reserving the second half for subsequent bichromatic evaluations:

half = length(items) ÷ 2

batch = [
    DenseItem(vectorize(lsi, it["text"]);
              doc_id = it["doc_id"], keywords = it["keywords"], refs = it["ref"],
              meta = Dict{String,Any}("word_count" => it["word_count"],
                                      "verb_count" => it["verb_count"]))
    for it in items[1:half]
]
append_items!(h, batch)  # Stages 362 vectors into dense_vectors.mmapdb

4. Constructing the Proximity Graph

For a SearchGraph backend, append_items! writes vectors to disk immediately but does not construct graph edges. To build graph connectivity across the staged backlog, invoke index!:

index!(h)  # Builds graph connections over the 362 staged items

5. Executing Queries and Metadata Filtering

Once indexed, queries are evaluated using search:

query = vectorize(lsi, "the monster and its creator")
results = search(h, query, 5)

for r in results
    println("Document ID: ", r.doc_id, " | Distance: ", r.distance)
end

To restrict query evaluation using metadata predicates, pass a filter function (record, meta) -> Bool:

# Filter results to include only paragraphs with non-empty keywords
filtered_results = search(h, query, 5; filter = (record, meta) -> !isempty(record.keywords))

Filtering is applied to a fixed number of candidates retrieved from the index, candidates, which defaults to 2k. A filtered search returns fewer than k results whenever fewer than k of those candidates satisfy the predicate, and it does so without raising an error: the alternative, enlarging the budget until k results are found, would let a selective predicate silently escalate into a scan of the entire collection, at two RocksDB reads per candidate.

Size the budget to the selectivity of the predicate. A predicate satisfied by roughly one item in \(n\) requires approximately \(n \cdot k\) candidates to fill a page of \(k\) results:

# One document in ~26 carries this year: 20 candidates are not enough for 10 results
rare = search(h, query, 10; filter = (record, meta) -> meta["year"] == 2005)                   # returns 0
enough = search(h, query, 10; filter = (record, meta) -> meta["year"] == 2005, candidates=8192) # returns 10

6. Batch Queries

A set of queries is answered in a single parallel pass rather than one call at a time. Passing a vector of query vectors to search returns one result list per query, in the same order:

queries = [vectorize(lsi, t) for t in ["the monster and its creator",
                                       "the arctic expedition",
                                       "letters to Margaret"]]
batched = search(h, queries, 5)     # Vector{Vector{SearchResult}}
batched[2][1].doc_id

searchbatch returns the same neighbourhoods in raw form – two (k, length(queries)) matrices of internal ids and distances, with no metadata reads at all – which is the appropriate input for evaluation loops, offline scoring, or feeding another index:

ids, dists = searchbatch(h, queries, 5)
size(ids)     # (5, 3)

Measured over 50,000 dense vectors on 8 threads, searchbatch sustains 39,000 queries/s against 3,800 queries/s query-by-query; the hydrated form reaches 12,600 queries/s, the difference being the metadata read and decode per hit.

Both are whole-dataset operations rather than concurrent searches: they acquire the project’s write lock (exclusive, including with respect to other batch calls) and refuse to run while items remain staged but not indexed. This follows from their internal parallelism, which cannot be nested under the default thread scheduler. Text projects have no batch entry point, since their queries are strings the library resolves individually; call ftsearch in a loop.

7. Logical Soft Deletions

The delete_item! function marks a document as deleted using its internal integer _id. The underlying proximity graph is not restructured:

delete_item!(h, 1)  # Mark internal ID 1 as deleted

results = search(h, query, 5)
first(results).deleted  # Returns true if document 1 is among the top candidates

Query results return matching candidates with an explicit deleted::Bool indicator, allowing client applications to handle tombstoned records without index re-indexing.

8. Calibrating Search Hyperparameters: calibrate!

The calibrate! function executes an internal hyperparameter optimization pass over the graph, calibrating BeamSearch parameters across multiple recall thresholds:

calibrate!(h; levels=[0.8, 0.9, 0.95, 0.97])

# Execute search enforcing minimum 95% target recall
precise_results = search(h, query, 5; minrecall=0.95)

9. Project Closure and Reopening

To close all active RocksDB handles and memory-mapped files:

close_project!(h)

Closing a session that performed writes also compacts the project’s storage. This is not housekeeping: what a bulk ingestion leaves behind is a write-ahead log that the next open must replay, so the cost appears as open latency. On a 50,000-vector project, reopening costs 2.97 s without compaction and 0.48 s with it, for a compaction of 0.16 s. Pass close_project!(h; compact=false) when closing sits on a latency path, or call compact_project! mid-session after a large ingestion the same process will continue to serve.

Reopening the project restores both the stored vectors and graph connectivity:

h2 = open_project(workdir, "frankenstein_dense")
reopened_results = search(h2, query, 5)
close_project!(h2)

Sparse Vector Search (SparseEngine)

SparseEngine indexes user-provided sparse representations (SparseItem) of fixed dimensionality using an InvertedFile backend.

Indexing Pre-Encoded Sparse Vectors

using SimilaritySearch: Dist
using SparseArrays: sparsevec

const DIM = 1 << 16  # 65,536 dimensions

# Example sparse feature encoder (hashed token frequencies)
function bag_of_words_hash(text::AbstractString)
    counts = Dict{Int32, Float32}()
    for w in split(lowercase(text), r"[^\p{L}\p{N}]+"; keepempty=false)
        k = Int32(mod(hash(w), DIM) + 1)
        counts[k] = get(counts, k, 0.0f0) + 1.0f0
    end
    ind = sort!(collect(keys(counts)))
    val = Float32[counts[i] for i in ind]
    sparsevec(ind, val ./ sqrt(sum(abs2, val)), DIM)  # Unit normalization for NormCosine
end

# Create sparse project
hs = create_project(workdir, "frankenstein_sparse";
                    engine=SparseEngine, dimension=DIM, distance=Dist.NormCosine())

# Append sparse items
append_items!(hs, [SparseItem(bag_of_words_hash(it["text"]); doc_id=it["doc_id"], keywords=it["keywords"])
                   for it in items])
index!(hs)  # Idempotent no-op for InvertedFile; items are indexed during append

hits = search(hs, bag_of_words_hash("the monster and its creator"), 5)
for r in hits
    println(r.doc_id, " => Distance: ", round(r.distance; digits=4))
end

Key Properties of SparseEngine

  • Fixed Dimension Requirement: The dimension parameter must be specified at project creation and must match the coordinate dimension of all appended SparseVector objects.
  • Strict Query Typing: Queries must be provided as SparseVector{Float32, Int32} matching the configured dimension.
  • Supported Distance Metrics: Supports Dist.NormCosine over vector weights or discrete set distances (Dist.Sets.Jaccard, Dist.Sets.Dice) over non-zero coordinate supports.

Full-Text Retrieval with BM25 (FullTextEngine)

For text retrieval without manual vector encoding, FullTextEngine integrates text normalization, vocabulary management, and inverted file scoring.

using TextSearch: BM25InvertedFile

hb = create_project(workdir, "frankenstein_bm25"; 
                    engine=FullTextEngine, backend=BM25InvertedFile,
                    textmodel=FitFromCorpus())

# Stage raw text paragraphs
append_items!(hb, [
    TextItem(it["text"]; doc_id = it["doc_id"], keywords = it["keywords"])
    for it in items[1:200]
])

# First invocation fits the TextProfile and builds the BM25 inverted index
index!(hb)

# Search using natural language queries
hits = ftsearch(hb, "monster creature fear", 5)
for r in hits
    println(r.doc_id, " => Score: ", r.distance)
end

close_project!(hb)

A text project persists the inverted index itself, not the objects that were indexed, so reopening it assembles the index rather than recomputing it – 1.4 s against 20.4 s over 265,000 Project Gutenberg paragraphs. This holds for both text backends, BM25 and the weighted TextInvertedFile:

hb2 = open_project(workdir, "frankenstein_bm25")
ftsearch(hb2, "monster creature fear", 5)     # same answers, no reindexing
close_project!(hb2)

Posting lists are read from storage as queries ask for them, behind a cache of the most frequently used ones; their size is set at open time with postings_cache_max and postings_cache_base (the maximum number of cached lists, and the number it is trimmed back to when that maximum is exceeded). Per-document term vectors are read into memory instead, because BM25 scores every candidate from its own vector and a query containing a frequent term makes most of the collection a candidate. The architecture guide carries the measurements behind both halves of that choice.

A project written by an earlier version, which stored the indexed objects instead of the index, opens with no index at all and says so when searched; index!(h) rebuilds it from the staged text, which was always persisted separately. That is the whole migration procedure, and it is explicit on purpose.

Appending after the first index! writes only what the new block changes, so a project can keep growing without ever being rebuilt. The vocabulary, however, is fixed at the first index! under FitFromCorpus: words absent from the text staged by then stay out of vocabulary no matter how many blocks follow. Stage the corpus you intend to fit before calling index! the first time, or start from a BaseProfile.

Configuring Linguistic Models (AbstractTextModelSpec)

Text projects require an explicit linguistic model specification passed via the textmodel keyword:

1. DefaultProfile (Recommended)

Loads a published language profile (e.g., Spanish, English) and refits its vocabulary statistics against the staged corpus during the first index! execution:

hes = create_project(workdir, "news_es"; engine=FullTextEngine, backend=BM25InvertedFile,
                     textmodel=DefaultProfile(:es))

This inherits high-quality stopword lists, lemma clusters, and query-expansion networks from large-scale reference corpora while calibrating term frequencies to the target dataset.

2. FitFromCorpus

Fits a TextProfile directly from the staged corpus without an external reference profile:

using TextSearch: NormalizationConfig

hf = create_project(workdir, "custom_corpus"; engine=FullTextEngine, backend=BM25InvertedFile,
    textmodel=FitFromCorpus(TextConfig(normalization=NormalizationConfig(lc=false, del_diac=false),
                                       language=:es);
                            min_ndocs=3, stopwords=0.9))

The fitting process is bounded by max_documents (default 1,000) to control compute time.

3. BaseProfile

Instantiates a text project from an existing, pre-computed TextProfile loaded from disk:

hp = create_project(workdir, "wiki_base"; engine=FullTextEngine, backend=BM25InvertedFile,
                    textmodel=BaseProfile(load_profile("wiki-es.zip")))

Query Resolution and Expansion: QueryPolicy

Full-text queries execute under a QueryPolicy that controls spelling variant correction and semantic expansion:

# Default policy: automatic orthographic correction
ftsearch(hes, "musica clasica", 5)

# Disable correction: search literal tokens as entered
ftsearch(hes, "musica clasica", 5; policy=QueryPolicy(correction=:off))

Explaining Corrections: ftexplain

The ftexplain function details the specific token substitutions performed by the query pipeline:

ftexplain(hes, "musica clasica")

Full-Text Retrieval with TF-IDF (TextInvertedFile)

To index text using classic TF-IDF weights and cosine distance:

using TextSearch: TextInvertedFile

ht = create_project(workdir, "frankenstein_tfidf"; engine=FullTextEngine, backend=TextInvertedFile,
                    textmodel=FitFromCorpus())

append_items!(ht, [
    TextItem(it["text"]; doc_id = it["doc_id"], keywords = it["keywords"])
    for it in items[1:200]
])
index!(ht)

hits = ftsearch(ht, "monster creature fear", 5)
close_project!(ht)

Whole-Dataset Metric Operations

For dense SearchGraph projects, SimilaritySearchEngine.jl provides whole-dataset algorithms that execute synchronously in-process:

h2 = open_project(workdir, "frankenstein_dense")

1. All-Pairs \(k\)-Nearest Neighbors: allknn

Computes the \(k\) nearest neighbors for every indexed element:

neighbors = allknn(h2; k=5)
first(neighbors)  # Returns (id=1, neighbors=[...], dists=[...])

2. Diverse Center Selection: fft

Executes Farthest First Traversal to select \(k\) well-separated representative centers:

R = fft(h2, 8; verbose=false)
R.centers      # Identifiers of the 8 chosen centers
R.separation   # Minimum distance between any two centers
R.covering     # Maximum distance from any object to its assigned center

3. Monochromatic Closest Pairs: closestpairs

Finds the \(k\) closest pairs of objects within the project:

pairs = closestpairs(h2; k=5)
for (i, j, d) in pairs
    ri = get_metadata(h2.project, i)
    rj = get_metadata(h2.project, j)
    println("Pair (", ri.doc_id, ", ", rj.doc_id, ") | Distance: ", d)
end

4. Bichromatic Closest Pairs: bichromatic_kclosestpairs

Finds the \(k\) closest pairs between the indexed project \(A\) and an external matrix collection \(B\):

using SimilaritySearch: MatrixDatabase

second_half_vectors = [vectorize(lsi, it["text"]) for it in items[(half + 1):end]]
B = MatrixDatabase(hcat(second_half_vectors...))

pairs = bichromatic_kclosestpairs(h2, B; k=5)
for (i, j, d) in pairs
    ri = get_metadata(h2.project, i)
    other = items[half + j]
    println("Cross-match (", ri.doc_id, ", ", other["doc_id"], ") | Distance: ", d)
end

Metadata Retrieval: fetch_items and exists

To retrieve stored records by internal _id or external doc_id:

# Retrieve full stored record including payload
items_fetched = fetch_items(h2, ["frankenstein_2"])
it = only(items_fetched)
it.doc_id         # "frankenstein_2"
it.keywords       # Indexed keywords array
it.meta           # Free-form metadata dictionary
it.payload        # Stored vector or text

# Check record existence and deletion status
exists(h2, [1, "frankenstein_2", "non_existent_id"])

An external identifier is resolved through a dedicated column family rather than by scanning the collection: 0.05 ms against 59 ms for the equivalent scan, measured on a 50,000-item project. Nothing requires doc_id to be unique, so fetch_items returns every item carrying the requested identifier, in ascending _id order, and the result may therefore be longer than the list of ids it was given. Accordingly, exists reports an identifier as deleted only when every item carrying it has been soft-deleted.

A numeric argument is read as an internal _id first, and only falls back to doc_id resolution when no record holds that _id.

Summary

This tutorial demonstrated the core lifecycle of SimilaritySearchEngine.jl: 1. Project creation with explicit payload engines and indexing backends. 2. Ingestion staging via append_items! with deferred graph or vocabulary indexing via index!. 3. Nearest-neighbor querying with metadata filtering, an explicit candidate budget, and soft deletion handling. 4. Batch query execution, hydrated (search) or raw (searchbatch). 5. Hyperparameter calibration (calibrate!) for guaranteed target recall. 6. In-process execution of whole-dataset metric operations. 7. Indexed retrieval by external identifier, and storage compaction on close.
