Getting started

by: Eric S. Téllez

This tutorial walks through the embedded API end to end, using paragraphs from Frankenstein (bundled in this package’s own test data) as a single running example: dense vector search with LSI-derived embeddings, full-text search with BM25 and TF-IDF, soft deletes, filtering, calibrating for a target recall, closing/reopening a project, and the “expensive”, whole-dataset operations (allknn, fft, closestpairs, bichromatic_kclosestpairs) that only make sense once you actually have a project’s worth of data to run them against. For a shorter, bare-minimum first look, see the repository’s README.

Installation

SimilaritySearchEngine.jl isn’t registered yet — develop it from a local checkout (or a git URL) alongside its own dependencies:

using Pkg
Pkg.develop(path="path/to/SimilaritySearchEngine.jl")

The Frankenstein dataset

This package’s own test suite ships test/data/frankenstein.jsonl — one JSON object per paragraph of the novel, already split, cleaned, and annotated by test/generate_datasets.jl. Loading it gives you a Vector of plain Dicts, each already shaped to match Schema.MetadataRecord’s record/data/metadata contract:

using JSON

items = [JSON.parse(l) for l in readlines("test/data/frankenstein.jsonl")]
length(items)  # 724 paragraphs
first(keys(items[1]))

Each item has:

  • "text": the paragraph itself (raw data — never duplicated into metadata).
  • "doc_id": an external id like "frankenstein_1" (the record’s fixed external-id field).
  • "keywords": character names detected in that paragraph, e.g. ["Elizabeth", "Victor"] (the record’s fixed, indexed tag field).
  • "ref": the previous paragraph’s doc_id (the record’s fixed, unvalidated reference field — a forward/backward link, here used to keep narrative order available even though nothing enforces refs point at something that exists).
  • "word_count"/"verb_count": free-form metadata (meta) — anything not a reserved key (vector/text/doc_id/keywords/ref) falls through here as-is, flat, with no wrapper key of its own.

There’s no "vector" key yet — that’s the dense section’s job, below.

Dense vectors with LSI (SearchGraph)

create_project makes a brand-new project directly on disk, at <workdir>/<dataset>. By default it builds a SearchGraph (an approximate, self-tuning index) autotuning toward minrecall=0.9:

using SimilaritySearchEngine
using SimilaritySearch: SearchGraph

workdir = mktempdir()
h = create_project(workdir, "frankenstein_dense"; index_type=SearchGraph, minrecall=0.9)

Getting real dense vectors quickly, with LSI

A SearchGraph project needs Vector{Float32}s to index — if you don’t already have an embedding model at hand, TextSearch.jl’s Latent Semantic Indexing (LSI) gives you real, meaningful dense vectors straight from a text corpus, in-process, with no external model or API call: fit once on your corpus, then project any text (an indexed paragraph, or a brand-new query) into that same dense space.

using TextSearch: LatentSemanticIndexing, outdim
using TextSearch.LSI: vectorize

corpus = [it["text"] for it in items]
lsi = LatentSemanticIndexing(corpus; maxoutdim=128, verbose=false)
outdim(lsi)  # 128 -- the full corpus easily supports it

(maxoutdim is a cap, not a guarantee: outdim(lsi) is min(maxoutdim, vocabulary size, corpus size) — a tiny placeholder corpus of just a handful of documents would yield far fewer dimensions than requested; 724 real paragraphs comfortably reach 128.)

Items are appended as a Vector of dicts, each carrying a "vector" key plus the record fields loaded above. We’ll only insert the first half of the book here, and hold the second half back in reserve, unindexed, for the bichromatic example further down:

half = length(items) ÷ 2

batch = [
    DenseItem(vectorize(lsi, it["text"]);
              doc_id = it["doc_id"], keywords = it["keywords"], refs = it["ref"],
              meta = Dict{String,Any}("word_count" => it["word_count"],
                                      "verb_count" => it["verb_count"]))
    for it in items[1:half]
]
append_items!(h, batch)  # inserted == 362

(append_items! accepts a batch — passing many items in one call amortizes better than one append_items! call per item, though both work; see Architecture for why batch size matters even more for a dense project specifically.)

Indexing the staged vectors

For a SearchGraph project, append_items! only stages raw vectors — cheaply, and durably, but without doing any of the (expensive) graph-connection work. Nothing is searchable yet:

search(h, vectorize(lsi, "the monster and its creator"), 5)  # Vector{...}[] -- empty, nothing indexed yet

index! explicitly builds the graph over whatever’s been staged since the last call (or since creation) — call it once you’re ready for staged items to become searchable, whether that’s right after every append_items! call, on your own periodic schedule, or just once before a batch of queries:

index!(h)

It’s cheap to call again later with nothing new staged (a no-op), and only ever processes the backlog — call it as often as fits your workflow. Searching now finds the 362 staged paragraphs:

query = vectorize(lsi, "the monster and its creator")
results = search(h, query, 5)
for r in results
    println(r.doc_id, " => distance ", r.distance)
end

Pass a filter predicate — a plain (record, meta) -> Bool function over each candidate’s fixed Schema.MetadataRecord (doc_id, keywords, refs, …) and its free-form meta (whatever else you appended it with) — to restrict results without building a separate query language:

mentions_someone = search(h, query, 5; filter = (record, meta) -> !isempty(record.keywords))

Soft deletes

delete_item! marks a document as logically deleted; the index itself is untouched. It takes the internal _id (the position add_item! assigned it, e.g. as returned in a search result’s doc_id field), not the "doc_id" you supplied when appending:

delete_item!(h, 1)  # internal _id 1, not any "doc_id"/metadata value

results = search(h, query, 5)
first(results).deleted  # true if internal _id 1 made the top-5 candidates

A soft-deleted candidate is reported, not hidden and backfilled — if you need k live results after filtering out deletions, overfetch and page yourself, or let SimilaritySearchServer’s cursor layer do it for you.

Calibrating for a target recall

calibrate! runs a real hyperparameter search and persists the result, so a later search(...; minrecall=0.95) call can serve that target recall from a tuned BeamSearch instead of the constructor’s default:

calibrate!(h; levels=[0.8, 0.9, 0.95, 0.97])
precise = search(h, query, 5; minrecall=0.95)

It needs a reasonably sized project to have anything meaningful to search against and tune over — this 724-paragraph corpus is plenty; a toy corpus of just a handful of items would print a wall of “ignoring configuration”/“too few queries” warnings instead (harmless, just noisy), since there wouldn’t be enough distinct items for its own internal sample queries.

Closing and reopening

close_project!(h)

h2 = open_project(workdir, "frankenstein_dense")
same_query_results = search(h2, query, 5)
close_project!(h2)

Every insertion was already persisted incrementally as it happened (see Architecture), so close_project! only needs to flush anything still pending for index kinds that don’t persist incrementally on their own. Staging and indexing are tracked separately, too: reopening restores exactly how far index! actually got, not just how much was staged – had we appended more items after the last index! call above and closed without indexing them, they’d still be there (staged, with their metadata already fetchable) after reopening, just not yet searchable, waiting on a future index! call to catch them up.

same_query_results will be close to, but isn’t guaranteed to be byte-identical to, the results from before closing: SearchGraph is an approximate index, and rebuilding it from persisted vectors (open_project replays every insertion in the same order) doesn’t guarantee an identical internal graph topology to the one built live, so its beam search can explore a slightly different candidate set — expect the same ballpark of hits (often exactly the same), not a bitwise-reproducible top-k, unless you calibrate and search with an explicit minrecall on both sides.

Full-text search with BM25

Text projects work the same way as dense ones, just with a "text" key instead of "vector", and ftsearch instead of search — and, since the redesign that decoupled staging from indexing, the exact same append_items!(stage)/index!(build) shape as a dense project, not a separate training step. BM25InvertedFile scores via BM25 over raw bags-of-words:

using TextSearch: BM25InvertedFile

# `textmodel` is required for a text project -- see the next section for what the
# alternative is and why neither is a default
hb = create_project(workdir, "frankenstein_bm25"; index_type=BM25InvertedFile,
                    textmodel=FitFromCorpus())

append_items!(hb, [
    TextItem(it["text"]; doc_id = it["doc_id"], keywords = it["keywords"])
    for it in items[1:200]
])  # only stages raw text -- nothing searchable yet

index!(hb)  # first call: fits the TextProfile from everything staged so far, then indexes it

hits = ftsearch(hb, "monster creature fear", 5)
for r in hits
    println(r.doc_id, " => distance ", r.distance)
end

close_project!(hb)

index!’s first call on a text project doubles as training: it fits a TextProfile (vocabulary, tf-idf weights, lineage) and builds the real BM25InvertedFile from every item staged so far, then encodes/indexes that same backlog — there’s no separate training entry point or “must be trained first” error. Every later index! call just catches up whatever’s been staged since, exactly like the dense case: idempotent, safe to call repeatedly, a cheap no-op when nothing new is staged.

Tokens never seen at that first index! call are out-of-vocabulary on every later append and silently dropped, so what you’ve staged before it has to be representative of the text you’ll keep appending. text_profile(hb) hands you the fitted model, and save_profile writes it out for reuse — but the real fix for a project that keeps growing is the next section.

Choosing the text model

textmodel above was not decoration. Creating a text project requires it, and there is no default:

create_project(workdir, "oops"; index_type=BM25InvertedFile)
# ERROR: a text project (BM25InvertedFile) needs an explicit `textmodel`, because the ways to
#        get a vocabulary are not interchangeable and the cheap one cannot be undone later: ...

Three forms answer where the vocabulary comes from. They are not variations on one setting, and the order below is the order worth preferring them in.

DefaultProfile — start from a language, adapt to your corpus

hes = create_project(workdir, "noticias"; index_type=BM25InvertedFile,
                     textmodel=DefaultProfile(:es))

This is the one to reach for. At the first index! call it loads the published Spanish paragraph profile and refits it against whatever you have staged: the base’s token counts are blended with your corpus’s, the weights recomputed, and the stopword set, lemma map and expansion network inherited. No embedding is fitted, which is what makes a refit cheap next to a fit.

Be clear about what the refit does and does not give you, because the obvious guess is wrong. Measured on the published English profile: 335,336 tokens in the base, 12,238 after refitting against an 800-document sample, of which 2,649 are tokens the sample never held. Fitting on that sample alone would have given 9,589. So the refit narrows to your corpus’s vocabulary, widened about a quarter by the base — it is not language-wide coverage. What you inherit is the part your own corpus cannot produce: weights calibrated over millions of paragraphs, and (for that base) 96 stopwords, 16,661 lemmas and 10,655 expansion entries.

If coverage is what you need — terms a later batch will introduce that today’s corpus has never seen — pass refit=false and index against the base untouched, all 335,336 tokens, with Wikipedia’s weights rather than yours. Calibration or coverage: the two forms answer different questions.

The profile is resolved from the library textsearch install maintains, under ~/.textsearch/profiles/. Nothing is bundled or downloaded — the profiles are 70–160 MB — and if the one you asked for is not installed the error says so and prints the command that installs it. refit=false indexes against the base untouched, and nickname= points at any installed profile instead of the per-language default.

FitFromCorpus — deliberately no base profile

Fit the model from this project’s own staged corpus, at the first index! call. This is the explicit way to say “I have nothing pre-fitted”, and it is the weakest of the three:

using TextSearch: NormalizationConfig

hf = create_project(workdir, "noticias_propias"; index_type=BM25InvertedFile,
    textmodel=FitFromCorpus(TextConfig(normalization=NormalizationConfig(lc=false, del_diac=false),
                                       language=:es);
                            min_ndocs=3, stopwords=0.9))

Its argument is the corpus-independent policy — normalization, tokenization, and the language the corpus is in. The default TextConfig() lowercases and strips diacritics, which is usually right for English and throws away a distinction that matters in Spanish.

The fit itself is handed whole to TextSearch.fit_profile; this package does not fit profiles. That has a consequence worth stating plainly: there is no cheap variant of that pipeline. Every fit runs an LSI over the sample, derives an expansion network from it and clusters a lemma map from the same embeddings. Measured on 3,000 paragraphs it takes about 49 seconds, against 0.2 for a bare vocabulary-and-weights pass — which is why max_documents exists:

option what it does
max_documents read at most this many documents (1,000 by default), sampled by an even stride across the corpus rather than taken from the front. 0 lifts the cap
min_ndocs drop a token seen in fewer documents than this, before the encoder runs. Not cosmetic: the expansion network is an all-pairs kNN over the vocabulary
stopwords a document-frequency threshold in (0, 1]; tokens above it are dropped and the vocabulary recounted without them. A second pass over the sample
encoder, expansion, lemmas the library’s own option groups, as NamedTuples — encoder=(; outdim=128), lemmas=(; apply=true)

The cap bounds the cost and cuts against the one thing this path is already worst at: a vocabulary from 1,000 sampled documents is thin, so more of what you append later is out-of-vocabulary and silently dropped. That is the trade, and it is why the section above exists.

BaseProfile — a model fitted elsewhere

hp = create_project(workdir, "noticias_wiki"; index_type=BM25InvertedFile,
                    textmodel=BaseProfile(load_profile("wiki20231101-es.zip")))

This trains the project before its first item is ever staged, and is what DefaultProfile does underneath once it has resolved and refitted — use this form when you already hold the file, or when you want the base used exactly as it is. To load a profile but decline one of its artifacts, change the profile rather than the project: BaseProfile(with_applied(p; lemmas=false)).

Either way the spec is persisted with the project and restored verbatim by open_project. And a project that fitted its own model can export it for the next one to index against:

save_profile("mi-perfil", text_profile(hes))
create_project(workdir, "hermano"; index_type=BM25InvertedFile,
               textmodel=BaseProfile(load_profile("mi-perfil")))

Passing a textmodel to a dense project is an error rather than an ignored keyword — there is no reading under which it does anything.

Correcting and widening a query

A query travels with a QueryPolicy, because whether to correct a misspelling or widen a search is a guess about what the person meant — a property of the query, not of the index:

ftsearch(hes, "musica clasica", 5)                                   # :auto (the default)
ftsearch(hes, "musica clasica", 5; policy=QueryPolicy(correction=:off))   # exactly as typed

Under :auto, a typed token is bridged to another spelling of the same word only where the evidence says the typed one is wrong — it is absent from the vocabulary, or far rarer than another spelling of it. On a corpus indexed with del_diac=false, musica reaches música and clasica reaches clásica; a correctly typed query is left alone. Under the default TextConfig() this is inert, since folding case and diacritics already collapsed those spellings into one.

A search that silently substitutes what was asked for owes the caller a way to see it, which is ftexplain:

julia> ftexplain(hes, "musica clasica")
2-element Vector{String}:
 "musica is in 1 document against música's 60, so it reads as a misspelling; searched as música (variant) instead"
 "clasica is in 1 document against clásica's 60, so it reads as a misspelling; searched as clásica (variant) instead"

QueryPolicy also carries expansion/expansion_k, which widen the query with the profile’s query-expansion network — inert unless the project was created from a profile that carries one.

Full-text search with TF-IDF

TextInvertedFile is the other text index kind: a classic TF-IDF-weighted (IdfWeighting + TfWeighting) inverted index, cosine distance by default — a good baseline to compare against BM25’s ranking on the same corpus. (InvertedFile selects the same engine and is accepted interchangeably; TextInvertedFile is the name of what actually gets built.)

using TextSearch: TextInvertedFile

ht = create_project(workdir, "frankenstein_tfidf"; index_type=TextInvertedFile,
                    textmodel=FitFromCorpus())

append_items!(ht, [
    TextItem(it["text"]; doc_id = it["doc_id"], keywords = it["keywords"])
    for it in items[1:200]
])

index!(ht)  # same stage-then-index shape as BM25 above

hits = ftsearch(ht, "monster creature fear", 5)
for r in hits
    println(r.doc_id, " => distance ", r.distance)
end

close_project!(ht)

Same insertion/search shape as BM25 — only index_type changes — so switching between the two to compare rankings on your own corpus is a one-line change.

Expensive, whole-dataset operations

allknn, fft, closestpairs, and bichromatic_kclosestpairs all run synchronously, in-process — no job queue, unlike the HTTP API’s POST /api/v1/jobs/allknn — which is exactly why they’re grouped here as their own section: each one does real work proportional to the whole dataset (or two datasets, for the bichromatic case), so run them against a project you actually want an answer for, not casually inside a hot loop. All four need a dense (SearchGraph) project; reopen the one from the LSI section above if you closed it:

h2 = open_project(workdir, "frankenstein_dense")

All-pairs nearest neighbors

allknn runs SimilaritySearch.jl’s batch all-nearest-neighbors — every item’s own top-k neighbors, all at once:

neighbors = allknn(h2; k=5)
first(neighbors)  # (id=1, neighbors=[...], dists=[...])

id/neighbors are internal _ids (1-based insertion position), not doc_ids — see Metadata lookups to resolve them back to paragraph text.

Farthest-first traversal (diverse sampling)

fft picks k items that are as far from each other as possible — useful for a diverse, representative sample of the corpus (e.g. candidate cluster centers), rather than the “closest to a query” shape every other search here has:

R = fft(h2, 8; verbose=false)
R.centers  # 8 well-separated internal _ids
R.ε        # the separation radius achieved

k closest pairs (near-duplicates and echoes within one corpus)

closestpairs finds the k globally closest pairs of items within a single project — useful for spotting near-duplicate or strongly echoing passages:

pairs = closestpairs(h2; k=5)
for (i, j, d) in pairs
    ri = get_metadata(h2.project, i)
    rj = get_metadata(h2.project, j)
    println(ri.doc_id, " <-> ", rj.doc_id, "  dist=", d)
    println("  A: ", first(items[i]["text"], 90))
    println("  B: ", first(items[j]["text"], 90))
end

Running this against the first half of the novel (h2 as built above) turns up passages like Elizabeth’s account of Justine’s trial echoed a few paragraphs later almost verbatim, at a distance well below typical unrelated pairs — exactly the kind of near-duplicate/ strong echo this function is for.

Bichromatic k closest pairs (across two collections)

bichromatic_kclosestpairs finds the k closest pairs between a project’s own index and a second, separate collection of vectors that isn’t indexed by anything — here, the first half of the novel (already indexed as h2, see above) against the second half’s vectors (computed with the same LSI model, but never inserted anywhere):

using SimilaritySearch: MatrixDatabase

second_half_vectors = [vectorize(lsi, it["text"]) for it in items[(half + 1):end]]
B = MatrixDatabase(hcat(second_half_vectors...))

pairs = bichromatic_kclosestpairs(h2, B; k=5)
for (i, j, d) in pairs
    ri = get_metadata(h2.project, i)             # i is h2's own internal _id
    other = items[half + j]                       # j is B's own 1-based position
    println(ri.doc_id, " <-> ", other["doc_id"], "  dist=", d)
    println("  A: ", first(items[i]["text"], 100))
    println("  B: ", first(other["text"], 100))
end

On the real novel, this surfaces thematically matched passages across the two halves — e.g. Walton’s opening framing letters about a “strange accident” pairing with an equally breathless first-person account much later in the book, well below the distance of an unrelated cross-half pair.

Metadata lookups

fetch_items and exists accept either the internal _id (an integer, or a string of one, e.g. "1") or the doc_id you supplied when appending. fetch_items returns a StoredItem per resolved id — the record’s fixed fields, its free-form meta, and the payload that was actually indexed:

it = only(fetch_items(h2, ["frankenstein_2"]))
it._id            # 2
it.doc_id         # "frankenstein_2"
it.keywords       # ["Chapter", ...]
it.meta["word_count"]
it.payload        # the vector this project indexed (a paragraph, in a text project)

exists(h2, [1, "some-doc-id"])   # Vector{ExistsResult}: (id, exists, deleted)

An id that resolves to nothing is dropped by fetch_items (so the result can be shorter than what you asked for) and reported by exists (so it is always the same length).

get_metadata(h2.project, _id) (used in the closest-pairs examples above) is the lower-level single-record accessor fetch_items itself is built on — it returns just the Schema.MetadataRecord (no meta merged in), which is all those examples needed.
