# Technical Specification: SimilaritySearchServer API

!!! warning "Read this as a specification with a date on it (2026-09-12)"
    This document is the design record of the HTTP API, the job model, tokens, cursors and
    pagination, and it is still the reference for *what* the server does and why. Parts of it
    describe *how* in terms that no longer hold, because the engine underneath moved:

    - **There is no JLD2 snapshot per dataset.** The engine persists its own index, so a
      dataset is the project directory; `dump` bundles that directory and `load` restores it.
      Every passage about `save_snapshot`/`load_snapshot`, snapshot layouts, or "snapshot not
      found" is historical.
    - **The server holds one `EmbeddedEngine` per dataset**, not a `ProjectManager` plus an
      `AbstractSearchEngine` it wires together; it calls the engine's public API and does not
      reach into `IndexEngine`/`Project`.
    - **`index_kind` names an engine/backend pair** (`sparse_invfile` is new), and failures
      are typed: categories map to status codes and exit codes (see `docs/manual.md` §5).
    - **Both packages live in one repository** (this one), the engine at the root and the
      server under `server/`. Passages about a "sibling package" at another path, and about
      porting work across repositories after the fact, describe an arrangement that ended on
      2026-09-12: the two are now developed together and tested in the same CI run. See
      `../DEVELOPMENT_STRATEGY.md`.

    `docs/manual.md` is the current description of the implementation; where the two
    disagree, that one is right.
    Treat this as the standing default for "what's next" until told otherwise.

### Pending work, in the order it is being addressed

1. ~~**Authentication (§4.1).**~~ Done on 2026-09-13. `[auth] enabled` in `config.toml`,
   false by default. With it enabled, every `/api/v1` endpoint requires a token and
   `/healthz`, `/readyz` and `/metrics` do not. A permission is `operation:dataset`, where
   the operation is `read`, `write` or `admin` and each one includes the ones before it, and
   the dataset is an id or `*`. Expiry is verified when a token is created and on every
   request. The first token is created against the working directory with
   `similarity-search add-token`, because a server with authentication enabled and no token
   refuses to start. **Still open:** the operation log records the token string presented by
   each caller, which is why reading the log is an administrative operation; storing a hash
   of it instead would make the log safe to read with `read`.
2. **Remnants of the port.** Removed on 2026-09-13: the `JLD2` dependency, `src/snapshots.jl`,
   and the passages that described a snapshot file as current behavior. Still pending: two
   docstrings in `server.jl` that document `parse_meta_schema` and `serialize_meta_schema`,
   functions that do not exist, and that describe the §4.5 schema that was never built.
3. ~~**The 80/20 split**~~ Done on 2026-09-13. The keys were read by nothing, and job
   subprocesses ran on one thread each, because `Base.julia_cmd()` does not carry the
   `--threads` of the process that spawns them. `batch_threads_pct` now yields a pair,
   how many jobs at once and how many threads each, and each subprocess is started with
   that budget in `JULIA_NUM_THREADS`.
4. ~~**§5.8**, counters derived from the `op_log`~~ Done on 2026-09-13. `/metrics` reports
   requests per dataset and operation, distance computations, items inserted, and a
   histogram of request durations, alongside the gauges it already had. The values are
   accumulated in memory as each request is recorded, by the same call that writes the log
   record, rather than read back from the log: a collector polls every few seconds, and the
   log grows with every request. They therefore cover the running process and reset when it
   restarts, which is what a Prometheus counter does;
   `simsearch_process_start_time_seconds` reports when that was.
5. ~~**§4.5**, the declared metadata schema~~ Done on 2026-09-13, in a smaller shape than
   the one this document proposes, decided in that order:
   - **`meta` is declared, not indexed.** There is no `meta_idx_<field>` column family and no
     pre-filter over one. Filtering stays a post-filter, and the only indexes are the ones
     the engine already maintains: `keywords`, `refs`, `doc_id`.
   - **The declaration is a project-level object, not columns on the record.**
     `Schema.MetaSchema` is a list of `(name, type)` with `type` in `:string`, `:int64`,
     `:float64`, `:bool`, `:timestamp`; it is stored in the project and both packages read
     the same one. `MetadataRecord` keeps its fixed shape: giving it typed columns would make
     its Julia type vary per dataset, which propagates to every signature that mentions it,
     to the Avro of `dump`, and to a server that holds several datasets at once. The record's
     `schema_version`, written and never interpreted until now, says which declaration was in
     force when the record was written.
   - **Additive.** An undeclared field is stored as it arrives, a record need not carry every
     declared field, and `null` is an absent field. Declaring says what a field must hold
     when it is present.
   - **No validation of what is already written.** `declare_meta_schema!` reads no record;
     the declaration governs what is appended from then on. A `rebuild` is what rewrites the
     rest.
   - What declaring buys, with no index: the value is the type it claims, so a filter
     compares in that type. A field declared `:timestamp` compares as an instant rather than
     as the text that stores it.
   - `:geopoint` of the section below was dropped with the index that justified it.
6. ~~**Out-of-vocabulary tracking** (§5)~~ Done on 2026-09-14, as two readings that answer
   different questions:
   - **Over the queries**, continuously and at no measurable cost: `ftsearch` tokenizes the
     query against the vocabulary's own `TextConfig` and counts the tokens it does not
     contain. The counters live in the project, are written when it closes and every 256
     queries, and survive a reopen. A process that is killed loses the queries since the last
     write; this is a drift signal, not accounting.
   - **Over the documents**, on request: `vocabulary_report(handle; scan=true)` re-tokenizes
     every live document. That is a pass over the whole project, which is why it is not the
     default, and it is what `describe` reports.

   The distinction decides whether a `rebuild` helps. The query rate says the words being
   asked for are missing, and a rebuild fixes that only if those words are in the documents;
   the document rate says the words the project already stores are missing from the
   vocabulary, which is exactly what refitting corrects. `GET /api/v1/datasets/{id}/vocab`
   reports both (§5.8's vocabulary endpoint), and `describe`'s own copy of the computation
   was removed in favour of the engine's.
7. ~~**The inverted `id`/`doc_id` of the wire**~~ Corrected on 2026-09-14. A search result
   reported the caller's identifier as `id` and the engine's as `doc_id`, which is the
   opposite of the record it came from and of what `/fetch` answered; `POST .../delete` took
   the internal identifier under the name `doc_id`. An item is now `doc_id` (the caller's,
   possibly null) and `_id` (the engine's, always present) everywhere, `delete` takes `_id`,
   `exists` reports both alongside the `id` that was asked about, and `/fetch` no longer
   repeats one of them as `id`. No aliases: nothing is released, and two names for one field
   is how the confusion started.
8. ~~**The token in the operation log**~~ Done on 2026-09-14. Every record stored the
   `Authorization` header verbatim, so the log of a dataset held live credentials, `dump`
   copied them into every bundle, and reading the log meant being able to impersonate the
   callers in it. A record now carries `user`, the name on the token when it was valid, and
   `token_fingerprint`, the first eight bytes of its SHA-256. The endpoint keeps requiring
   `admin`: the log no longer carries a credential, but it does say who did what, which is
   an audit surface rather than a reading of the dataset.

   **Still open, and of the same family:** the token database stores each token as its own
   RocksDB key, and `GET /api/v1/admin/tokens` returns them in full. Storing a hash instead
   would mean the token is shown once, when it is created -- which is what
   `similarity-search add-token` already does -- and that revoking one takes the fingerprint
   rather than the token, since the listing would no longer contain it.
9. **The request collector of §2** — its purpose is served, its structure is not built.
   On 2026-09-15 the query side gained a bound: `max_concurrent_queries` searches run at
   once, derived by default from the thread split, and a request that finds every slot taken
   waits for one. That is a semaphore around the four search handlers, ten lines, not the
   collector this document describes: a channel of pending requests and a pool of worker
   tasks that every search passes through.

   What is still open is whether the collector adds anything over the bound. It would allow
   ordering or dropping the queue, which a semaphore cannot, and it would move every search
   onto a worker task, which costs a channel round trip on a server that is not busy. The
   measurements that would answer this are now reported: `simsearch_queries_waiting`,
   `simsearch_query_wait_seconds_total`, and the histogram of request durations. A server
   whose waiting count stays at zero does not need either.

The stemmer registry of §5.3 and §9's phase 5 is not on this list: it was discarded. Stemming
was the way this specification proposed to make a query match a word it does not equal. That
is now the work of the query pipeline of `TextSearch.jl`, which the engine exposes through the
text profile and `QueryPolicy`: the profile carries lemma clusters and the expansion network,
and the policy applies orthographic correction and expansion to each query. Passages below
that describe `StemmerRegistry`, a `stemmer` field of `TextConfig`, or `Snowball` as a
dependency describe a design that was not built and will not be.

## 1. System Overview & Application Architecture

`SimilaritySearchServer` is a high-performance, vector and full-text search engine built on top of `SimilaritySearch.jl` (v1.2.0) and `TextSearch.jl` (v1.1.0). The system is designed to provide both standard vector database integration and advanced topological graph operations through a robust CLI and HTTP REST API. Both interfaces are almost equivalent and can do almost the same operations, but going coherent with their medium design; one important difference is that cli don't need tokens to access indexes and datasets.

* **Runtime Environment:** The application is packaged as a native Julia 1.12 App, utilizing the `[apps]` directive in `Project.toml` for standard installation and deployment without requiring static cross-compilation.

!!! warning "Julia version compatibility"
    `SimilaritySearch.jl`'s `Project.toml` pins `[compat] julia = "^1.10"`. Targeting the Julia 1.12 `[apps]` mechanism is fine (1.12 satisfies `^1.10`), but pin the *app's own* `Project.toml` to `julia = "1.12"` explicitly rather than leaving it open, since the `[apps]` directive is still a relatively new mechanism and behavior can vary across minor releases.


* **Three Command Line Interfaces (CLI):** The entry point (`@main`) utilizes `ArgParse.jl` strictly to handle startup arguments. Supported CLI commands include:
* Metric operations (similarity-search):
  * `build`: Creates an index with raw files that can be used to start in a warmup index for the web api, it can use dumped meta-data and vectors or h5 files for vectors; it accepts distances, a projection or a bitsketches or dimensional reduction or scalar quantization; it accepts reranking (in which case it saves both original and reduced-sketched-quantized data). It must support for arguments that allow to do everything, and the application ensure a nice interface to deal with all of these pipelines.

    !!! warning "Quantization/projection/sketching are not index constructor kwargs"
        In `SimilaritySearch.jl`, dimensionality reduction (`Projections` module: `RandomProjections`, `HadamardProjection`, and also `SphericalEmbedding` — a third transform for MIPS-to-metric-style embedding, with separate `transform`/`transform!` for the data side and `transform_query`/`transform_query!` for the asymmetric query side), binary sketches (`bitsketch`), and scalar quantization (`ScalarQuant` module) are **standalone transforms applied to the raw database** (`transform`/`transform!`), not keyword arguments accepted by `SearchGraph(...)` or `ExhaustiveSearch(...)`. The scalar-quantization type names need correcting too: it's `SQu2Vec`/`SQu4Vec`/`SQu8Vec` (plus matching `SQu2Database`/`SQu4Database`/`SQu8Database`), not bare `SQu2`/`SQu4`/`SQu8`; and `SQgu4`/`SQgu8` are **not struct/type names at all** — the `gu4`/`gu8` variants are `quantize(X; ...)` functions returning plain `UInt8` arrays, evaluated at search time via `Dist.NormCosine()`/`Dist.SqL2()`, not a bespoke quantized-vector type. The real `build` pipeline is therefore:
        1. Load raw vectors (h5 or dumped format).
        2. Optionally apply one transform (`transform!`) to produce a reduced/sketched/quantized `AbstractDatabase`.
        3. Build the index (`SearchGraph`/`ExhaustiveSearch`, or the data-parallel `ParallelExhaustiveSearch` — see the note below) over the *transformed* database.
        4. If `--rerank` is requested, additionally persist the *original* (untransformed) database, since `rerank!(dist, original_db, queries, knns)` needs the exact vectors and an exact distance function — the library does not manage two parallel representations for you.
        The `build` CLI flags should reflect this as an explicit pipeline (`--transform gaussian-projection:128`, `--rerank-with-original`), not as flat index-constructor options.

    !!! note "A third exact-search index type exists: `ParallelExhaustiveSearch`"
        Alongside `SearchGraph` (approximate, graph-based) and `ExhaustiveSearch` (exact, single-threaded scan), `SimilaritySearch.jl` also exports `ParallelExhaustiveSearch` — a data-parallel exact brute-force scan. For small-enough datasets, or as a ground-truth generator for §5.6 calibration, `build`'s `--index-kind` should offer this as a third option, not just `searchgraph`/`exhaustive_search`. This also means every place in this spec that enumerates dense `index_kind` values needs a third entry — see the correction to §1's one-index-per-dataset note below.

    !!! note "Rerank is straightforward given the one-index-per-dataset + join-dataset pattern above"
        Given the strict one-index-per-dataset rule, `--rerank-with-original` produces **two separate datasets that share the same `doc_id` sequence**: the primary dataset (transformed/reduced/quantized vectors, backing the actual `SearchGraph`/`ExhaustiveSearch` index that is searched) and a companion original-vectors dataset (no index — or a trivial flat/exhaustive one — just random-access-by-id storage of the exact vectors). `build --rerank-with-original` must therefore also record **two distance functions** in the index's metadata: the one the primary index was built/searched with (possibly a distance appropriate to the transformed space, e.g. Hamming for a bitsketch), and the exact distance used for the final `rerank!(exact_dist, original_db, queries, knns)` pass. At query time: search the primary (transformed) index for candidates, batch-fetch those candidate ids from the companion original-vectors dataset, then call `rerank!` with the exact distance. This is exactly the join-dataset use case above, just with "companion original-vectors dataset" playing the role of the metadata-holding dataset.

  * `searchbatch`: Executes heavy offline batch queries from file inputs, natively returning an `(ids, dists)` tuple; it uses a built index, note that this implies that understand all the set of possible variants in the index. `--edit-correction` (a flag, off by default) opens a text dataset with edit correction, the same setting `POST /api/v1/datasets` stores as `edit_correction`; the flag decides it for that run, independently of `descriptor.json`, and a dataset without text exits with code 2.
  * `allknn`: Executes heavy offline `allknn` operation. it uses a built index, note that this implies that understand all the set of possible variants in the index.
  * `neardup`: Executes heavy offline `neardup` operation. it uses a built index, note that this implies that understand all the set of possible variants in the index.
  * `fft`: Executes heavy offline `fft` operation. 
  * `hsp`: Executes heavy offline `hsp` operation. it uses a built index, note that this implies that understand all the set of possible variants in the index. It is solved with `hsp_queries`, it also requieres a set of queries, and the index to produce the input for `hsp_queries`.

    !!! warning "`fft`/`neardup`/`hsp` do not all require a pre-built index"
        Verified signatures in `SimilaritySearch.jl`:
        - `fft` and `dnet` (now under `SimilaritySearch.KCenters`) operate directly on the raw database, no index needed at all. E.g. `SimilaritySearch.KCenters.fft` is a diversity-sampling/clustering-seed routine, not a graph query.
        - `neardup` has two forms: `neardup(idx::AbstractSearchIndex, ctx, X, ϵ; ...)` (index-based) **and** `neardup(dist::PreMetric, X::AbstractDatabase, ϵ; recall=1.0, ...)` (index-free, builds a throwaway index internally at the requested recall). Either is valid depending on whether the user already has a persisted index to reuse.
        - `hsp` is **not an exported function name** — the real entry point is `hsp_queries(dist, X::AbstractDatabase, Q::AbstractDatabase, knns::AbstractMatrix)`, and it requires knn candidate lists (`knns`) computed beforehand (e.g. via `allknn` or a batch `search`), plus an explicit query set `Q`. The CLI command can still be named `hsp` for consistency, but its implementation must first obtain/compute `knns`, then call `hsp_queries`. Document this data dependency explicitly in the command's help text.
        - `allknn(g::AbstractSearchIndex, ctx, k; ...)` and `closestpair(idx::AbstractSearchIndex, ctx; min_k=8)` genuinely require a pre-built index — the original claim holds for these two only.

  * `describe`: Describe a dataset and its indexes; also extracts distance statistics and other useful metric statistic from a dataset to help people know about their data.
  * `rebuild`: Rebuild indexes for the given dataset, useful for many deletions. Use specific functions when available and full reindexing when no other way is possible.

    !!! note "Resolved: `rebuild` for full-text indexes is required and must be supported, not only for deletions"
        Confirmed: `TextSearch.jl`'s `Vocabulary` is built once from a training corpus; a token unseen at training time resolves to sentinel id `0` on lookup, and — verified in `bagofwords!` — is then **dropped outright** before it ever reaches a bag-of-words or posting list, not stored under id `0`. Documents appended later via `push_item!`/`append_items!` only ever read the existing `voc`, never mutate it — there's no automatic re-training. `rebuild` for a text index (`invfile | bm25_invfile`) must therefore support two modes: (a) a full re-tokenization/re-vocabulary pass (rebuilds `Vocabulary` from the current live document set and re-indexes from scratch — the only way to recover from vocabulary drift), and (b) a lighter "just compact posting lists" pass. Mode (b) is **BM25-only**: `filter_lists!` exists only on `BM25InvertedFile` — `InvertedFile` (which recently merged the old `WeightedInvertedFile` and `BinaryInvertedFile` into a single type in `SimilaritySearch.jl`) has no equivalent posting-list-compaction function, so `rebuild` on it only ever has mode (a) available; document this asymmetry in the CLI help rather than implying mode (b) applies uniformly across both text index kinds. Track an OOV-rate metric per text index (exposed via `describe`/`GET .../vocab`, see §5.4) as the trigger signal for when a full `rebuild` (mode a) is actually needed versus mode (b) being sufficient — `Vocabulary` already carries the raw counters this needs (`occs`, `ndocs`, `trainsize`, `avgdoclen(voc)`), see §5.4's update for the concrete APIs.

    !!! danger "Correction: `filter_lists!` does not exist anywhere in the current library source — mode (b) above isn't implementable yet"
        Grepped both `TextSearch.jl` and `SimilaritySearch.jl` (the local dev packages this app pins to) for `filter_lists!` or any other posting-list-compaction function on `BM25InvertedFile`/`InvertedFile`: nothing exists. The claim above ("mode (b) is BM25-only via `filter_lists!`") was accurate against an earlier library snapshot but is stale now — *neither* text index kind has any lighter compaction mode today, not just `InvertedFile` lacking BM25's. The CLI `rebuild` command (implemented — `execute_rebuild` in `cli_handlers.jl`) therefore only implements mode (a), uniformly for text *and* dense index kinds: a full reindex from the dataset's current live (non-tombstoned) documents. Since every dense/text index here is a dense array with no notion of a gap, purging tombstones means renumbering survivors to fresh sequential doc_ids (`1..n'`) and rewriting their metadata rows accordingly, not merely filtering in place — dense needed the same full-reindex treatment text always required, once it turned out neither kind has a lighter path. This also required persisting `deleted_ids` into the JLD2 snapshot for the first time (previously tombstones lived purely in a running server's in-memory `engine.deleted_ids`, invisible to a `rebuild` CLI subprocess); `handle_delete_item` now resaves the snapshot for this reason. For a `SearchGraph`, the fresh index is additionally passed through the real `SimilaritySearch.rebuild(g, ctx)` (a genuine library function — full topology recomputation seeing the whole survivor set at once, distinct from and not a replacement for the reindex itself) as a bonus optimization pass. If a future library version ships a real compaction primitive, mode (b) can be added as a lighter alternative then — don't add a CLI flag for it before it exists.

* Server (`similarity-search-serve`):
  * `serve`: Binds to a host/port and starts the web server in the current (or given) dir as working directory (place to store metadata, RocksDB databases); always foreground yet possible attached to a tmux. This is the only command this binary exposes — it is deliberately a thin, single-purpose entry point so it can be the unit that gets supervised (systemd/tmux/container `CMD`), restarted, and resource-capped independently of the administrative tooling below.

    !!! note "`serve` has two responsibilities, not one: it is both the HTTP/API server and the heavy-Job dispatcher"
        `similarity-search-serve` is the process that binds the HTTP/API surface (§5) **and**, in the same process, runs the §2 Internal Application Scheduler and the §5.5 `JobExecutor` that dequeues `queued/` jobs from the spool and dispatches their `LocalCLIExecutor` subprocesses against the reserved 20% compute pool. There is no separate job-dispatcher binary or background daemon — dispatching heavy jobs is an explicit second responsibility of this one command, on par with answering requests, not an incidental side effect of the HTTP layer being up. Consequently `serve` going down (crash, restart, `systemd`/container supervision cycling it) also stops job dispatch: any job left in `running/` when that happens is picked back up (or requeued) on the next `serve` startup by replaying the spool exactly as §5.5 already describes for crash recovery — the same process boundary that owns request-serving is the one that must own that recovery step, since it's the only thing with the `queued/`↔`running/` `rename` ownership (§5.5).
* Admin and operative (`similarity-search-ctl`):

    !!! note "`admin` is a control-plane client, not a second process touching the same RocksDB files"
        RocksDB's exclusive process-level lock is real for **writers**: a second OS process cannot safely open the same column families for writing while `similarity-search-serve` already holds them, and `RocksDB.jl` doesn't work around that. Correction to a previous claim here: `RocksDB.jl` *does* ship a first-class, ergonomic `opendb(path; read_only=true, column_families=...)` mode explicitly documented for "inspecting a database another process still has open for writing" — so a local `admin` process reading `list`/`log`/`stats` directly off the RocksDB files, concurrently with a running `serve`, is technically supported by the library, not just unsafe-but-tempting. The resolved design still has `similarity-search-ctl` talk to a *running* `similarity-search-serve` instance over HTTP for every command below — but the reason is **consistency and correctness, not a hard technical wall**: one code path regardless of whether `admin` is local or remote; a `dump` that needs a consistent point-in-time view across CFs (RocksDB's own hand-written `Snapshot`/`RocksDBSnapshotView` API, §4.2, is the right tool for that, and only the process already holding the DB open conveniently has one); and `kill` needing to reach a process handle the *server* itself tracks rather than `admin` guessing at a pid from a stale file. By default it targets `http://127.0.0.1:<port>` (or a unix socket) of a server in the same workdir and authenticates with a local admin credential auto-provisioned into the workdir on first `serve` (a file only the workdir owner can read) — so, consistent with the "CLI doesn't need tokens" principle noted in this document's introduction, a local operator never has to manage a token by hand. Pointing `admin` at a *remote* server (`--host`/`--port`) requires passing an explicit admin-scoped token instead, since there is no workdir to read the local credential from. If `similarity-search-serve` is not running, `list`/`log`/`stats`/`dump` fail with a clear "server not reachable" error rather than silently reading stale files — a deliberate choice to keep one behavior, even though a read-only local fallback is technically possible now that `opendb(read_only=true)` is confirmed to exist; adding that fallback later is a pure availability optimization, not a correctness fix. `jobs queue|result|block|resume|kill|gc` are the one exception where a *local* `admin` could in principle bypass HTTP and manipulate the `jobs`/`cursors` spool directories (§5.5) directly, since those are plain files safe for multiple processes to touch — but `admin` still goes through the HTTP surface by default even for these, so there's one code path regardless of whether `admin` is local or remote, and so `kill` reliably reaches a process the *server* knows about (rather than `admin` guessing at a pid from a stale file).

  * `list`: Lists available datasets/indexes known to the running server.
  * `log`: Extract logs from the given index (proxied from the server's view of its own `*_log` column families).
  * `stats`: Extract and compute statistics usage and costs from the given index.
  * `dump`: Exports graph topology and metadata for backup/migration purposes. Implemented as submitting a `dump` Job (§5.5) and downloading its result once done.
  * `load`: Imports indexes and datasets from dumps (prev output). Implemented as a `load` Job.

    !!! warning "`dump`/`load` need a persistence format that doesn't exist yet in either library"
        Neither `SimilaritySearch.jl` nor `TextSearch.jl` ships save/load for their index structs (`SearchGraph`, `InvertedFile`, `BM25InvertedFile`) — confirmed by source inspection (no `serialize`/`save`/`load` anywhere in either package). `dump`/`load` (and crash recovery) require building this serialization layer from scratch. See the new **§4.4 Persistence Layer (JLD2 for index snapshots, Avro for datasets & wire format)** below for the chosen design.

  * `add-token`: Add a token for the index with the specific permisions (appends, searches, allknns, etc.) must record the creation time, and the expiration time. Useful for remote applications accessing the index.
  * `del-token`: Delete a token
  * `prune-tokens`: Delete tokens already expired.
  * `log-tokens`: List the log of tokens (added and deleted, backed in the same dataset of tokens with different column families)
  * `jobs queue`: Lists jobs currently queued/running (HTTP-proxied `GET /api/v1/jobs`, see §5.5).
  * `jobs result <job_id>`: Fetches a finished job's result payload.
  * `jobs block <job_id>` / `jobs resume <job_id>`: Pauses a *queued* job so the scheduler skips it (e.g. to let other jobs drain first), and releases it back into the queue. Adds a `blocked` status to the Job state machine (§5.5), distinct from `cancelled`.
  * `jobs kill <job_id>`: Forcibly terminates a *running* job (sends the terminate signal to its `executor_handle` via the `JobExecutor`'s new `kill(handle)` method — see §5.5 update). Distinct from the existing best-effort `DELETE /api/v1/jobs/{job_id}`, which only applies to not-yet-started jobs; `kill` is the explicit, always-available operator override for a job already consuming the reserved compute pool.
  * `jobs gc`: Garbage-collects finished/expired jobs and their result artifacts past retention, **and** expired result cursors (§5.4) — see new §5.5 warning on cursor storage/GC below. Same command surfaces both because they share the same lease/expiry protocol.

### Interactive Mode (Term.jl-guided CLI, new)

Both `similarity-search` and `similarity-search-serve` must offer an **interactive mode** alongside their normal flag-driven invocation: a guided session where every command the binary supports is reachable from a menu, and every argument/option of the chosen command is presented as a prompt **pre-filled with a sensible default** rather than a blank field the operator has to fill from memory.

* **Entry point:** every binary keeps its traditional flag-driven CLI as the default for every existing command — nothing about today's non-interactive invocation changes. Interactive mode is entered exclusively through one new, explicit `interactive` subcommand (e.g. `similarity-search interactive`, `similarity-search-serve interactive`), never implicitly (not by omitting a command, not by a bare `-i` flag) — this keeps "no arguments" a normal ArgParse usage/error case rather than an ambiguous mode switch, and keeps interactive mode strictly additive: it must never change what the non-interactive parser accepts, since §5.5's `LocalCLIExecutor` depends on that surface staying script-stable.
* **Command menu:** for `similarity-search`, the first screen lists its full command set (`build | searchbatch | allknn | neardup | fft | hsp | describe | rebuild`, §1) as a selectable menu. For `similarity-search-serve`, whose design (§1, intro) deliberately restricts it to the single `serve` command so it stays a thin, supervisable unit, the menu degenerates to that one guided form directly — interactive mode there is about not hand-writing flags, not about choosing among commands. Since `serve` is both the HTTP server and the heavy-Job dispatcher (§1's note above), that one form spans both roles' options: HTTP/API bind settings (`--workdir`, `--host`, `--port`), *and* the dispatcher-side settings that used to only be reachable by flag — `--query-threads-pct` (the §2 80/20 core split), the §3 Long-Lived Search Policy mode (`deny | warn_only`), and the Job-side knobs from §5.5 (e.g. which `JobExecutor` backend, and its concurrency cap within the reserved pool). It is one guided form, not two, because it's one process with two responsibilities.
* **Per-argument prompting:** once a command is picked, walk its arguments one at a time. Enumerated-choice options render as a selection menu, not free text — `--distance` (from the `DistanceRegistry`, §3), `--index-kind` (`searchgraph | weighted_invfile | binary_invfile | bm25_invfile`), `--transform` (§1's projection/sketch/quantization pipeline), `--stemmer` (from the `StemmerRegistry`, §5.3). Boolean flags render as a Yes/No prompt. Every prompt shows and accepts its default on a bare Enter.
* **Pre-filled options must be dynamically discovered, not just the parser's static defaults.** "Pre-filled" should mean more than falling back to whatever default `ArgParse.jl` declares — where a valid value is knowable from the current workdir, offer it as the selectable/default choice instead of asking the operator to type or remember an id: existing dataset/index UUIDs discovered by scanning the workdir (the same listing `describe`/`list` already produce), a `key`'s already-declared join-group members (§5.3) when prompting for which text field to index/query, a dataset's already-declared `MetaSchema` fields (§4.5) when building a `filter`. This is the concrete meaning of "menus and pre-filled options" for this spec — static ArgParse defaults alone would not satisfy it.
* **Single source of truth: derive the interactive menu tree from the same `ArgParseSettings` used for non-interactive parsing.** Each command's arguments, types, defaults, choice-lists, and help strings are already declared once, in the `add_arg_table!` calls backing the ordinary CLI (§1). The interactive layer must introspect that same settings object rather than maintaining a second, hand-written description of "which args exist for which command" — two independent copies of that mapping will drift the moment one is edited and the other isn't.
* **Confirm-before-run:** after all arguments are collected, render the fully assembled command (as the exact equivalent non-interactive invocation, e.g. `similarity-search build --dataset ... --distance L2 --transform sq_u8`) in a panel for the operator to confirm before it actually runs — this doubles as a way to learn the flag-driven form for later scripting, and as the one point where the operator can back up and re-edit a single field instead of restarting the whole flow.

!!! warning "Term.jl (v1.2.0, verified locally) ships almost no interactive input capability — don't assume it provides menus/prompts out of the box"
    Checked against the locally available package (`~/.julia/packages/Term/TgMii`, `Project.toml` version `1.2.0`): the only file containing prompt/menu-shaped code, `src/prompt.jl` (`AbstractPrompt`, `YNPrompt`, `ask`), is **not `include`d anywhere in `src/Term.jl`** — it is not part of the loadable package at all, and none of those names appear in `Term.jl`'s `export` list. What Term.jl actually, verifiably provides is rendering: `Panel`/`TextBox` (framed sections for each prompt step and the final confirm screen above), `Term.Tables.Table` (the assembled-command summary), `Term.Trees.Tree`/`Term.Dendograms.Dendogram` (the command menu / help hierarchy), `Term.Progress.ProgressBar` (progress for a long-running command launched from interactive mode), `tprint`/`Compositor` (styled multi-panel layout). None of this handles a keypress loop, arrow-key highlighting, or an editable pre-filled text field. **Resolved approach:** pair Term.jl (visual rendering) with the Julia stdlib `REPL.TerminalMenus` (`RadioMenu`, `MultiSelectMenu`, `request`) for the actual selection/input loop — it already implements exactly this interaction pattern and ships with every Julia install, so it needs no extra dependency — rather than building a keystroke-handling loop from scratch or wrongly assuming Term.jl supplies one.

!!! warning "Even with `interactive` as an explicit subcommand, still gate it on a real TTY — defense in depth against deadlocking a Job-spawned subprocess"
    Requiring the explicit `interactive` subcommand (rather than "no arguments") already makes it very unlikely that §5.5's `LocalCLIExecutor` — which spawns "the exact same CLI command a human would run offline" as an unattended subprocess and blocks on its exit code — would ever generate `cli_args` containing `interactive` in the first place. But it costs little to also have the `interactive` subcommand's own entry point check `isatty(stdin)` and refuse to start (fail fast with a normal error, not a hang) when it isn't attached to a real terminal — a cheap backstop in case a job's generated arguments are ever malformed, a wrapper script mistypes a command, or a future refactor of the Job-submission path introduces the bug the check exists to catch. Without it, that failure mode is a silent hang on `readline()`/`REPL.TerminalMenus.request` with no human on the other end, which — since Job execution is capped by the §2 reserved-pool size — can eventually starve the whole Job pool rather than surfacing as an obvious error.

### Data architecture

- It works on a working directory, all datasets, indexes, logs, etc are under this working directory, by default the directory where it was launched
- It works on foreground mode, sending log outputs to console, yet also saving them in RocksDB.jl datasets
- The way it is expected to work is to be run in a docker container or a full machine with a limit in computer resources (threads, memory) and launch julia under these resources
- The core data is to maintain a dataset depot, where each dataset is a directory/RocksDB database where a number of indexes can live.
- **Resolved design: strictly one index per dataset.** Although `SearchGraph`, `ExhaustiveSearch`, `ParallelExhaustiveSearch`, `InvertedFile`, and `BM25InvertedFile` all implement the same `push_item!`/`append_items!` interface and *could* be fed from one shared dataset in parallel, this application does not need that flexibility and the extra bookkeeping it requires (a separate `AbstractContext`, log/WAL stream, and rebuild policy per index type sharing one id space) isn't worth carrying. Each dataset directory/RocksDB database backs exactly one index (`searchgraph | exhaustive_search | parallel_exhaustive_search | invfile | bm25_invfile`) — the two exhaustive kinds cover `SimilaritySearch.jl`'s exact brute-force index types, useful for small datasets or as a calibration ground-truth generator (§5.6), alongside the approximate `SearchGraph`. This simplifies §3's context pooling, §4.2's column-family layout, and §4.4's snapshot format to a strict 1:1 dataset↔index mapping.

  !!! note "Use case: multi-representation search (e.g. hybrid) via a join dataset, not multiple indices per dataset"
      The scenario that used to motivate "multiple indices over one dataset" — e.g. dense semantic search *and* BM25 lexical search over the *same* logical documents — is instead handled with **multiple single-index datasets sharing a common `doc_id` space, plus one designated dataset holding the full metadata for random-access-by-id batch retrieval.** Concretely: create one dataset per representation (a `searchgraph` dataset over dense embeddings, a `bm25_invfile` dataset over the raw text), each storing only the minimum it needs to build/search its own index (vectors, or tokenized text) plus the shared `doc_id`. Exactly one of these datasets — or a dedicated metadata-only dataset with no index at all — carries the *complete* metadata record per `doc_id` and answers `GET /api/v1/simsearch/{index}/fetch?ids=...`-style batch exact-id lookups; the others carry only the minimal join key (`doc_id`) needed to look up that metadata by id after a search. Fusion (§6) and rerank (see the updated `build` warning below) both reduce to: search the smaller per-representation index(es), then batch-`fetch` the join dataset by the resulting ids to hydrate metadata/original vectors before merging/reranking. This pattern should be documented explicitly as the recommended way to model hybrid or multi-representation search, since it is the direct consequence of the strict one-index-per-dataset rule above.

      This same pattern generalizes beyond "one dense + one lexical" to **N per-field text indices**: a join group can hold any number of lexical-index members, each tagged with a `key` (e.g. `"title"`, `"body"`, `"tags"`) identifying which text field it indexes, alongside zero or one dense member and the metadata-holding member. See §5.3 for how `ftindex`/`ftsearch` address a specific `key` (or fan out to all of them).

- Deletes must be supported but through weak/soft deletes, where each deletion is marked through a bit array; note that this may reduce the number of elements that are retrieved.

  !!! warning "Soft deletes are not a library feature — must be built entirely at the application layer"
      Grepped `SimilaritySearch.jl` for tombstones/soft-delete/bit-array exclusion: nothing exists. There is no `mark_deleted!`/`remove!`, and indexes only support append-style growth. A bit-array tombstone filter must be designed and applied by this application at the result-post-processing layer (filter candidate ids after `search`/`allknn`/etc., before returning results), and its interaction with recall must be documented: a beam-searched `SearchGraph` may return fewer than `k` *live* results if many top candidates are tombstoned, since the graph traversal itself has no notion of exclusion — it filters after the fact, not during beam expansion. For workloads with a high delete ratio, this can silently degrade recall; the plan should require the `describe`/`stats` commands to report the current tombstone ratio per index so operators can decide when a `rebuild` is warranted.

- Since each dataset now backs exactly one index, operations that used to need disambiguation ("which index on this dataset?") no longer do; the only remaining disambiguation is at the *fetch/join* layer above — the operator must specify which dataset in a join group is the metadata-holding one when it isn't the obvious default.

## 2. Concurrency & Resource Management

The system is built to maximize hardware utilization while preventing resource exhaustion during heavy analytical queries.

* **Threading Model:** The application defaults to Julia's `:dynamic` thread scheduler (`Threads.@spawn :dynamic` or `Threads.@threads :dynamic`) to allow the runtime to migrate tasks efficiently across available OS threads.
* **Internal Application Scheduler:**
* **Request Collector:** Incoming HTTP requests do not spawn direct search threads. Instead, they are parsed and pushed into an internal asynchronous queuing system (e.g., `Channel`).
* **Workload Segregation:**
* *Heavy Workloads* (`searchbatch`, `allknn`, `fft`, `closestpair`, `neardup`, `hsp`): These operations consume the entire thread pool compute capacity. When active, the scheduler temporarily pauses or queues standard query ingestion.
* *Standard Queries* (`search`): Individual queries run in parallel, competing for standard worker availability. If workers are saturated, requests are held in the collector until resources free up.
* **Resolution:** Worker tasks execute the operations and route the results back to the specific waiting HTTP handler via callback channels.

!!! warning "Fully pausing standard queries during heavy workloads may be an availability problem in production"
    If `serve` is meant to run as a long-lived production endpoint (not just a batch tool), letting any `allknn`/`neardup`/`fft`/`closestpair`/`hsp` job fully starve live `search` traffic means a single administrative job can take the whole service down from the caller's perspective for its entire duration (which, for `allknn` over a large dataset, can be minutes to hours).

**Resolved design:** `serve` starts with a fixed core/thread split, configurable but defaulting to **80% for standard query traffic / 20% reserved for Job execution** (`--query-threads-pct 80`). The 80% pool is the in-process `:dynamic` scheduler described above, serving `search`/`ftsearch`/`upsert` etc. directly. The 20% pool is *not* used to run heavy library calls in-process — it bounds how many concurrent Job executions (§5.5) may run at once, each one dispatched as its own CLI subprocess capped to that thread budget (`JULIA_NUM_THREADS=<reserved_threads>`). This turns "pause everything" into a hard, sized ceiling instead of an all-or-nothing stall, and — because Job execution is just "run the CLI command" — the exact same split and executor abstraction is what allows migrating heavy Job execution off-box to Slurm (`sbatch`/`srun`) later without changing the Job registry, the HTTP surface, or the CLI commands themselves. See §5.5 for the executor design.

## 3. Core Engine & Distance Resolution

* **Distance Registry Module:** Distance function resolution must be isolated in a dedicated internal module (e.g., `DistanceRegistry`).
* String-to-distance resolution must be executed safely via `getproperty(DistanceRegistry, Symbol(distance_name))`.
* This registry explicitly imports and exposes valid distance functions from both `SimilaritySearch.jl` and `Distances.jl`.

!!! warning "Almost no distance function is actually exported from `SimilaritySearch.jl` — the registry must be hand-built from qualified names, not from reflection against the module's own exports"
    Grepped every `src/dist/*.jl` file: every distance-function `export` line is commented out (`L1`/`L2`/`SqL2`/`Lp`/`LInfty` in `vecs.jl`, `Cosine`/`Angle`/`NormCosine`/`NormAngle` in `cos.jl`, `Hausdorff`/`Chamfer` in `cloud.jl`, `Jaccard`/`Dice`/... in `sets.jl`, `Hamming`/`LCS`/... in `seqs.jl`). The **only** distance actually exported at the top level is `RussellRao` (`src/dist/bits.jl`) — everything else must be qualified through the package's internal `Dist` submodule (`Dist.L2()`, `Dist.Cosine()`, `Dist.SqL2()`, ...). `getproperty(DistanceRegistry, Symbol(distance_name))` as proposed above still works fine, but only because `DistanceRegistry` is expected to explicitly re-export/alias each supported name itself — it is **not** a shortcut for reaching into `SimilaritySearch`'s own namespace directly, since there's almost nothing exported there to reach into. Build `DistanceRegistry` as an explicit `Dict{String,Any}`/set of `const` bindings mapping each supported string name to a constructed `Dist.XXX()` instance, covering exactly the distances this server intends to expose — not as a reflective lookup against `SimilaritySearch`'s or `Distances.jl`'s export lists, since at least one of those lists is nearly empty.

* **Context Management:** Global or pooled context objects (`SearchGraphContext`, `InvertedFileContext`) must be maintained in memory to eliminate allocation overhead during request serving; we need up to nthreads() thread workers at the time; then it is important to have several one thread context (up to nthreads()); and just a couple of context using the full assigned pool (one per kind of index). Note that this is by user or index level to be safe accounted (We always can do fill! to zeros operation and capture the costs after finish; this may also work for delta real time costs).

  !!! note "`InvertedFileContext` belongs to `SimilaritySearch.jl`"
      `SearchGraphContext` and `InvertedFileContext` are both defined in `SimilaritySearch.jl`. Previously, `InvertedFileContext` was in `TextSearch.jl`, but it was moved when `InvertedFile` was merged into `SimilaritySearch.jl`. `BM25InvertedFile` in `TextSearch.jl` still uses this context. Both are legitimate `AbstractContext` subtypes and the pooling strategy described here is sound for both.

!!! warning "`InvertedFile` thread-safety — verify before relying on concurrent multithreaded appends"
    Given this spec's plan to pool `InvertedFileContext`s up to `nthreads()` (above) and serve concurrent `append`s against the same index, write a targeted concurrent-append stress test against `InvertedFile` before depending on it, or serialize appends to it behind an application-level lock as a safety net regardless of what the library claims to guarantee internally. "Verify, don't assume" should apply generally before this spec locks in a per-index-type concurrency model.

* **Safety Safeguards:** The Core execution barrier must validate `BeamSearch` hyperparameters. If a payload requests excessively high parameters (e.g., extremely large `bsize`), the system must log a `WARN` event and return an HTTP warning header indicating potential performance degradation. We can also put a global barrier on these parameters and maxvisits parameter, to ensure be safe operation. For isntance, index operator (user) must not be able to increase `maxvisits` beyond 2 or 3 times the computed one, and follow that \Delta < 1.7, and bsize <= 20.

  !!! warning "Hardcoded global safety thresholds lack a defined baseline ('the computed one')"
      `BeamSearch`'s real fields/defaults (from `SimilaritySearch.jl` source) are `bsize::Int32=4`, `Δ::Float32=1.0`, `maxvisits::Int64=10^6`. The plan says operators can't exceed "2 or 3 times the computed one" for `maxvisits`, but never defines what computes that baseline, and `bsize <= 20` / `Δ < 1.7` are asserted with no justification. These should not be global constants — they should be derived **per index**, from the Hyperparameter Calibration step (see new §5.6), which already needs to run a `SearchModels`-driven parameter sweep against ground truth to pick good defaults for that specific dataset/distance/dimensionality combination. Store the calibrated `(bsize, Δ, maxvisits)` baseline alongside the index's metadata, and define the safety multiplier (e.g. 3×) relative to *that* stored baseline, not a hand-picked global constant.

* **Long-Lived Search Policy:** Independently of the per-request `bsize`/`maxvisits` multiplier barrier above, the server must support a configurable policy for *denying* searches whose estimated cost (in distance evaluations, derived from the same calibrated baseline) exceeds an operator-set threshold, rather than only warning about them. Default behavior: **deny with HTTP `429`** before execution, with a response body pointing the client at `POST /api/v1/jobs/search` (see §5.5) to resubmit the same query as an async Job instead of a blocking call. This applies to any endpoint that triggers a synchronous index traversal (`/simsearch/{index}/search`, `/simsearch/ftsearch`, hybrid search) — the policy lives here, at the Core execution barrier, so it isn't duplicated per endpoint. The policy mode itself (`deny | warn_only`) should be a workdir-level config, not hardcoded, since a trusted internal deployment may prefer `warn_only`.

## 4. Telemetry, and Persistence

The system tracks resource usage comprehensively for billing and performance monitoring, utilizing `RocksDB.jl` for persistence.

### 4.1. Identity Model

The system is limited to resources given as running input; we can use julia and linux tools for this. Access control to operations and indexes are driven by tokens, and handled by CLI and WEB interface for admin.

* **Index Entity:** Contains `index_uuid`.
* **Identity is handled via tokens:**, a token comprises user and index access; a token is a validated dataset of keys and ACL (operations and index permisions); it must be managed via a dedicated RocksDB table; global for the running server (workdir).

### 4.2. Database Design (`RocksDB.jl`)

Data is isolated using distinct Column Families in RocksDB, one per index/dataset; one directory in the working dir (pattern workingdir/data/{uuid-of-the-project-as-rocksdb-dbname})

* each project (dataset) holds exactly one index (§1) plus its own metadata
* `meta`: Stores the standard mapping of `(doc_id -> metadata_dict)`, shaped per the declared/typed + `extra`-blob split in §4.5.
* `meta_idx_<field>`: One optional CF per declared-and-`indexed` metadata field (§4.5), mapping value → sorted `doc_id` list, backing pre-filtering for that specific field.
* `op_log`: Stores the usage telemetry and distance accounting.
* `searchgraph_log`: Stores the incremental Write-Ahead Log (WAL) of the graph's topology. It stores as key 0 the header of the struct, not the dataset.
* `ftindex_log`: is similar but for vectors to be appended into the inverted index (`InvertedFile`). It stores as key 0 the header of the struct, not the dataset.
* `bm25index_log`: is similar but for vectors to be appended into the inverted index (BM25). It stores as key 0 the header of the struct, not the dataset.

  !!! note "The Job registry and result cursors are deliberately *not* RocksDB column families — see §5.5"
      An earlier draft of this plan put `jobs`/`result_cursors` in RocksDB CFs. Moved out to a plain spool directory instead (§5.5), specifically because RocksDB only ever has one process holding the write lock on a given DB — fine for `meta`/`*_log`, which only `similarity-search-serve` ever touches, but awkward for job state, which the `LocalCLIExecutor`'s spawned *child* CLI process also needs to update as it progresses, without going through the parent for every tick.

!!! note "RocksDB.jl provides backup, compaction, and TTL APIs natively"
    `RocksDB.jl` now ships with ergonomic Tier 2 APIs for `BackupEngine`, TTL databases, and manual compaction. You don't need to write raw `ccall` bindings or use the Tier 1 escape hatch for these features.

!!! note "What IS ergonomic and tested — worth designing around rather than reinventing"
    `RocksDB.jl`'s hand-written Tier 2/3 layers already cover several things this spec's data paths need, beyond plain `put!`/`get`/`delete!`:
    - **Range-scan iterator** (`DBIterator`, per-CF and snapshot-aware, `for (k,v) in DBIterator(db)`) — exactly what `meta_idx_<field>`'s value→sorted-`doc_id` scans (§4.5) and `op_log` telemetry range scans need, with no Tier-1 drop-down required.
    - **`WriteBatch`/`batch(f, db) do wb ... end`** — atomic multi-key, multi-CF writes; relevant for keeping a `meta` write and its `meta_idx_<field>` secondary-index update consistent, and for batching `op_log` telemetry writes.
    - **Hand-written, tested `Snapshot`/`RocksDBSnapshotView` (do-block or Tier-3 form)** — a genuine point-in-time-read capability, distinct from (and not to be confused with) the raw-ccall on-disk checkpoint/backup features above. This is the right tool for §4.4's `dump` to get a consistent cross-CF read without racing concurrent writers, and for the read-only-adjacent scenario discussed in §1's `admin` note.
    - **`property(db, name; cf=...)`** — cheap per-CF introspection (e.g. `"rocksdb.estimate-num-keys"`, `"rocksdb.stats"`) usable by `describe`/`stats` without a full scan.
    - **Known gap to plan around: `ColumnFamily` handles are never explicitly destroyed** (no caller of `rocksdb_column_family_handle_destroy`) — a native-handle leak on every CF open/close cycle. This spec's design creates CFs dynamically and somewhat often (`meta_idx_<field>` per newly-declared-and-indexed metadata field, per-dataset CFs on every `POST /api/v1/datasets`, deleted on every `DELETE /api/v1/datasets/{uuid}`) — a long-running `serve` process that sees a lot of dataset/schema churn should be assumed to leak native memory until this is fixed upstream or worked around; track it as an operational risk, not just a code-quality nit.

### 4.3. Callback-Driven Logging & Accounting

* **Event Handling:** Telemetry and graph persistence are strictly implemented via the native `LOG` callback handler provided by `SimilaritySearch.jl` v1.0.0.
* **Usage Accounting (`op_log`):**
* Cost metrics are extracted directly from the `SimilaritySearch` context cost counters — concretely `distance_evaluations`/`block_evaluations`/`distance_stats`/`block_stats` (`src/SimilaritySearch.jl`), which already support a snapshot-diff form (read before/after an operation and subtract) — and measuring delta times, log dimensionality of data, and operation made.
* Logged telemetry must capture: `token`, `index_uuid`, `distance_name`, `dimension`, `distance_evaluations` (as `Int64`), and the **delta computing time** (elapsed execution time).

!!! note "Resolved (chunk 17): wired into request handlers, real content, log endpoint + ctl command complete the loop"
    A real, previously-latent bug was found and fixed: `log_operation` called `RocksDB.put(db, cf, key, value)`, but the real function is `put!(db, key, value; cf=...)` (bang, keyword `cf`) -- never caught before since nothing called `log_operation` at all until now. `Telemetry.snapshot_costs`/`log_request!` (diff `SimilaritySearch.distance_evaluations` + elapsed time) are now called from `_run_search` (shared by `handle_search`/`handle_ftsearch`), `handle_append`, and `handle_delete_item`. `token` reads an `Authorization` header if present but is NOT validated anywhere (§4.1 auth enforcement is still unimplemented). `handle_hybrid_search`/`handle_ftsearch_group` are deliberately not wired (each spans more than one dataset's `op_log`). New `GET /api/v1/datasets/{id}/log` + `similarity-search-ctl log` complete PLAN.md §1's admin command enumeration.

* **Graph Persistence (`graph_log`):**
* The `LOG` handler captures incremental topological updates, storing strictly the direct links (neighbor arrays) as the graph grows, allowing for crash recovery without full recalculations.

!!! warning "The `LOG` callback is coarser than a per-edge topology diff stream"
    Verified against `SimilaritySearch.jl` source (`src/log.jl`, `src/searchgraph/log.jl`): `LOG(log, event, index, ctx, sp, ep)` fires on graph-growth operations with a *range* `sp:ep` of affected ids — it's a throttled progress/telemetry hook (used by the built-in `InformativeLog` to print memory/size summaries, and by a `SearchGraph`-specialized override to additionally report neighborhood-size quantiles), not a structured per-edge "edge (i,j) added" event stream. The `:add!` event symbol is confirmed to fire this way; whether `:push_item!`/`:append_items!` fire their own distinct `LOG` events (versus `:add!` being the one event name used internally for both) wasn't confirmed at the call site and should be spot-checked against `src/searchgraph/insertions.jl` during implementation rather than assumed from this spec. Either way, treat `LOG` as the trigger point at which *this application* reads the current state of `index.adj[sp:ep]` and writes those neighbor arrays to `searchgraph_log` itself — the library doesn't hand you a topology diff, you compute it by reading the affected range at each callback invocation.

### 4.4. Persistence Layer (JLD2 for index snapshots, Avro for datasets & wire format)

!!! warning "Neither SimilaritySearch.jl nor TextSearch.jl ships index serialization — this entire layer is net-new application code"
    This is the single biggest scope item this spec was previously silent about. `dump`/`load`, crash recovery, and warm-starting the web server from a working directory all depend on being able to fully reconstruct `SearchGraph`, `InvertedFile`, and `BM25InvertedFile` instances from disk — and there is no `save`/`load` for any of them in either package (verified by source inspection). Design this explicitly rather than assuming it falls out of "storing the log in RocksDB."

!!! note "TextSearch.jl's own docs independently corroborate the JLD2-for-snapshots choice below"
    Neither package ships a bespoke `save!`/`load!` API, but `TextSearch.jl`'s tutorial (`docs/src/tutorial.md`, "Saving and loading indexes with JLD2") explicitly documents that `Vocabulary`, `VectorModel`, `BM25InvertedFile`, and `InvertedFile` are "plain Julia structs" that `JLD2.jl` — an external, non-dependency package — round-trips with zero glue code. This is useful external validation that the JLD2-for-index-snapshots design below is the officially-sanctioned persistence story for these structs, not just this spec's own invention — it also means `SearchGraph`, being likewise a plain struct with `Vector{Vector{Int32}}` adjacency, should JLD2-round-trip directly with little or no custom `SearchGraphSnapshot` wrapping logic beyond what's already planned for the calibrated-baseline/header fields.

**Resolved design — split by purpose, not one format for everything:**

* **`JLD2.jl` for index struct snapshots.** `SearchGraphSnapshot`/`InvertedFileSnapshot` (adjacency lists, posting lists, headers, calibrated `BeamSearch` baseline, `Vocabulary`, etc.) are pure in-memory Julia structures that only this application ever reads back — there is no cross-language consumer for a graph's raw adjacency representation. JLD2 (HDF5-based, `FileIO.jl`-integrated) serializes arbitrary Julia structs directly, with no hand-written schema per struct and no schema-evolution ceremony for internal-only fields, which is exactly what index snapshots need and what hand-modeling `SearchGraph`'s adjacency lists as Avro records does not buy us. `save`/`load` of `SearchGraphSnapshot`/`InvertedFileSnapshot` is now a thin wrapper over `JLD2.save`/`JLD2.load`.
* **Avro (`Avro.jl`) stays for two things where cross-language interop and streaming actually matter:**
  1. **Dataset content** — the raw vectors/text and their `MetadataRecord`s, i.e. exactly what `dump` needs to hand back to a non-Julia consumer (a bulk export/import format any Avro-capable tool can read), and what a fresh `load` re-ingests to rebuild a dataset before it gets re-indexed or its snapshot reattached.
  2. **Binary wire format for the HTTP API** — request/response bodies for the bulk endpoints (`upsert`, `query_batch`, `fetch`) are Avro-encoded rather than JSON when the client opts into the binary content type, avoiding per-request JSON (de)serialization cost for large batches while remaining readable by any Avro client, not just Julia ones.
  * `TokenRecord` (§4.1) and `JobRecord` (§5.5) are small control-plane records with no cross-language transfer requirement of their own; keep them as plain RocksDB CF values (e.g. `JSON3.jl`) rather than pulling Avro in for them.
  * `BSON.jl` remains the fallback for any Julia-specific value that doesn't map cleanly onto an Avro schema (e.g. `Ref`-wrapped fields, `SIMD`-backed vector types) when encoding dataset content.

!!! warning "Avro.jl is a young dependency — mitigate with round-trip tests"
    Confirmed in the local Julia General registry: `Avro.jl` has shipped only two versions (`1.0.0`, `1.1.0`) as of this writing. It leans on `StructTypes.jl` for the struct↔schema mapping, which is a mature, widely-used pattern (same one `JSON3.jl` uses), so the risk is moderate rather than high — but budget for writing exhaustive round-trip (serialize→deserialize→structural-equality) tests per Avro schema before relying on it for dataset dump/load, and pin an exact `Avro.jl` version rather than a loose `^1` compat bound until it's been exercised in this project. `JLD2.jl` is comparatively low-risk (mature, widely used for exactly this kind of "serialize my Julia structs" job) but still needs round-trip tests per snapshot struct, plus attention to `JLD2`'s own file-format-version compatibility guarantees across Julia/package upgrades, since a snapshot written by an older `JLD2` minor version must still load after an upgrade.

* **Versioned Avro schemas** for dataset content, each carrying an explicit `schema_version: int` field for forward evolution:
  * `DatasetRecord` — the raw vectors or raw text payload per `doc_id`, plus which representation (`dense_vector | sparse_vector | text`) it is.
  * `MetadataRecord` — the `(doc_id -> metadata_dict)` mapping mirrored from the `meta` column family (see new §4.5 for the recommended internal shape of this record).
* **Versioned JLD2 snapshot structs**, each carrying its own `schema_version::Int` field so `load` can detect and migrate an older snapshot:
  * `SearchGraphSnapshot` — header fields (distance name, dimension, `BeamSearch` calibrated baseline) + adjacency lists (`Vector{Vector{Int32}}`) + a reference (not a copy) to the dataset backing it.
  * `InvertedFileSnapshot` — one variant per `InvertedFile` / `BM25InvertedFile`, each with its own posting-list layout (`adj`, `sizes`, and for BM25 additionally `voc`/`doclens`).
* **Snapshot + short WAL strategy:** a full JLD2 snapshot of the index struct is written periodically (or on clean shutdown); the existing RocksDB `*_log` column families continue to act as the short-lived WAL of changes *since the last snapshot*, replayed on startup. `dump` = JLD2 snapshot-now (index) + Avro export-now (dataset + metadata) bundled together; `load` = restore the JLD2 snapshot + Avro-import the dataset/metadata + replay any trailing WAL entries newer than the snapshot's watermark. The Avro export-now step should read `meta`/`*_log` through a `RocksDB.jl` `Snapshot` (§4.2's note on what's ergonomic/tested) rather than a live read, so a `dump` running concurrently with in-flight appends exports one consistent point in time instead of a torn mix of before/after states.

!!! note "Resolved: `dump`/`load` implemented — real `Avro.jl` API differs from what this section assumed, and the shipped design is deliberately a simpler slice of the one above"
    **API correction, confirmed empirically (wrote and round-tripped a real Avro file, not just read the docs):** `Avro.writetable`/`Avro.readtable` are a plain `Tables.jl` reader/writer -- given a `Vector` of a concrete Julia struct, `writetable` derives the Avro schema directly from the struct's field types via `StructTypes.jl`; there is no `schema=` keyword argument, and `Avro.parseschema` is for interpreting raw bytes against an externally-known schema when *reading*, not for dictating what `writetable` produces. (An earlier, never-exercised version of `Persistence.jl` called `Avro.writetable(path, records; schema=parsed_schema)`, which doesn't match any keyword the real function accepts — exactly the kind of unverified-API risk this section's warning above anticipated.)

    **Shipped design, and where it's a smaller slice of the fuller design above:**
    - **One flat `Persistence.DumpRecord`** (`doc_id`, `declared_json`, `extra_json`, `tombstoned`) replaces the separate `DatasetRecord`/`MetadataRecord` split above. `extra_json` already holds the complete original raw item (including its `"vector"`/`"text"` key, since `execute_build`/`handle_append` always store the full posted item) — a dedicated `dense_vector | sparse_vector | text` representation field would be pure redundancy against data `declared_json`/`extra_json` already carry losslessly.
    - **The index itself is restored via a straight file copy of the JLD2 snapshot**, not "Avro-import the dataset/metadata + rebuild the index" — this restores the exact original graph topology/posting lists byte-for-byte (confirmed: a restored `SearchGraph`'s sampled nearest-neighbor distance stats are bit-for-bit identical to the original's), rather than a plausible-but-different reconstruction `add_item!`-ing rows back in original order would produce for an incrementally-built structure like `SearchGraph`.
    - **No WAL-replay/watermark step**: `*_log` column families and a periodic/on-shutdown snapshot cadence aren't implemented anywhere in this codebase yet (a separate, larger gap — see §4.2's own note), so `dump` exports whatever the *current* JLD2 snapshot already reflects (which handle_append/handle_delete_item already keep current on every mutation, see the PLAN.md §5.7 chunk-7/8 notes) rather than a snapshot-plus-trailing-WAL. Revisit once/if the WAL layer exists.
    - **Bundle is a plain directory** (`dataset.avro` + `index.snapshot.jld2` + `manifest.json`), not a single archive file — avoids adding a packing dependency (e.g. `Tar.jl`) for a first version; each of the three files is independently a standard, documented format regardless of how they're packaged, so a non-Julia consumer loses nothing by them not being bundled into one file.
    - **`manifest.json`** carries `index_kind`/`distance`/`meta_schema`/`join_group`/`holds_metadata`/`key`/`edit_correction`/`record_count`/`dumped_at` — read from the source's `descriptor.json` when one exists (HTTP-created datasets), or best-effort derived from the live engine object when it doesn't (CLI-built datasets, which never write a `descriptor.json` at all — the same two-layout gap the CLI's `describe`/`rebuild` already work around). `load` always targets the HTTP layout (`<workdir>/datasets/{id}/`) and always writes a fresh `descriptor.json` from the manifest, so a loaded dataset is immediately visible to `Server.reload_datasets!`/`GET /api/v1/datasets` with no extra step, regardless of which layout the original dump came from.
    - **Resolved: wired as a Job/HTTP surface** — `POST /api/v1/jobs/dump` (`{"dataset": "<source-id>"}`) and `POST /api/v1/jobs/load` (`{"bundle": "<bundle-dir>", "dataset": "<new-target-id>"}`) join `HEAVY_JOB_KINDS` alongside `allknn`/`fft`/`neardup`/`hsp`, dispatching to the exact same `execute_dump`/`execute_load` CLI functions above via `Executors.submit` — no new CLI code, just the friendly-params-body translation `build_heavy_job_command` already does for the other four kinds. `dump`'s result is a bundle *directory*, not a single file like every other `HEAVY_JOB_KINDS` result — `GET /api/v1/jobs/{id}/result` special-cases a directory `result_ref` and returns `{"bundle_dir": ..., "manifest": {...}}` (the parsed `manifest.json`) instead of streaming raw bytes; `load`'s `result_ref` points at the new dataset's `descriptor.json`, which *is* a plain file and streams normally. Composes with the existing `POST /api/v1/admin/datasets/{id}/reload` (§5.7) to bring a job-loaded dataset live with no `serve` restart — the same flow `test/api/test_12_dump_load_via_admin.jl` already exercises for the CLI-subprocess version of `load`.

### 4.5. Metadata Schema Design (suggestion — answers the open "free-form via Avro" question)

Today's design (§4.2, §4.4) states metadata is free-format, encoded via Avro, stored independently of the vector representation in the `meta` column family. That independence from the vector representation is correct and should stay — the open question is what "free-format... via Avro" should actually mean at the record level, since Avro itself is not schemaless: encoding *anything* with it requires *some* schema, and a single fully-generic recursive union schema (Avro's usual answer to "arbitrary JSON") throws away exactly the property that makes typed filtering (§5.4: equality/range/set-membership) cheap.

**Suggestion: split each `MetadataRecord` into a small set of declared, typed fields plus one opaque catch-all, rather than one fully-generic blob.**

* At dataset-creation time (`POST /api/v1/datasets`), let the operator optionally declare a **`MetaSchema`**: a short list of `(field_name, type ∈ {string, int64, float64, bool, timestamp, geopoint}, indexed::Bool)` entries. This is a schema *per dataset*, stored once (not per record), and is itself just another versioned Avro schema (`schema_version: int`) so it can gain fields later. `geopoint` is `{lat::Float64, lon::Float64}` as one declared field (e.g. `location: geopoint`) rather than two independent floats the operator has to keep paired by convention — it exists specifically to back the geo predicates in §5.4's filter language.
* `MetadataRecord` becomes `{ doc_id, schema_version, <declared fields as real typed Avro fields>, extra: bytes }`, where `extra` is an opaque Avro/JSON-encoded map holding whatever the operator didn't declare up front. This keeps the "free-format" promise (anything can still go in `extra`) while giving the common, actually-queried fields (tenant id, language, source, a timestamp, a category) real types.
* **Declared + `indexed: true` fields get a secondary-index column family** (`meta_idx_<field>`, value → sorted `doc_id` list/roaring-bitmap). This is what makes the pre-filter path — flagged in §5.4 as "revisit only if post-filter proves too lossy" — cheap to add later *without* a redesign: pre-filtering only needs to consult declared+indexed fields, and the fallback for everything else (undeclared fields, or declared-but-not-indexed ones) remains today's post-filter-and-decode approach.
* **Filter evaluation** first checks the filter's field names against the dataset's `MetaSchema`: a declared field is range/set-checked directly against its typed value (and can hit the secondary index if `indexed`); an undeclared field name falls back to decoding `extra` and checking there. Both paths coexist — declaring fields is a pure opt-in optimization, not a requirement.
* **Schema evolution:** declaring a new field bumps the dataset's `schema_version`; existing records simply don't have it (`null`/absent) until they're rewritten — a natural fit for the "full re-tokenization/rewrite" mode of `rebuild` (§1) to also promote a field out of `extra` into a proper typed column for datasets where a field was originally undeclared and later turns out to be worth indexing.

!!! warning "`geopoint` fields get correct geo filtering, not indexed geo filtering — `meta_idx_<field>` doesn't help here even when `indexed: true`"
    `meta_idx_<field>` is a value→`doc_id` list, which is the right shape for equality/range/set-membership on a scalar but not for "nearest within radius" or bounding-box containment — those need a genuinely spatial structure (a geohash-bucketed column family, an R-tree, or an S2/H3 cell index), none of which this design provides yet. Marking a `geopoint` field `indexed: true` today is a no-op for geo predicates specifically: every `within_radius`/`within_bbox` call (§5.4) still runs as a brute-force per-candidate post-filter, correct but with the same cost profile as an undeclared field. Treat real spatial indexing as explicit future scope, not something this section's `indexed` flag already buys — don't let the flag's name imply otherwise.

This is additive to the current design (nothing declared → today's fully-free-form behavior via `extra` alone, with correspondingly no pre-filter capability) and gives operators a deliberate, visible knob to trade a little upfront schema rigidity for query performance on the fields that actually matter for their workload.

### 4.6. Filesystem Layout & Naming Conventions (new)

!!! note "Resolved: every standalone artifact file is named `{owning-uuid(s)}.{function-suffix}.{format-extension}`, and lives under a path that includes its owning dataset/index uuid"
    Two related debugging requirements: (1) a file's **extension must denote its serialization format** (`.avro`, `.jld2`, `.json`), and its **suffix must denote its function** (`.snapshot`, `.dump`, `.job`, `.cursor`) — so `ls`/`find` output alone tells you what a file is without opening it; (2) a file's **path must include the dataset/index uuid(s) it belongs to** — so ownership is visible from the path alone, without cross-referencing RocksDB or a job's JSON content. This applies to every file *this application* creates directly — it explicitly does **not** apply to RocksDB's own internal SST/WAL files under `data/{dataset_uuid}/`, whose layout is owned and named by `RocksDB.jl`/upstream RocksDB itself, not by this application.

    ```
    <workdir>/
      data/{dataset_uuid}/                                                # RocksDB database directory (internal layout is RocksDB's own)
      snapshots/{dataset_uuid}/{index_uuid}.{index_kind}.snapshot.jld2    # §4.4 JLD2 index-struct snapshot
      snapshots/{dataset_uuid}/{index_uuid}.{index_kind}.snapshot.meta.json  # small sidecar: schema_version, watermark, calibrated baseline — human-readable without loading the JLD2 blob
      dumps/{dataset_uuid}/{watermark}.dataset.dump.avro                  # §4.4 Avro dataset+metadata export (`dump`/`load`)
      jobs/{queued,blocked,running,done,failed}/{index_uuid}/{job_id}.{kind}.job.json    # §5.5 spool record
      cursors/{open,exhausted,expired}/{index_uuid}/{cursor_id}.cursor.json              # §5.4 spool record
    ```

    This refines (without contradicting) the layouts already given in §4.4 and §5.5: it adds the `{index_uuid}`/`{dataset_uuid}` path segment those sections' examples omitted, and makes the filename-suffix convention explicit and uniform across all four artifact kinds. Text/lexical datasets that declare a `key` (§5.3) get it woven into the same convention — e.g. a `bm25_invfile` snapshot for the `"title"` key is `snapshots/{dataset_uuid}/{index_uuid}.bm25_invfile.title.snapshot.jld2` — since `key` is exactly the kind of disambiguating detail this convention exists to surface directly in the path.

!!! warning "`key` (and any other user-supplied string) must be validated before it ever touches a filesystem path — this is a path-traversal risk, not just a naming nicety"
    Once `key` is woven into snapshot filenames as shown above, an unvalidated `key` value like `"../../../etc"` or containing a `/` becomes a path-traversal vector the moment the server constructs `snapshots/{dataset_uuid}/{index_uuid}.{index_kind}.{key}.snapshot.jld2` and writes to it. `POST /api/v1/datasets`'s `key` field (§5.7) must be checked against a strict whitelist (e.g. `^[A-Za-z0-9_-]{1,64}$`, plus the separate business rule rejecting the literal reserved value `"*"`) at creation time, **and** the path-construction code itself should re-validate rather than trust that "it was already checked once at creation" — the same discipline the plan already expects for filter field names (§4.5, §5.4) and for any other value interpolated into a filesystem path.

## 5. API Routing Specifications

The API layer relies on `Oxygen.jl` for HTTP routing and OpenAPI spec generation, async dispatch but threaded computation.

### 5.1. Core Data API (`/api/v1/simsearch/`)

!!! note "Resolved: dropped the separate Pinecone-shaped compatibility surface — one native API, addressed the way the rest of this spec already addresses everything else"
    An earlier draft carried a second, parallel `/api/v1/std/` surface modeled after Pinecone's request/response shapes, on the theory that it would be easier for experienced vector-DB users to adopt. Two problems with that, on inspection: (1) it never actually specified how a request picked *which* index/dataset to operate on — Pinecone answers that at the transport layer (each index gets its own dedicated host; the client binds to that host once), which doesn't fit this server's single-process, working-directory-based model, so copying Pinecone's request/response *shapes* without its connection model left the gap unfilled; (2) Pinecone's `upsert` name promises update-by-id semantics that `SimilaritySearch.jl`/`TextSearch.jl` don't actually have — both libraries are append-only (`push_item!`/`append_items!`, no in-place mutation), so calling the operation "upsert" was advertising a guarantee this system can't make. Rather than carry a second API surface whose main value proposition (superficial Pinecone familiarity) didn't survive contact with either the architecture or the underlying libraries, these operations are folded into the one native API below, addressed via the `{index}` path segment already used everywhere else in §5 (calibrate, describe, ftindex, ftsearch), and named for what they actually do.

* `POST /api/v1/simsearch/{index}/append`: Appends vectors with metadata. Named `append`, not `upsert` — this always adds a new entry, whether or not `doc_id` already exists; "updating" a document means soft-deleting the old entry (§1) and appending a new one, since neither underlying library supports in-place mutation of an indexed vector. Matches the `push_item!`/`append_items!` semantics of `SimilaritySearch.jl`/`TextSearch.jl` directly, including the same `append` permission scope already used in the `Token` model (§7).
* `POST /api/v1/simsearch/{index}/search`: Performs K-NN search, accepting `BeamSearch` overrides (bounded by the per-index calibrated safety multiplier, §3) and an optional metadata `filter` (§5.4) with `offset`/`limit` pagination. Subject to the §3 Long-Lived Search Policy, which may `429` and point the caller at `POST /api/v1/jobs/search` instead.
* `POST /api/v1/simsearch/{index}/search_batch`: Performs multiple K-NN queries against the same index in a single request, returning one result list per input query — avoids per-query HTTP overhead for bulk client-side workloads.
* `POST /api/v1/simsearch/{index}/delete`: Triggers a soft-delete (tombstoning via a `BitVector` exclusion filter — see §1 warning on soft deletes for the recall caveat).
* `GET /api/v1/simsearch/{index}/fetch?ids=...`: Retrieves stored vectors + metadata by id, without performing a similarity search. Useful for clients that already have an id and just need the payload back — including the join-dataset metadata-hydration pattern (§1, §6) and the multi-key `ftsearch` hydration step (§5.3).
* `GET /api/v1/simsearch/{index}/exists?ids=...`: Lightweight existence/tombstone-status check by id, without paying for a full `fetch`.

### 5.2. Index Administration & Calibration (`/api/v1/simsearch/`)

Exposes the advanced/administrative capabilities of the underlying index — as opposed to §5.1's day-to-day data operations.

* `POST /api/v1/simsearch/{index}/calibrate`: Triggers hyperparameter calibration (see §5.6) against a supplied or sampled ground-truth set, persisting the resulting `BeamSearch` baseline.
* `GET /api/v1/simsearch/{index}/describe`: HTTP mirror of the CLI `describe` command — distance stats, size, tombstone ratio, calibrated `BeamSearch` baseline.

!!! warning "Heavy/offline operations moved to the async Job model"
    The previous draft exposed `allknn`, `closestpair`, `neardup`, `fft`, `hsp` as synchronous `POST` endpoints directly under `/api/v1/simsearch/`, while §1 (CLI) calls these same operations "heavy offline" and §2 (Concurrency) says they consume the *entire* thread pool. A synchronous HTTP POST that can legitimately run for hours, on an endpoint that also starves all other traffic while running, is a availability and HTTP-timeout hazard. These operations are now exposed exclusively through the Job model (§5.5): `POST /api/v1/jobs/{kind}` where `kind ∈ {search, allknn, neardup, fft, closestpair, hsp}`, immediately returning `202 Accepted` + `job_id`, with progress/result retrieved via the `/api/v1/jobs/*` endpoints below. `searchbatch` remains CLI-only by design (it reads/writes local files on the same machine and isn't meant for network transfer of bulk inputs/outputs). `search` is included in the Job kind enum specifically as the resubmission target for the §3 Long-Lived Search Policy `429` response.

Fixed in `IndexEngine` by building a `TextSearch.VectorModel(IdfWeighting(), TfWeighting(), voc)` once the vocabulary is trained (`ensure_trained!`) and calling `vectorize(model, text)` — which returns a real `SparseVector{Float32,Int32}` — instead of `bagofwords` for this index kind specifically (`BM25Kind` is unaffected and still uses `bagofwords`/`BOW`, which is what `BM25InvertedFile` actually wants).   !!! note "Resolved: multi-field documents are modeled as N `key`-tagged join-group members, per the §1 update"
      A document is rarely one blob of text — it typically has several distinct text fields (`title`, `body`, `tags`, ...) that are worth scoring separately rather than concatenated into one bag of words. Given the strict one-index-per-dataset rule, this is modeled as: **each field gets its own dataset+index, tagged with a `key` string, all members of the same `join_group`** (§1, §7) as whatever dense/metadata datasets exist for that logical document collection.
      * **Indexing:** `POST /api/v1/datasets` accepts an optional `key` alongside `index_kind` when creating a text-index dataset (§5.7). `ftindex` still targets exactly one `{index}` per call — same as every other endpoint in this spec — so indexing a multi-field document means one `ftindex` call per populated key/field, each carrying the same shared `doc_id`. A document missing a given field simply isn't appended to that key's index; per-key posting lists are allowed to have different coverage over the shared `doc_id` space, same as any inverted index with absent terms.
      * **Querying:** `ftsearch`'s payload requires a `key`: either one specific key string (routes to the one join-group member tagged with that key) or the reserved wildcard **`"*"`**, meaning "fan out this query to every key-tagged member of the query's join group in parallel." Responses for `key: "*"` are **grouped by key, not fused** — `{ "title": [ {doc_id, score}, ... ], "body": [...] }` — fusing per-field lexical scores into one ranked list is a different, harder scoring problem than the RRF semantic/lexical fusion in §6 and isn't required here; if the caller wants a single ranked list across fields, that's a client-side or future concern, not this endpoint's job. Metadata hydration happens once at the end, via the join group's `holds_metadata` member, over the union of `doc_id`s across all per-key result sets — the same "fetch once after gathering candidates" execution flow already used by §6's hybrid search.
      * **Validation:** `"*"` is a query-time-only wildcard and must be rejected with `400` if supplied as an actual `key` at dataset-creation time. See §4.6 for why `key` also needs strict character validation independent of this rule (it ends up embedded in filesystem paths).

  !!! note "Confirmed: `TextSearch.jl`'s own attempt at multi-field support is dead code — the join-group-of-single-field-indices design above isn't reinventing something the library already provides"
      `src/multi.jl` (`joinmodel`, `update!`, `glue`) is not `include`d by `src/TextSearch.jl` at all, and references types (`IdFreq`, `WeightedVocabulary`, a zero-arg `Vocabulary()`) that don't exist in the current API — it's leftover/abandoned code, not a usable feature. `bagofwords!` does accept a list of texts for "a multi-field document," but flattens them into one undifferentiated bag of words, with no per-field weighting or separate posting lists. Neither is a substitute for the per-`key` join-group pattern above; this spec's design is the only real multi-field story for this library, not a redundant one.

### 5.4. Metadata Filtering & Pagination (new)

!!! note "Resolved: `filter` is a restricted-Julia boolean expression string, not a JSON operator DSL"
    An earlier draft used a JSON filter DSL (`{"field": {"gte": ..., "in": [...]}}`). Replaced with a **string** containing a boolean expression, evaluated against the record as if it were a `Dict` — familiar to anyone who reads Julia, and more expressive than a fixed set of JSON operator keys:

    ```
    filter: "lang in (\"es\", \"en\") && score >= 0.5 && !flagged"
    ```

    A bare identifier (`lang`, `score`, `flagged`) resolves as a field lookup against the record — sugar for the fully explicit `record["lang"]`, which `Meta.parse` also accepts unchanged (`a[b]` parses to its own `:ref` node, distinct from a function call, so both forms are trivial to support with the same evaluator). See §4.5 for how declared/typed vs. free-form (`extra`) metadata fields affect evaluation cost either way.

    !!! warning "This must never become `eval(Meta.parse(filter))` — that is arbitrary remote code execution"
        Parsing the filter string with `Meta.parse` is safe and desirable (it's just building an `Expr` tree; no code runs yet) — the danger is entirely in *evaluation*. The server must never call real `eval`/`Base.eval`/`invokelatest` on anything derived from `filter`. Instead, implement a small hand-written recursive interpreter that walks the parsed `Expr` tree and only descends into an explicit whitelist of node shapes: `Expr(:&&, ...)`, `Expr(:||, ...)`, `Expr(:call, :!, x)`, comparison calls (`==`, `!=`, `<`, `<=`, `>`, `>=`), `in`/`∈`, `Expr(:ref, :record, key)` (field lookup), literals (`String`, `Int`, `Float64`, `Bool`), and calls to functions resolved via the `FilterFunctions` registry below. Anything else — `:macrocall`, `:block`, `:(=)` (assignment), `:$` (interpolation), a bare `Symbol` that isn't recognized as a field name, or a `:call` whose function isn't in the registry — is a **validation error (`400`)**, not something the evaluator attempts to run. Additionally cap the filter string's length (e.g. 2 KB) and the parsed tree's recursion depth (e.g. 32) before evaluating at all, so a pathologically nested expression is rejected as a malformed request rather than exercised as a resource-exhaustion vector.

    **`FilterFunctions` registry — function admissibility is structural, not a hand-maintained string list.** A function is callable from a filter expression if and only if it is `export`ed from one specific internal module, e.g. `SimilaritySearchServer.FilterFunctions` — mirroring the `DistanceRegistry` (§3) and `StemmerRegistry` (§5.3) pattern of "resolve safely via `getproperty(Registry, Symbol(name))` against a registry, don't hardcode a type/string list into the evaluator's core logic." Concretely: on a whitelisted `Expr(:call, f, args...)`, the evaluator checks `Base.isexported(FilterFunctions, f)` (or an explicit `names(FilterFunctions, all=false)` membership check) before resolving and calling it — an unexported or undefined name is a `400`, exactly like an unrecognized field. Adding a new filter-callable function is then "export it from this one module," not "touch the evaluator." This is a stronger gate than a flat `Set{String}` whitelist (it forces a deliberate, reviewable act — exporting from a module whose entire purpose is "safe for user-supplied filter expressions" — rather than one line added to a list that can drift from what's actually safe), but it is **not** a safety guarantee by itself: every function admitted into `FilterFunctions` still needs to be manually verified pure, deterministic, and bounded-cost (no I/O, no unbounded loops, no allocation scaling with anything other than its arguments) as part of code review — the module boundary centralizes *where* that review has to happen, it doesn't replace it. This matters concretely for string-matching functions in particular (`occursin`-style helpers): a naively-implemented regex predicate is a ReDoS vector even though it's "just string matching," so `FilterFunctions` members that touch strings need the same scrutiny as anything else on this list.

    **Initial `FilterFunctions` membership**, seeded with what's needed now:
    * `startswith(s, prefix)`, `occursin(needle, s)` — basic string predicates (already proposed; kept here as the non-geo baseline).
    * `geo_distance(lat1, lon1, lat2, lon2) -> meters` — haversine great-circle distance; pure, cheap, no external dependency.
    * `within_radius(lat, lon, center_lat, center_lon, radius_m) -> Bool` — built on `geo_distance`; the primary geolocated-filter predicate. Takes plain `lat`/`lon` numbers when those are two separate declared fields, or dispatches on a single `geopoint`-typed field (§4.5) directly — `within_radius(location, 19.4326, -99.1332, 5000)` — via a second `FilterFunctions` method rather than requiring new grammar (e.g. dot-field access) just to unpack it.
    * `within_bbox(lat, lon, min_lat, min_lon, max_lat, max_lon) -> Bool` — bounding-box containment; cheaper than `within_radius` (no trig), useful when a rectangular region is a good-enough approximation.
    * See §4.5's new warning: none of these three geo functions get a secondary index today — they're correct, evaluated-per-candidate post-filter predicates, not indexed spatial queries. A real geo index (geohash/R-tree/S2-H3) is future scope.

* **Pre-filter vs. post-filter tradeoff must be documented per endpoint:** post-filtering (search first, discard non-matching candidates afterward) is simple but can silently under-return `k` results when the filter is selective; pre-filtering (restrict the candidate set before/during graph traversal) preserves recall but is not natively supported by `SearchGraph`'s beam search and would require either an id-restricted variant of the search loop or an initial candidate-set narrowing pass. Start with post-filter + an explicit `"insufficient_results"` response flag when filtering drops below the requested `k`; revisit pre-filtering only if that proves too lossy in practice.
* `offset`/`limit` (or an opaque `cursor`) apply to `/simsearch/{index}/search`'s result list and to all listing endpoints (`list`, `GET /api/v1/jobs`, `GET /api/v1/datasets`).

  !!! note "Explicit: an opaque result `cursor` needs its own persistent state, with the same resolution/poll/gc protocol as Jobs"
      A `cursor` isn't a stateless encoding of `offset`/`limit` once the underlying result set is expensive to recompute (e.g. paging through a large `search`/`allknn`/`neardup` result, or through a filtered listing that had to over-fetch to satisfy `k` after post-filtering, §5.4 above) — the server needs somewhere to actually hold the materialized result page(s) between requests. This is stored with the identical state machine and spool-directory mechanism as the Job registry (`<workdir>/cursors/{open,exhausted,expired}/{index_uuid}/<cursor_id>.cursor.json`, per §4.6's naming convention — see §5.5 for why it's a spool directory rather than a RocksDB table, and for the accompanying scaling warnings, which apply here just as much): `cursor_id` created on first response, directory-as-state (`open|exhausted|expired`), `last_polled_at` updated on each `GET .../result?cursor=...` poll, a `result_ref` pointing at the materialized page data, and a TTL (`expires_at`) after which the cursor is eligible for garbage collection via `similarity-search-ctl jobs gc`.

* `GET /api/v1/simsearch/{index}/vocab`: (TextSearch-only) vocabulary size, top-N tokens by document frequency, and current OOV rate — the operational signal for when a text `rebuild` is actually needed (see §1 warning on vocabulary drift). Backed directly by existing `Vocabulary` bookkeeping rather than anything bespoke: per-token `occs`/`ndocs` counters, `trainsize`/`numtokens` (and the derived `avgdoclen(voc)`), and a `table(voc, DataFrame)` dump of `token/ndocs/occs` for the top-N listing. `filter_tokens`/`filter_tokens!` (hapax/doc-frequency pruning) and `update_voc!`/`merge_voc` are existing vocabulary-maintenance utilities worth reusing for the `rebuild` mode-(a) full re-vocabulary pass (§1) rather than reimplementing vocabulary pruning from scratch.

### 5.5. Async Job Model & Pluggable Execution Backends (new)

Heavy/offline operations (`search` when denied by the §3 policy, `allknn`, `neardup`, `fft`, `closestpair`, `hsp`, and administratively, `rebuild`/`dump`/`load`) are modeled as Jobs rather than blocking HTTP calls, resolving the contradiction flagged above.

* `POST /api/v1/jobs/{kind}`: Enqueues a job (`kind ∈ {search, allknn, neardup, fft, closestpair, hsp, rebuild, dump, load}`), returns `202 Accepted` with a `job_id`.
* `GET /api/v1/jobs/{job_id}`: Returns current `status` and `progress`.
* `GET /api/v1/jobs/{job_id}/result`: Streams/downloads the result payload once `status == done`.
* `DELETE /api/v1/jobs/{job_id}`: Cancels a job that hasn't started running yet (best-effort cancellation for a running job, since `SimilaritySearch.jl` operations aren't natively interruptible mid-traversal — cancelling a running Job means terminating its executing process/allocation).

    On review, this bullet's own text was internally inconsistent with §1's `jobs kill` note directly above (which says `DELETE` "only applies to not-yet-started jobs," `kill` being the one that handles a running job). Implemented per that clearer, more decisive reading: `DELETE` cancels a `queued`/`blocked` job (moves it straight to `failed/` with `error: "cancelled by operator"`, the same shape `kill` already uses for `error: "killed by operator"`) and returns `409` for an already-`running` or already-finished job -- pointing the caller at `kill` instead, rather than silently no-op'ing or falling back to actually killing it. * `GET /api/v1/jobs?index_uuid=...&status=...&kind=...`: Lists/filters jobs, paginated per §5.4. `status` also accepts `blocked` (see updated enum below).

**Resolved design: the Job (and result-cursor) registry is a spool directory, not a RocksDB column family.**

!!! note "Why: RocksDB's single-writer-process constraint is a poor fit for a queue a child process must update"
    RocksDB's column families can only be opened for writing by one OS process at a time. `meta`/`*_log` are fine as RocksDB CFs because only `similarity-search-serve` itself ever writes them. Jobs are different: `LocalCLIExecutor` (below) spawns a genuinely separate CLI process to do the actual heavy work, and that child is the natural place to report its own progress as it runs — funneling every progress tick back through the parent so *it* can be the one to write RocksDB is an indirection that buys nothing. A **spool directory with atomic `rename`-based state transitions** (the classic maildir/mail-queue pattern) sidesteps the constraint entirely: POSIX guarantees `rename` within one filesystem is atomic, so multiple processes can safely move/update files without any database-level locking, coordination service, or single-writer rule.

* **Layout:** `<workdir>/jobs/{queued,blocked,running,done,failed}/{index_uuid}/{job_id}.{kind}.job.json` (§4.6's naming convention applied here), one file per job, whose *directory* is its `status`, whose path segment identifies which index/dataset it targets, whose filename suffix identifies its `kind`, and whose *content* is the JSON record shown below (minus the redundant `status`/`index_uuid`/`kind` fields already implied by the path — kept in the record too for callers that only have the file content, e.g. after `GET /api/v1/jobs/{job_id}` hands it back over HTTP without the local path). `result_cursors` (§5.4) uses the identical layout under `<workdir>/cursors/{open,exhausted,expired}/{index_uuid}/{cursor_id}.cursor.json`.
* **Ownership split, so no two processes ever write the same thing at the same time:** the parent (`similarity-search-serve`) owns every directory-to-directory transition (`queued/` → `running/`, `running/` → `done|failed/`, `queued/` ↔ `blocked/`) via `rename`. While a job is in `running/`, its *content* (the `progress` field specifically) is owned by whatever is actually executing it — the `LocalCLIExecutor` child process, or a Slurm-submitted task (see below) — which updates it via write-to-temp-file-then-`rename`-over-itself (never an in-place partial write, so a reader never observes a torn record). The parent never touches a running job's content, only its directory placement on start/exit.
* **Record shape** (file content — the same shape as before, just no longer a RocksDB value):

```json
{
  "job_id": "uuid",
  "index_uuid": "uuid",
  "kind": "search | allknn | neardup | fft | closestpair | hsp | rebuild | dump | load",
  "params": { "...": "kind-specific parameters" },
  "submitted_at": "RFC3339 timestamp",
  "started_at": "RFC3339 timestamp | null",
  "finished_at": "RFC3339 timestamp | null",
  "progress": { "done": 0, "total": 0 },
  "executor_handle": "opaque handle from the JobExecutor backend (pid, or Slurm job id) | null",
  "result_ref": "opaque pointer to result storage | null",
  "error": "string | null"
}
```

!!! warning "Scaling limits of the spool design — know them, and let `gc` be the thing that keeps them from biting"
    This trades RocksDB's indexed/range-scan lookups for `readdir` + per-file parsing, which changes where the safe operating envelope is:
    - **`GET /api/v1/jobs?index_uuid=...&status=...&kind=...` is a directory scan + filename/content filter**, not an indexed lookup. Fine at the cardinality this system actually has — `queued/`+`running/`+`blocked/` is hard-bounded by the §2 reserved-pool sizing (tens of concurrent jobs, not thousands) — but it does **not** scale as a general-purpose job-history query engine. Don't repurpose it for "list every job ever run, filtered, across months" — that's what `dump`'s Avro export is for if long-term job history ever needs to be queryable.
    - **`done/`/`failed/` grow unboundedly without pruning**, since nothing removes a finished job's file automatically. This makes `similarity-search-ctl jobs gc` (§1) load-bearing, not just a nice-to-have: routine GC is what keeps the `done/failed` directories — and therefore every future listing scan — small. Recommend running it on a schedule (e.g. a cron-triggered `jobs gc` call) rather than only on-demand.
    - **Progress-file rewrite frequency should be throttled** (e.g. at most once per second, not once per distance-evaluation batch) — each update is a small write-then-rename, cheap on local disk but with real per-call metadata-operation latency on network filesystems, which matters once `SlurmExecutor` puts that spool directory on NFS/Lustre (see below).
    - **A single flat directory with very many entries** can make `readdir` slower on some filesystems; the five-way `{queued,blocked,running,done,failed}` split already keeps the hot ones (`queued`/`running`) small, so this is really just another way `gc` on `done`/`failed` matters — it's the one directory pair with no natural cap otherwise.

**Execution backend — `JobExecutor` abstraction.** The Job registry (queueing, status, HTTP surface above) is deliberately decoupled from *how* a job's compute actually runs, via a small 4-method interface: `submit(cli_args) -> handle`, `poll(handle) -> status`, `result_path(handle) -> path`, and `kill(handle) -> nothing` (added to formally back the `POST /api/v1/jobs/{job_id}/kill` admin endpoint above — previously "cancelling a running job" was only described informally under `DELETE`; `kill` makes it an explicit, always-implemented backend method rather than an ad hoc process-signal call bolted onto the registry). `poll(handle)` now just means "read the spool file's current `progress`/liveness" — there is no separate RocksDB write to keep in sync with it. Because a Job's real work is always "run one of the CLI commands from §1 with these arguments," any backend just needs to know how to launch, monitor, and forcibly stop that CLI invocation — the Job logic itself never changes. `block`/`resume` don't need an executor method at all: a `blocked` job is one sitting in `blocked/`, which the scheduler simply never scans for work, so it's handled entirely in the registry, before any executor is involved.

!!! note "Job GC and result-cursor GC share one lifecycle — and one admin command"
    `jobs` and `result_cursors` (§5.4) are structurally the same kind of spool record: created, polled, resolved/connected, and eventually garbage-collected past a retention window. `similarity-search-ctl jobs gc` (§1) sweeps both in one pass — `done`/`failed`/`cancelled` job files and `expired` cursor files past their retention TTL — rather than requiring two separate GC entry points. `similarity-search-ctl jobs queue` similarly surfaces both queued/running/blocked jobs and currently-open result cursors, since both represent server-side state an operator may need visibility into before deciding to restart or scale the server.

* **`LocalCLIExecutor` (default, v1):** For each dequeued job, `serve` renames the job file `queued/` → `running/` and spawns the exact same CLI command a human would run offline (e.g. `similarity-search allknn --dataset <uuid> --workdir .`) as a subprocess, pointed at that same file path so it can update its own `progress` field in place, with its thread budget capped to the reserved Job pool from §2 (`JULIA_NUM_THREADS=<reserved_threads>` passed to the child). The number of concurrently running subprocesses is bounded so their combined thread usage never exceeds the reserved 20%. On exit, the parent reads the child's exit code, writes the final `result_ref`/`error`, and renames the file to `done/` or `failed/`. This is cheap to do per-job specifically *because* of the `[apps]`-based packaging chosen in §1 — a precompiled Julia app image starts far faster than a plain `julia -e` invocation, which is what makes "one subprocess per job" viable instead of prohibitively slow.
* **`SlurmExecutor` (documented future backend, not built in v1) — the spool design is a direct fit, not just a tolerable one:** Submits the *same* CLI command wrapped in a small generated `sbatch` script (or via a blocking `srun` allocation), tracks the returned Slurm job id as `executor_handle`, polls `squeue`/`sacct -j <id> --format=State` on the existing poll cadence, and once Slurm reports `COMPLETED`, reads the result from the working directory exactly as `LocalCLIExecutor` does. This works with **no snapshot-transfer step** as long as the Slurm cluster's compute nodes share the same filesystem as the submitting node for the working directory (the normal case for on-prem HPC clusters with NFS/Lustre home/scratch) — the CLI subprocess launched by Slurm simply opens the same working-directory path, including the spool file it should update. Because job state now lives in plain files rather than a RocksDB CF, the Slurm-side compute node needs *zero* RocksDB client access to report progress — it only needs the POSIX filesystem access it already has for reading the dataset/index; a RocksDB-backed job registry would have forced either routing every Slurm-node progress update back through the submitting server, or opening RocksDB from a node that isn't the lock-holding process, which isn't supported. Migrating from `LocalCLIExecutor` to `SlurmExecutor` is a backend swap behind the same 4-method interface: the Job registry, the `/api/v1/jobs/*` HTTP surface, and the CLI commands themselves are all unaffected.

!!! warning "Fully remote workers without a shared filesystem are a different, harder problem — deliberately out of scope for now"
    If a deployment ever needs Job execution on machines that do **not** share a filesystem with the origin server (e.g. untrusted or fully external compute, no Slurm/NFS available), `SlurmExecutor`'s free ride on shared storage disappears, and a real distributed worker protocol would be needed instead: workers authenticating with a dedicated `worker` token scope (§4.1), pulling the index's JLD2 snapshot plus its dataset's Avro export (§4.4) via a resumable `GET /api/v1/datasets/{uuid}/snapshot` range-request endpoint, an atomic claim/lease mechanism with heartbeats over the `jobs` registry to recover from a dead worker, and a `snapshot_watermark` field on the `JobRecord` so results computed against a snapshot can be correctly interpreted against subsequent inserts. None of this is needed for the local-pool-now/Slurm-later path above — note it here only so it isn't forgotten if the deployment target changes later.

### 5.6. Hyperparameter Calibration (new)

* `POST /api/v1/simsearch/{index}/calibrate`: Runs a `BeamSearch` hyperparameter sweep (using `SearchModels`, already a direct dependency of `SimilaritySearch.jl`) against either a supplied ground-truth query/knn set or an internally sampled one, and persists the resulting calibrated `(bsize, Δ, maxvisits)` baseline as part of the index's metadata/header.
* This baseline is what the §3 safety-multiplier barrier is anchored to (replacing the previously-arbitrary global `bsize <= 20` / `Δ < 1.7` constants), and it's also surfaced via `GET /api/v1/simsearch/{index}/describe`.

!!! note "Relationship to `SearchGraph`'s own built-in auto-tuning — don't let the two mechanisms silently fight each other"
    `SimilaritySearch.jl` already ships an online auto-tuning mechanism independent of this endpoint: `SearchGraphContext`'s default `hyperparameters_callback` (`src/searchgraph/context.jl`) runs `optimize_index!` against an `OptimizeParameters`/`MinRecall` target *during construction/growth* of a `SearchGraph`, using the same `SearchModels`-based machinery (`BeamSearchSpace`, `combine`/`mutate` in `src/opt.jl`/`src/searchgraph/optbs.jl`) this endpoint drives explicitly. Left at its default, a freshly-built `SearchGraph` may therefore already have a reasonably-tuned `BeamSearch` baseline before `calibrate` is ever called. Decide explicitly which mechanism owns the baseline that's actually persisted and used for the §3 safety multiplier: either (a) disable/override the default `hyperparameters_callback` at construction time and treat `calibrate` (an explicit sweep against a caller-supplied or sampled ground-truth set, not just a `MinRecall` target) as the sole source of truth, or (b) let construction-time auto-tuning provide a reasonable starting baseline and have `calibrate` be an explicit, better-grounded *refinement* step layered on top. Pick one and document it — silently having both write to the same stored baseline independently is the failure mode to avoid.

!!! danger "Open issue (flagged for review, not yet re-resolved): the disable-at-construction choice below needs its own follow-up spec, not just a resolved bullet"
    The implementation (chunk 6) picked option (a) above and stopped there: `IndexEngine.get_context_for_index(::SearchGraph)` passes `hyperparameters_callback=nothing`, so `optimize_index!` never runs during construction/growth anymore, and `calibrate!`/`POST .../calibrate` is the *only* thing that ever writes a `BeamSearch` baseline. On review, "disabled" is too coarse an answer by itself — it settles which mechanism owns the stored baseline, but not what either mechanism should actually be doing. Two separable questions still need an explicit spec before this is done:
    1. **Construction-time optimization**: is *never* running any construction-time quality signal correct for every dataset size, or does a large bulk `build`/`append` deserve some construction-time behavior (even something distinct from the disabled `OptimizeParameters`/`MinRecall` callback — e.g. running `SimilaritySearch.rebuild`'s topology pass, §1's `rebuild`, once automatically after a large bulk load) before the first explicit `calibrate!` ever runs? Right now a freshly built `SearchGraph` sits at `DEFAULT_BEAMSEARCH` (the bare library default) until an operator remembers to calibrate — decide whether that interim state is acceptable or whether `build`/`append` should be doing something about it on their own.
    2. **Search-time optimization**: `calibrate!` today only sweeps `BeamSearch` (`bsize`/`Δ`/`maxvisits`) via `MinRecall`. Confirm that this is the intended full scope of "optimization for search," as distinct from construction-time optimization above — e.g. should it also ever touch `SearchGraph`'s neighborhood/hint construction parameters, and should a `rebuild` (§1) be something `calibrate!` triggers as part of its own sweep, rather than only ever being invoked as the separate, manually-run `rebuild` CLI command?
    Until both are answered explicitly and the resulting behavior documented, treat "construction-time auto-tuning is disabled" as a placeholder that only closes half the original note above, not a settled design.

### 5.7. Dataset & Index Management (new)

* `POST /api/v1/datasets`: Creates a new dataset (working-dir-relative RocksDB database + `meta` column family) with exactly one index kind (§1), returning its `index_uuid`. Accepts an optional `join_group` (existing or new) and `holds_metadata` flag for the multi-representation/hybrid use case (§1, §6), plus an optional `meta_schema` (§4.5) declaring typed/indexed metadata fields. For a text/lexical `index_kind` (`weighted_invfile | binary_invfile | bm25_invfile`), also accepts an optional `key` (§5.3) identifying which text field this dataset indexes within its join group — rejected with `400` if `key == "*"` (reserved for the `ftsearch` fan-out wildcard, §5.3) or if it fails the path-safety character whitelist (§4.6). A text dataset also accepts an optional boolean `edit_correction` (default `false`): its queries then correct a token absent from the vocabulary to the only vocabulary token at Damerau-Levenshtein distance 1 from it. The engine does not persist this value, so the server stores it in `descriptor.json` and passes it to `open_project` on every open; it is refused with `400` for a dataset without text.
* `GET /api/v1/datasets`: Lists datasets in the current workdir (HTTP mirror of the CLI `list` command), paginated.
* `GET /api/v1/datasets/{uuid}`: Dataset details — index kind, size, tombstone ratio, telemetry summary, `join_group` (if any).
* `DELETE /api/v1/datasets/{uuid}`: Deletes a dataset and its index (destructive — should require an explicit confirmation flag in the request body, mirroring the caution already implied by soft-deletes for individual documents; deleting the `holds_metadata` member of a `join_group` should warn/require extra confirmation since other members' `fetch` calls depend on it).
* `GET /api/v1/datasets/{uuid}/join_group`: Returns the full `JoinGroup` (§7) this dataset belongs to, i.e. its sibling datasets and which one `holds_metadata`. Empty/`null` if the dataset isn't part of a join group.

!!! note "Resolved: `serve` now reopens every existing dataset on startup"
    `similarity-search-serve` previously never re-opened datasets from a prior run — a restart could still `list`/`describe` them (their `descriptor.json` sidecar is enough for that) but couldn't `search`/`append`/`ftsearch`/`calibrate` any of them until they were recreated. Fixed: `Server.reload_datasets!(app)` scans `<workdir>/datasets/`, reopens each dataset's RocksDB handle with its originally-declared `meta_schema` (now also persisted into `descriptor.json`, alongside `index_kind`/`distance`), and restores its search engine from the JLD2 snapshot if one exists (or a freshly-created empty engine if the dataset was created but never appended to). Runs once, right after `AppState` construction and before `run_server` starts accepting requests.

!!! note "Resolved: single-dataset hot unload/reload"
    `POST /api/v1/admin/datasets/{id}/unload` closes just that one dataset's RocksDB handle and drops it from `app.datasets`/`app.engines`, releasing the exclusive write lock so an external process — concretely, the CLI `rebuild` (§1) — can safely open it for writing while `serve` stays up and keeps handling every other dataset. `POST /api/v1/admin/datasets/{id}/reload` reopens it afterward (via the same per-dataset logic `reload_datasets!` uses, but deliberately overwriting rather than skipping an existing entry), picking up whatever `rebuild` (or any other out-of-band CLI operation) changed on disk. The intended operator flow is `unload` → run `rebuild` → `reload`, with no `serve` restart and no downtime for any dataset other than the one being refreshed. `reload` accepts an optional body `{"edit_correction": true | false}`: the value is written to `descriptor.json` before the dataset is reopened with it. A non-boolean value, or `true` for a dataset without text, is a `400` that is answered before the loaded handle is closed.

### 5.8. Health & Metrics (new)

* `GET /healthz`: Liveness — process is up and serving.
* `GET /readyz`: Readiness — working directory RocksDB handles open, no crash-recovery WAL replay pending.

## 6. Hybrid Search Readiness (Suggestions & Specifications)

The architecture must inherently support Hybrid Search (the fusion of dense semantic search and sparse lexical search).

!!! warning "Fusion logic is entirely out of scope for both libraries — this section's suggestions are the actual design, not optional decoration"
    Grepped both `SimilaritySearch.jl` and `TextSearch.jl` for fusion/hybrid/RRF: zero matches in either. There is no library-provided way to combine a `SearchGraph` distance score with a `BM25InvertedFile`/`InvertedFile` score — this application must implement the entire fusion layer itself. The shared-`doc_id` requirement below is what makes that possible at all; without it, hybrid search isn't feasible with these two libraries as-is.

* **Shared Metadata Architecture (Required), now expressed via the §1 join-dataset pattern:** given the strict one-index-per-dataset rule (§1), the `SearchGraph` (semantic) and the lexical index (`BM25InvertedFile`/`InvertedFile`) live in **two separate datasets** sharing one `doc_id` space, plus one designated dataset (either one of the two, or a third metadata-only dataset) holding the full `meta` record for random-access-by-id batch retrieval. The in-memory indices themselves still only hold identifiers, not metadata, to prevent memory bloat — that constraint is unchanged, it's just now enforced across dataset boundaries rather than within one shared dataset.
* **Proposed Endpoints (Suggestion):** Introduce `POST /api/v1/simsearch/hybrid_search` to accept dual payloads (raw text + dense vector) plus **two dataset/index references** (`dense_index_uuid`, `lexical_index_uuid`) instead of one — a direct consequence of hybrid search now spanning two single-index datasets rather than one dual-index dataset.
* **Fusion Strategy (Suggestion):**
* Implement **Reciprocal Rank Fusion (RRF)** as the default ranking merger to harmonize the vastly different scoring scales of semantic distance metrics and BM25 scores.
* Expose an `alpha` scalar parameter in the API payload to allow users to perform a convex combination of normalized scores if they require explicit weighting between semantic and lexical relevance.
* **Execution flow:** query the dense index and the lexical index independently (each returns `doc_id`s + its own score), fuse the two ranked lists by `doc_id` (RRF or the `alpha`-weighted combination), then batch-`fetch` the metadata-holding dataset once for the union of surviving `doc_id`s to hydrate the response — metadata hydration happens once, after fusion narrows the candidate set, not once per source index.

## 7. Data Model Reference

Representative JSON payloads for the entities introduced above.

### Dataset

Strictly one index per dataset (§1) — `index_kind` is singular, not a list:

```json
{ "index_uuid": "uuid", "created_at": "RFC3339", "index_kind": "searchgraph", "doc_count": 128000, "tombstone_ratio": 0.012, "join_group": "uuid | null", "meta_schema_version": 1 }
```

### JoinGroup (new — backs the §1 join-dataset use case and §6 hybrid search)

Datasets that share a `doc_id` space (e.g. one `searchgraph` dataset over dense embeddings + one `bm25_invfile` dataset over the same documents' text, plus an optional metadata-only dataset) are tagged with a common `join_group` id. Exactly one member is flagged `holds_metadata: true` and answers batch `fetch`; the rest carry only `doc_id` plus whatever their own index needs. A text/lexical member may additionally carry a `key` (§5.3) — `null` for non-text members (dense, metadata-only) and for a text member indexing a single undifferentiated field; a join group may hold any number of distinct-`key` text members, one per indexed field:

```json
{ "join_group": "uuid", "members": [ { "index_uuid": "uuid-a", "index_kind": "searchgraph", "holds_metadata": false, "key": null }, { "index_uuid": "uuid-b", "index_kind": "bm25_invfile", "holds_metadata": false, "key": "title" }, { "index_uuid": "uuid-d", "index_kind": "bm25_invfile", "holds_metadata": false, "key": "body" }, { "index_uuid": "uuid-c", "index_kind": "metadata_only", "holds_metadata": true, "key": null } ] }
```

### IndexDescriptor

```json
{ "index_uuid": "uuid", "kind": "searchgraph", "distance": "L2", "dimension": 768, "beamsearch_baseline": { "bsize": 8, "delta": 1.05, "maxvisits": 250000 }, "transform": { "kind": "sq_u8", "rerank_with_original": true } }
```

### Token

```json
{ "token": "opaque-secret", "index_uuid": "uuid", "permissions": ["search", "append", "allknn"], "created_at": "RFC3339", "expires_at": "RFC3339 | null" }
```

### AppendRequest

`POST /api/v1/simsearch/{index}/append` (§5.1) — always adds a new entry; "updating" `doc_id` is soft-delete + re-append, not an in-place field of this request:

```json
{ "items": [ { "doc_id": "optional-external-id", "vector": [0.1, 0.2, "..."], "metadata": { "lang": "es", "source": "..." } } ] }
```

### SearchRequest

`POST /api/v1/simsearch/{index}/search` (§5.1):

```json
{ "vector": [0.1, 0.2, "..."], "k": 10, "filter": "lang in (\"es\", \"en\") && within_radius(lat, lon, 19.4326, -99.1332, 5000)", "offset": 0, "limit": 10, "beamsearch_overrides": { "bsize": 12 } }
```

### HybridSearchRequest

Two index references, per the §6 update — hybrid search spans two single-index datasets, not one dual-index dataset. `filter` is the §5.4 restricted-Julia expression string; omit or use `"true"` for no filtering:

```json
{ "dense_index_uuid": "uuid-a", "lexical_index_uuid": "uuid-b", "text": "raw query text", "vector": [0.1, 0.2, "..."], "alpha": 0.5, "k": 10, "filter": "true" }
```

### FtIndexRequest

Targets one specific key's dataset (§5.3) — one call per populated field of a multi-field document, same shared `doc_id` across calls:

```json
{ "doc_id": "doc-123", "text": "raw text for this field only" }
```

### FtSearchRequest / FtSearchResponse

`key` selects one join-group member, or `"*"` to fan out to all of them (§5.3). Single-key response is a flat ranked list; `"*"` response is grouped by key, not fused. `filter` is the §5.4 restricted-Julia expression string:

```json
{ "join_group": "uuid", "key": "*", "text": "raw query text", "k": 10, "filter": "true" }
```

```json
{ "title": [ { "doc_id": "doc-123", "score": 8.41 } ], "body": [ { "doc_id": "doc-123", "score": 3.02 }, { "doc_id": "doc-456", "score": 2.87 } ] }
```

#### TextConfig (passthrough)

Mirrors `TextConfig`'s current nested shape (§5.3's warning) — `normalization`/`tokenization` sub-objects, plus a `stemmer` field the server resolves into the `transformation` value:

```json
{
  "normalization": { "lc": true, "del_punc": false, "del_diac": true, "del_dup": false, "group_num": false, "group_url": true, "group_usr": true, "group_emo": true },
  "tokenization": { "nlist": [1] },
  "stopwords": ["..."],
  "stemmer": { "kind": "snowball", "language": "spanish" }
}
```

No `qlist`/`slist`/`collocations` fields — those preprocessing knobs no longer exist in `TextSearch.jl` (§5.3's warning); a custom `AbstractTokenGenerator` would be needed to bring back char q-grams/skip-grams/collocations, and isn't part of this pass. `stopwords`+`stemmer` both resolve, via the `StemmerRegistry` (§5.3), into the single concrete `AbstractTokenTransformation` that becomes `TextConfig.transformation` — omit or pass `stemmer: null` to keep today's default (`IdentityTokenTransformation`, no stemming). If both stopword-removal and stemming are requested together, see §5.3's caveat on whether `AbstractTokenTransformation` composition needs its own wrapper, since `transformation` only ever holds one value.

## 8. Scripting Packages (new — Python, Julia & Node.js/JS scripting against the remote API, plus §8.5's embedded no-HTTP alternative)

!!! note "These are scripting libraries, not client SDKs — the distinction matters for how much ceremony belongs here"
    The goal is narrower than a general-purpose SDK product: give someone a set of plain, importable functions over `similarity-search-serve`'s HTTP API (§5) so they can write a script — batch-load a dataset, poll a long `allknn` Job, run a hybrid query, drive the §1 stress-client — without hand-rolling token auth, Avro encode/decode, or a Job-polling loop each time. No class hierarchy of request/response models, no client/server version-lockstep policy, no contract-testing pipeline — just functions a script calls. Both packages wrap the same server 1:1: no reimplementing server behavior client-side (RRF fusion for hybrid search, §6, stays server-side; the script just calls the endpoint).

!!! note "§8.1-8.4 vs §8.5: two different problems, not two implementations of the same one"
    §8.1-8.4 are for a script that talks to a `similarity-search-serve` process it does *not* share a machine/workdir with — the network round-trip and the HTTP/JSON boundary are the point, not overhead to eliminate. §8.5 is the opposite case: a script running *on the same machine, against the same `--workdir`* a `similarity-search-serve`/`similarity-search` CLI already uses — for that script, going through HTTP at all is pure overhead (serialize a vector to JSON, open a socket, deserialize the response) for calling code that already lives in this same repository, in the same process space, one `include`/`using` away. Added on user request (2026-08-18) as a fourth scripting surface, not a replacement for §8.1-8.4.

!!! warning "Nothing in this section is verified against a live implementation — these are proposed shapes, not confirmed names/dependencies"
    Unlike most of this document's warnings (grounded in reading `SimilaritySearch.jl`/`TextSearch.jl`/`RocksDB.jl` source), this section has no existing code to check against — both packages are net-new. Treat names, dependency choices, and the function list below as a starting proposal to react to, not a locked decision.

### 8.1. Shared shape, independent of language

* **Connection:** a small config value (`host`, `port`, `token`, §4.1) threaded through every call — either passed explicitly per call or held in one lightweight session object a script creates once at the top and reuses; either way, it's plain state, not a class hierarchy. No local workdir access, unlike the CLI (§1) — a script only ever talks HTTP.
* **Wire format:** JSON by default; an opt-in binary mode using the Avro encoding already defined for bulk endpoints (§4.4) for `append`/`search_batch`/`fetch`, for scripts moving enough data that JSON overhead actually matters. Check the response's `schema_version` (§4.4, §4.5) before decoding binary rather than assuming it matches what the package was built against — server and script are upgraded independently.
* **Job helper — the one piece of real ergonomic value here:** a `run_job(kind, params)` function that submits, polls `GET /api/v1/jobs/{job_id}` at a configurable interval, and returns the fetched result once `status` is `done` (raising on `failed`/`cancelled`). This is what makes §5.5's async Job model usable from a script instead of everyone hand-writing the same poll loop.
* **Long-Lived Search Policy (§3):** a synchronous `search` call can come back `429` pointing at `POST /api/v1/jobs/search`. Expose an explicit opt-in argument (`fallback_to_job=True`/`fallback_to_job=true`) rather than silently retrying as a Job — that turns a call from "fast or an error" into "possibly blocks for minutes," which a script should ask for, not get by default.
* **Cursors (§5.4):** a plain iterator (Python generator; Julia iterator) over pages, hiding `cursor` bookkeeping.

### 8.2. Python package (Suggestion) — `similarity-search-scripts` (PyPI)

* **HTTP layer:** `httpx` — one dependency covers both a simple blocking call (for a straight-line script) and `asyncio` (for a script that wants to fire off several Jobs concurrently).
* **Payloads:** plain `dict`s matching the JSON shapes in §7 (`AppendRequest`, `SearchRequest`, `HybridSearchRequest`, `FtIndexRequest`, `FtSearchRequest`, `TextConfig`, ...) — no `pydantic` model layer unless later experience shows scripts keep getting payload shapes wrong; start with the simplest thing that lets someone write a working script today.
* **Vectors:** accept/return `numpy.ndarray` when `numpy` is installed, with a plain-`list[float]` fallback otherwise — this is the actual ergonomic win over building raw JSON/Avro payloads by hand, without forcing a numpy dependency on a script that doesn't need it.
* **Avro binary mode:** `fastavro`, only exercised when a script opts into binary mode (§8.1).
* **Ready-made scripts, not just a library:** ship the §1 stress-client (a script that exercises most of the API automatically) as a console-script entry point of this same package, so it doubles as a worked example of using the library functions.

### 8.3. Julia package (Suggestion) — `SimilaritySearchScripts.jl` (unregistered/local at first, like `RocksDB.jl` today, §1 — candidate for the General registry once the API stabilizes)

* **HTTP layer:** `HTTP.jl`.
* **Payloads:** plain `Dict`/`NamedTuple` values matching §7's shapes, encoded with `JSON3.jl` — again, no struct-per-endpoint modeling layer unless it earns its keep.
* **Vectors:** plain `Vector{Float32}`/`Matrix{Float32}` in/out — Julia arrays are already the natural fit, no equivalent of the numpy decision needed.
* **Avro binary mode:** `Avro.jl`, for scripts that opt in, matching the server's `schema_version` handling (§4.4).
* **Job helper:** the same `run_job(kind, params)` function as the Python package, plus optionally a `Threads.@spawn`-friendly non-blocking variant so a script can fire off several Jobs and `wait` on them — a scripting nicety, not something the server needs to know about.
* **Dependency hygiene:** this package only ever speaks HTTP to a remote server — it must **not** depend on `SimilaritySearch.jl`, `TextSearch.jl`, or `RocksDB.jl`. Someone running scripts from a laptop with no local `RocksDB_jll` build should never need to compile any of the server's local packages just to call the API.

### 8.4. Node.js/JS package (Suggestion) — `similarity-search-scripts` (npm), added on user request, not yet built

* **HTTP layer:** the built-in `fetch` (Node ≥18, and every browser) — no HTTP client dependency needed at all, consistent with §8.1's "plain functions, not an SDK" framing. `async`/`await` throughout, matching the Python package's `asyncio` option and the Julia one's `Threads.@spawn` variant for firing off several Jobs concurrently.
* **Payloads:** plain objects matching §7's JSON shapes (`AppendRequest`, `SearchRequest`, `HybridSearchRequest`, `FtIndexRequest`, `FtSearchRequest`, `TextConfig`, ...) — no class-per-endpoint modeling layer, same reasoning as the other two packages.
* **Vectors:** plain `number[]`/`Float32Array` in/out — `Float32Array` accepted anywhere a vector is expected (matches the wire format's `Float32` numerically and avoids a silent double-precision round-trip), with a bare `number[]` fallback so a script that doesn't care about the distinction can just pass an array literal.
* **Avro binary mode:** deferred until a real Avro-for-JS library is picked and verified against this project's actual Avro schemas (§4.4) — same "don't trust a library's API without checking it" lesson `Persistence.jl`'s own `Avro.jl` correction (this codebase's implementation notes) already learned the hard way. JSON-only is a complete, working v1; binary mode is additive, not a prerequisite.
* **Module format:** ship as an ES module (`type: "module"` in `package.json`) with named exports, not a default-exported class — a script does `import { search, runJob } from "similarity-search-scripts"`, consistent with "plain functions" over an SDK object.
* **Job helper / cursors / Long-Lived Search Policy opt-in:** identical shape to §8.1's shared contract — `runJob(kind, params)` (submit + poll `GET /api/v1/jobs/{job_id}` + return on `done`, throw on `failed`/`cancelled`), an async iterator (`for await (const page of cursor(...))`) over cursor pages, and an explicit `fallbackToJob: true` opt-in on `search` rather than a silent retry-as-Job.
* **Ready-made scripts:** same idea as the Python package's stress-client script — ship it as an npm `bin` entry so `npx similarity-search-scripts stress-test` works without a separate install step.

### 8.5. Embedded/in-process package (new, on user request — no HTTP, direct access to the shared core engine)

!!! note "The premise: `similarity-search` (CLI) and `similarity-search-serve` (HTTP) are already two thin shells over one shared engine"
    Verified directly against this codebase's own module structure, not assumed: `cli_handlers.jl`'s `execute_build`/`execute_search`/`execute_rebuild`/etc. and `server.jl`'s `handle_append`/`handle_search`/etc. both call the exact same underlying modules — `Dataset` (open/close a dataset, get/put metadata), `Schema` (typed metadata records, filter matching), `IndexEngine` (`SearchEngineWrapper`, `create_engine`/`add_item!`/`search_live`/`calibrate!`/`mark_deleted!`), and `Persistence` (JLD2 snapshots, Avro dump/load records) — each already a real Julia module with a real `export` list (`src/dataset.jl`, `src/schema.jl`, `src/index_engine.jl`, `src/persistence.jl`). Neither the CLI dispatcher nor the HTTP router adds any actual *capability* on top of these four modules — they only add, respectively, `ArgParse` command parsing and `Oxygen`/JSON request handling around calls those modules already expose. A script that already lives on the same machine, with direct filesystem access to the same `--workdir`, doesn't need either shell: it needs exactly what these four modules already provide, `using`-ed directly.

* **Shape:** a plain function-per-operation API mirroring §8.1's "plain functions, not a class-per-endpoint SDK" philosophy, but skipping the network boundary entirely — `open_dataset(workdir, id) -> handle`, `append!(handle, items)`, `search(handle, vector; k=10, filter=nothing)`, `ftsearch(handle, text; k=10)`, `delete_item!(handle, doc_id)`, `fetch(handle, ids)`, `calibrate!(handle; kwargs...)`, `close_dataset!(handle)` — each a thin, documented wrapper composing `Dataset.open_dataset`/`IndexEngine.create_engine or restore_engine`/`IndexEngine.search_live`/etc. exactly the way `cli_handlers.jl`'s `execute_*` functions already do, just returning values instead of printing/exiting. `handle` bundles the `DatasetManager` + `SearchEngineWrapper` pair a script needs for every subsequent call — today's code always threads these two separately (see `_load_dataset_and_engine` in `cli_handlers.jl`), which is fine for a CLI command that runs once and exits, but a poor ergonomic fit for a script making many calls against the same open dataset.
* **Heavy operations run synchronously, no Job/spool machinery:** `allknn`/`fft`/`neardup`/`hsp`/`rebuild`/`dump`/`load` are exposed as plain blocking function calls (`allknn(handle; k=10) -> result`, etc.) — the same real `SimilaritySearch.jl` functions `execute_allknn`/etc. already call directly, just without going through `Jobs.create_job!`'s spool/dispatcher indirection. §5.5's async Job model exists specifically to let an HTTP request return immediately while heavy work continues server-side; an embedded script blocking its own call stack for the duration of its own heavy operation is the normal, expected way to call a function, not a regression. A script that *does* want to enqueue work for a separately-running `serve` process to pick up later can still `using Jobs` directly (already a real, exported module) rather than needing a bespoke wrapper here.
* **No tokens, no auth surface:** `Tokens`' whole reason to exist is authenticating a caller *arriving over the network* (§4.1) — irrelevant here, since the trust boundary for an embedded script is the OS's own file permissions on `--workdir`, the same boundary the CLI already relies on today. Not included in this package's surface at all, not merely unenforced.
* **The real, already-observed constraint this section must document rather than paper over**: RocksDB's exclusive per-process write lock (already hit and documented elsewhere in this codebase's own implementation notes, e.g. `describe`'s `read_only=true` open mode existing specifically to work around it) applies here exactly as it does between the CLI and a running server today — an embedded script opening a dataset for writing while `similarity-search-serve` (or another embedded script, or a CLI subprocess) already has it open for writing will fail with RocksDB's own lock error, not a friendly one this package invents. `open_dataset(workdir, id; read_only=true)` (mirroring `Dataset.open_dataset`'s existing kwarg) is the documented way to inspect a dataset a live server still has open, same as `describe` already does.
* **Packaging — a real open question, not a locked decision**: these four modules currently live *inside* `SimilaritySearchServer.jl` itself, which also pulls in `HTTP.jl`/`Oxygen.jl`/`ArgParse.jl` — none of which an embedding script needs at all. Two honest options: (a) expose them as a documented, stable public re-export of the existing `SimilaritySearchServer` package (`using SimilaritySearchServer: Dataset, IndexEngine, ...`) — zero new package, but a script pulls in the HTTP/CLI dependencies transitively regardless of never using them; or (b) extract `Dataset`/`Schema`/`IndexEngine`/`Persistence` into their own smaller package (e.g. `SimilaritySearchEngine.jl`, unregistered/local at first like `RocksDB.jl`/`SimilaritySearchScripts.jl` already are, §1/§8.3) that `SimilaritySearchServer.jl` itself then depends on, so the CLI/HTTP/embedded surfaces all share one real engine package instead of the engine being an implementation detail of one of its own consumers. (b) is the properly-factored answer and avoids forcing `HTTP.jl`/`Oxygen.jl` onto a script that only wants the engine, but is a real refactor (moving files between packages, updating every `using ..Dataset`-style relative import) — not attempted as part of writing this plan section, left as the recommended target shape for whoever implements §8.5.

!!! note "Resolved (2026-08-18, chunk 22): option (b) built — `SimilaritySearchEngine.jl`"

## 9. Implementation Roadmap

1. **Phase 1: Foundation:** Setup Julia 1.12 App structure, `ArgParse.jl` CLI split across the three binaries (`similarity-search`, `similarity-search-serve`, `similarity-search-ctl`, §1), and internal `DistanceRegistry`. Enforce the strict one-index-per-dataset rule (§1) at the dataset-creation layer from the start, since retrofitting it later would mean migrating any multi-index dataset created under a looser rule. Structure each binary's `ArgParseSettings` so the interactive-mode layer (§1's new subsection) can introspect it directly — one declared set of args/defaults/choices per command, not a second hand-written copy for the menu tree.
2. **Phase 1.5: Interactive Mode:** Once the three binaries' non-interactive parsers exist, add the Term.jl + stdlib `REPL.TerminalMenus` guided layer (§1) on top — command menu, per-argument prompts with dynamically-discovered pre-filled defaults, confirm-before-run panel, and the `isatty(stdin)` gate that keeps it from ever engaging inside a `LocalCLIExecutor`-spawned Job subprocess (§5.5). Pure CLI-layer work, so it can land before the server/persistence phases below without depending on them.
3. **Phase 2: Concurrency & Engine:** Implement the Request Collector, `:dynamic` task queue, and Core execution barriers with `BeamSearch` safeguards anchored to per-index calibrated baselines (§5.6).
4. **Phase 3: Persistence & Telemetry:** Connect RocksDB. Implement the `LOG` callback handlers to populate `op_log` (with delta times/context counters) and the `*_log` WAL column families. Stand up the `meta` column family per the declared/typed + `extra`-blob split (§4.5), including the optional `meta_idx_<field>` secondary-index CFs.
5. **Phase 3.5: Job Model & Persistence Layer:** Implement the async Job registry (including `blocked` status and the `JobExecutor`'s `kill(handle)` method, §5.5), the `result_cursors` table sharing the Job protocol's create/poll/resolve/GC lifecycle (§5.4), the `JobExecutor` abstraction with `LocalCLIExecutor` as the only backend, the 80/20 core-pool split (§2), and the split persistence layer (§4.4): `JLD2.jl` for index-struct snapshots, Avro for dataset content and API wire format — all laid out on disk per the §4.6 naming convention (`{uuid}.{kind}.{function}.{format}`, uuid-bearing paths) from the start, since retrofitting file layout after `dump`/`load` and job-result tooling already assume a shape is expensive. This must land *before* the web layer exposes any heavy operation, since those endpoints depend on it directly. `SlurmExecutor` is explicitly deferred past this phase — it's a backend swap behind the same interface, not a prerequisite. `similarity-search-ctl`'s job-control surface (`jobs queue|result|block|resume|kill|gc`, §1) is implemented against this same registry.
6. **Phase 4: Web Layer:** Implement `Oxygen.jl` routers, segmenting into `/api/v1/simsearch/` (data ops §5.1, administration §5.2, full-text §5.3), `/api/v1/jobs/`, `/api/v1/datasets/`, plus `/healthz`/`/readyz`/`/metrics`. Implement the `join_group`/`holds_metadata`/`key` dataset fields (§1, §5.3, §7), including the `key` validation whitelist (§4.6), so the multi-representation and multi-field join pattern is available before Phase 5 needs it for hybrid and per-field text search.
7. **Phase 5: Full-Text & Hybrid:** Integrate `TextSearch.jl`, establish `TextConfig` defaults (using its current nested `normalization`/`tokenization`/`transformation` shape, §5.3), implement the `StemmerRegistry` wiring up `TextSearch.jl`'s already-shipped `SnowballTokenTransformation` extension (add `Snowball`/`Languages` as this app's own dependencies to activate it — no new stemmer implementation needed, §5.3) as its first entry, implement vocabulary-drift detection (OOV-rate tracking + `rebuild`, tracked per `key`), implement `ftsearch`'s `key`/`"*"` fan-out and grouped-by-key response (§5.3), and wire up hybrid querying against the two-dataset join-group pattern (§6) rather than a single shared-index dataset.
8. **Phase 6: Scripting Packages (§8):** Once the HTTP surface (Phase 4) is stable, build `similarity-search-scripts` (Python) and `SimilaritySearchScripts.jl` against it — deliberately last, since both are thin wrappers over an API that should not still be shifting weekly. Ship the `run_job` blocking-poll helper and cursor iterator first (the two things that make scripting against §5.4/§5.5 tolerable), plus the §1 stress-client as the Python package's first worked-example script; Avro binary-mode support can follow once the plain-JSON path is exercised against a real deployment.
